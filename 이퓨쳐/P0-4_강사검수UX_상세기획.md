## 1. 목적·배경

AI 생성물(문항·자료·리포트 코멘트)을 **원장/강사가 최종 검수·수정**하고, **AI 개입강도를 직접 조절**하게 한다. 완제품 강요형 도구에 대한 불신을 해소하는 신뢰 장치.

- 시장 근거: 완제품 불신·자기주도 저하 우려(각 23%). 족보닷컴 AI "70%만 만족, 쓰레기 문제도 있다", "AI 티 나서 다시 허접하게"(전소영 강사). 설계형 원장은 프롬프트 직접 설계 선호.
- 대응 원칙: **사람이 최종 통제**. 검수 없는 자동 발행 금지.
- **진짜 차별점은 "원장 형식 자유도"**: AI가 초안을 대신 만들어주는 데 그치지 않고, **원장이 학생을 가르치는 그 방식·형식 그대로** 자료를 생성한다. 핵심은 "AI 생성물을 원장이 검수하느냐"가 아니라 **원장마다 다른 자기만의 자료 형식·구성을 자유롭게 구현**하는 유연함이다. 검수·AI 개입강도(최소/보통/최대)·톤 조절은 이 유연성을 받치는 **신뢰 장치(부속물)**일 뿐이다.

## 2. 사용자 스토리

- (원장) AI가 만든 문항을 그대로 쓰기 전에 내가 훑어보고 고칠 수 있어야 안심된다.
- (원장) AI 개입을 최소로 두고 내 프롬프트/자료 위주로 쓰고 싶을 때도, 최대로 맡기고 싶을 때도 있다.
- (강사) 리포트 코멘트가 너무 완벽해 보이지 않게, 우리 톤으로 다듬고 싶다.

## 3. 범위 (In/Out)

**In (MVP)**
- 공통 검수 패널: 생성물(문항·자료·리포트 코멘트)에 대해 **검토 → 수정 → 승인/반려** 단계
- **AI 개입강도(최소/보통/최대)** 설정: 기관 기본값 + 항목별 오버라이드
- 승인 전 배포/발행 차단(게이트)
- 수정 이력·승인자 기록(감사 로그 §22.4 연계)

**Out (후속)**
- 협업 리뷰(다중 검수자), 코멘트 스레드(P2), 프롬프트 직접 편집 고급 모드(P1)

## 4. 기능 요구사항 (FR)

- **FR-1** 검수 큐: Studio에 "검수 대기" 목록(문항·리포트 등 생성물) 표시.
- **FR-2** 검수 패널: 생성물 원본 표시 + 인라인 수정 + [승인]/[반려·재생성].
- **FR-3** 승인 게이트: 미승인 생성물은 학생 배포·학부모 발행 불가(P0-2·P0-5 연동).
- **FR-4** AI 개입강도: 설정 값(최소/보통/최대)이 생성 프롬프트·자동화 범위에 반영. 최소=사람 주도(초안만), 최대=완전 자동(검수만).
- **FR-5** 재생성: 반려 시 사유·톤 지정하여 재생성 요청(Seed/LLM 전략 연동).
- **FR-6** 이력·감사: 누가 언제 무엇을 수정·승인했는지 기록(§22.4).
- **FR-7** 톤 조절: 리포트 코멘트에 "덜 완벽하게/우리 학원 톤" 프리셋 제공.
- **FR-8** 원장 형식 템플릿: 원장이 **문항 형태·구성·출력 레이아웃을 지정·저장**하면, 같은 범위·같은 내용을 **그 형태로 반복 생성**한다. 저장한 템플릿은 재사용·공유 가능.
  - 예시(단어 퀴즈 3형태): ① 뜻 30개 제시 → 학생이 영단어 작성 ② 단어 음성 제시 → 학생이 철자+뜻 작성 ③ 단어·뜻 표에서 한쪽을 블랭크로 비워 채우기.

## 5. 화면·플로우

```
[Studio] 검수 대기 큐 → 항목 선택
   → 검수 패널 (원본 + 인라인 수정)
       ├─ [승인] → 배포/발행 게이트 통과
       └─ [반려] → 사유·톤 → 재생성
   설정: 기관 AI 개입강도(최소/보통/최대) + 항목별 오버라이드
```

## 6. 데이터 모델 / 입출력

**확장 필드 / 신규**

| 대상 | 필드 |
|---|---|
| 생성물 공통(문항·리포트 등) | reviewStatus(pending/approved/rejected), reviewedBy, reviewedAt, editDiff |
| Institution 설정 | aiAssistLevel(min/normal/max) 기본값 |
| 항목별 | aiAssistLevelOverride |
| 형식 템플릿(신규) | FormatTemplate(id, ownerId, name, questionShape, layout, config), reusable/shared 플래그 |

## 7. 기존 자산 연계 (재사용/확장)

- **재사용**: §9.5 강사 검수 워크플로우 골격, §9 콘텐츠 생성 엔진, Seed/Slot/LLM 전략, 감사 로그(§22.4), Studio 편집 UX(§8.5).
- **확장**: 검수를 **모든 생성물 공통 표준 단계**로 승격, 개입강도 설정 신규.

## 8. 예외·엣지 케이스

- 대량 생성물 검수 부담: 일괄 승인(신뢰 항목) + 스팟 체크 옵션.
- 개입강도 최대 + 검수 생략 설정 시: 최소한 사후 열람 로그 보장(완전 무검수 금지 정책).
- 재생성 반복 실패: N회 후 수동 편집 유도.
- 승인 후 원본 데이터 변경: 재검수 필요 플래그.

## 9. 완료 정의(DoD) · QA

- 문항·리포트 코멘트가 승인 전에는 배포/발행되지 않음(게이트 검증).
- 개입강도 설정이 실제 생성 결과에 차이를 만듦(최소 vs 최대 비교 QA).
- 수정·승인 이력이 감사 로그에 남음.

## 10. 의존성 · 오픈 이슈

- **연동**: P0-2(리포트 코멘트 승인), P0-5(문항 승인)가 이 워크플로우를 사용.
- **오픈 이슈(개발팀 확인)**: ①개입강도 3단계가 프롬프트/자동화에 구체적으로 어떻게 매핑되는지 ②일괄 승인 허용 범위(신뢰 vs 리스크) ③검수 SLA(파일럿 운영 부하).
