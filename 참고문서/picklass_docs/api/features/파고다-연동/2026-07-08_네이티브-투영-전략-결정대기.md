## 0. 사용자 결정 (2026-07-08)

> **"기존 픽클래스 로직을 파고다 vs 네이티브로 분기 처리하고 싶지 않다."**

→ 결론: **파고다 데이터를 픽클래스 네이티브 테이블로 투영(materialize)** 해서, 기존 로직이 파고다인지 모른 채 그대로 소비하게 한다. **코드 분기 0.**

- `pagoda_*` 5종 = **원본 staging/mirror** (파고다 #1~6 수신 결과, 이미 구현·검증됨)
- 네이티브 테이블(`users`·`access_codes`·`institution_settings`) = **투영 대상** — 기존 로직이 읽는 곳
- 투영 = mirror → 네이티브 복제. 기존 서비스 코드는 **손대지 않음**.

## 1. 확정된 네이티브 읽기 경로 (코드 근거)

기존 픽클래스(speaking)는 수강/이수를 **딱 두 관문**으로만 읽는다.

| 관문 | 위치 | 읽는 것 |
|------|------|---------|
| 수강 목록·기간 | `apps/api/src/lessons/lessons.service.ts` (getEnrolledCourses, ~L62) | `access_codes ac JOIN courses c ON ac.course_id=c.id WHERE ac.status_code='active' AND ac.user_id=:studentId AND c.course_type IN ('speaking','integrated')` + usage_start/end_date |
| 수료조건·기간 | `apps/api/src/config/config.service.ts` (getProgram, L102~134) | active `access_codes` 1건 → `institution_settings` **WHERE institution_id = access_codes.institution_id** → `default_completion_sentences/lesson_rate/minutes` |
| 달성값 | config.service.ts L156~175 | 발화량 `utterance_logs`, 진도 `lesson_results` (이미 speaking DB) |

> **핵심 통찰**: 완료조건 기관은 `users.institution_id`가 아니라 **`access_codes.institution_id`** 로 결정된다(config.service.ts L125·L131). → access_code에 어떤 institution_id를 넣느냐로 완료조건이 자동 분기된다(코드 분기 없이).

즉 **`access_codes` + `institution_settings` 두 개만 채우면** getEnrolledCourses·getProgram·이수판정·레슨 로직이 전부 파고다 학습자에게도 동작한다.

## 2. 투영 매핑 (mirror → 네이티브 3테이블)

### 2.1 `users` ← `pagoda_user_map` — ✅ 완료(§8-4)
로그인 시 `AuthService.provisionPagodaLogin`이 upsert. (user_id=`pagoda:{comCd}:{loginId}`, name=loginId, password_hash=`!pagoda-sso`, institution_id=파고다 고정, role=student)

### 2.2 `access_codes` ← `pagoda_enrollments` — 🔲 구현 필요
| access_codes 컬럼 | ← 소스 | 비고 |
|---|---|---|
| `user_id` | pagoda_enrollments.picklass_user_id | 로그인 후 채워짐 |
| `course_id` | pagoda_enrollments.picklass_course_id | classId 주매핑 |
| `usage_start_date` / `usage_end_date` | bgn_dt / end_dt | #4·#5 갱신 반영 |
| `status_code` | active (Refund·Cancel → inactive) | #3 반영 |
| `institution_id` | **결정 §4-1** (파고다 고정 vs comCd별) | 완료조건 소스 |
| `role_code` | `'student'` | NOT NULL |
| `code` | 생성(unique char(6)) | NOT NULL, §3 참고 |
| `registration_expiry` | end_dt | NOT NULL(Date) |
| `usage_period_days` | (end_dt − bgn_dt) 일수 | NOT NULL(Int) |

**멱등성**: `pagoda_enrollments.picklass_access_code_id` 컬럼(이미 설계됨)에 생성된 access_code id를 저장 → 있으면 update, 없으면 insert 후 backfill. (access_codes엔 (user,course) unique가 없어 이 링크로 dedup)

### 2.3 `institution_settings` ← `pagoda_company_settings` — 🔲 구현 필요 (§4-1 의존)
| institution_settings 컬럼 | ← 소스 |
|---|---|
| `default_completion_sentences` | completion_sentences |
| `default_completion_lesson_rate` | completion_attendance (출석=진도율) |
| `default_completion_minutes` | (파고다 미제공 → null) |

> ⚠️ 파고다 criteria의 **AND/OR**(`sentences&attendance` vs `sentences|attendance`)는 institution_settings에 표현 필드가 없다. 네이티브 getProgram은 non-null 임계값을 **각각 규칙으로 나열**할 뿐 조합 판정을 안 한다 → **완료 PASS/FAIL 조합 로직은 별도 확인 필요**(§5).

## 3. 투영 시점 (트리거)

- **로그인(#7)**: user provision 직후 → 그 사용자의 `pagoda_enrollments`(active) → `access_codes` upsert. (user_id가 이때 확정되므로 자연스러움)
- **#3·#4·#5 수신**: `pagoda_*` mirror 갱신 + **사용자가 이미 provision된 경우** 연결된 access_code 즉시 동기화(picklass_access_code_id로 찾아 update). 아직 로그인 전이면 다음 로그인 때 반영.
- **#2(기수정보)**: institution_settings 투영(§4-1 결정에 따라).

구현 위치 후보: speaking `AuthService.provisionPagodaLogin` 확장 또는 별도 `PagodaProjectionService`(로그인·수신에서 공용 호출).

### 4-1. 수료조건이 comCd별로 달라야 하는가?
완료조건은 `access_codes.institution_id → institution_settings`로 결정된다.

| 옵션 | 방식 | 장 | 단 |
|---|---|---|---|
| **A. 단일 정책** | 모든 파고다 access_code를 고정 기관(`0364cb92`)에. institution_settings 1행 | 가장 단순, 기관 신설 0 | **comCd별 상이 불가**. #2가 comCd마다 오면 서로 덮어씀 |
| **B. comCd별 정책** | comCd마다 picklass 기관+institution_settings 생성, access_code.institution_id=comCd 기관 | comCd별 수료조건, **여전히 코드 분기 0**(institution_id로 자동 분기) | "comCd 기관 매핑 불요" 결정 뒤집음, 기관 자동 생성 로직 필요 |

> 판단 포인트: **파고다 회사(comCd)마다 수료 기준(문장/출석)이 다른가?** 다르면 B, 전사 공통이면 A.

### 4-2. 횟수(quota) 게이트를 picklass가 하는가?
네이티브엔 횟수 개념이 **없다**(access_codes는 기간제). picklass에서 횟수 제한을 걸면 그게 곧 **파고다 전용 분기**.

- **권장: picklass는 횟수 게이트 안 함** — 파고다가 grant/소진 관리(class_cnt는 mirror에 보관만). 분기 0 유지.
- 대안: Phase B에서 `enrollment_usage` + 게이트(이때는 파고다 전용 로직 = 분기 발생 감수).

## 5. 미해결·리스크 (구현 전 점검)

- **완료 AND/OR 조합**: §2.3 참고. 파고다 criteria 조합 판정을 네이티브가 안 함 → 판정 로직 위치/방식 확인 필요.
- **access_codes.code 생성**: unique char(6) 충돌 회피(생성+재시도) 필요. 파고다 투영분 식별용 접두 규칙 검토.
- **course_type 필터**: getEnrolledCourses는 `course_type IN ('speaking','integrated')`만 노출 → 파고다 매핑 course의 course_type 확인.
- **picklass_course_id 미해결 시**: classId↔course 매핑이 안 된 enrollment는 access_code 투영 불가(course_id NULL) → 매핑표(§파고다 협의) 선행 필요.
- **institution_settings 소유**: backoffice 소유 테이블에 파고다 값 write → 소유·정책 정렬(§db-migration-policy).
- **B 선택 시**: 기관 자동 생성이 institutions에 파고다 회사 행을 늘림 → backoffice 정책 합의.

## 부록: 왜 read-through(§6.2)를 폐기했나
read-through `EnrollmentProvider`는 `partnerId==null ? AccessCodeProvider : PartnerProvider`로 **출처 분기**가 필수다. 사용자 요구(분기 금지)와 배치. 투영 방식은 access_codes/institution_settings를 미리 채워 **단일 경로**로 흡수하므로 분기가 없다. (대가: 코어 테이블에 파고다 원본 rows를 write — 단, `pagoda_*` mirror가 원본 소스로 남아 추적 가능)
