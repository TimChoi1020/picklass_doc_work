## 1. 설계 원칙

**3계층 분리 — 픽클래스 코어 무변경, 파고다용은 참조.**

```
파고다 자연키                pagoda_* 인터페이스(신설)         픽클래스 코어(참조·무변경)
 comCd                  →   pagoda_company_settings      →   (없음 — com_cd 자립)
 loginId·userId         →   pagoda_user_map              →   users
 classId                →   pagoda_enrollments           →   courses
 processId·detailId     →   pagoda_enrollment_processes  →   course_lessons (파고다 동봉 코드)
 (설문/공지)             →   pagoda_notices               →   (없음 — com_cd 스코프)
```

- **소유**: 신규 `pagoda_*` 테이블은 **backoffice**가 마이그레이션 소유. `api.picklass.com`은 `prisma db pull` 서브셋으로 참조(read + 협의 write), `speaking`은 `pagoda_notices`·`pagoda_enrollments` read.
- **참조 규칙**: 코어를 가리키는 FK는 speaking 선례(`external_access_tokens`)와 동일하게 **`@relation` 없는 plain `uuid` 스칼라(soft FK)**. 소유가 다른 부모를 강제 결합하지 않는다. 프로비저닝 전 상태를 허용하도록 참조 컬럼은 nullable.
- **기존 레이어 재사용**: backoffice에 이미 존재하는 `partner_api_keys`·`partner_api_configs`·`partner_auth_logs`·`partner_completion_logs`·`partner_enrollment_logs`는 인증·콜백 엔드포인트·감사 로그로 그대로 활용. 신규 `pagoda_*`는 **수강·식별자의 상태(master)**를 담당(로그 테이블엔 상태가 없음).

### 확정 사항 (2026-07-08)
1. **classId ↔ `courses`** — 수강(classId)은 **과정 단위 → `courses.id` 매핑**. 개별 차시는 processes/detailId로 내려오는 **파고다가 함께 보내주는 `course_lessons` 코드**로 연결(별도 매핑표 불요).
2. **attendance = 진도율** — "출석 인정 = 수업 미션 전부 완료" 정의상 차시 완료율로 계산. 별도 출석 컬럼·요구처 없음. (picklass `default_completion_lesson_rate` 개념)
3. **comCd별 기관 매핑 불요** — `com_cd`는 파고다 레이어 앵커 키로만 자립. `institution_settings`/`course_categories` 결합 제거 → `pagoda_company_settings`가 수료기준 소스. (단, provisioning용 파고다 **단일 고정 기관** 1개는 예외 — 6번·§6.1)
4. **신원은 로그인 upsert** — #1~6은 `pagoda_*` 미러에만 적재(코어 무기록), 픽클래스 `users`는 **#7 로그인 시점 upsert**(있으면 update, 없으면 insert)로 실체화. 상세 §6.
5. **#1~6 수신 인증 = `partner_api_keys`(Bearer) 우선** — 기존 파트너 키 방식으로 먼저 적용. IP/서명 등 검증 로직 강화는 추후.
6. **provisioning 규칙** — `users.user_id`=**`pagoda:{comCd}:{loginId}`**(충돌 방지), `institution_id`=**`0364cb92-22e8-4a93-9a2b-4fc16ecbd183`**(기존 파고다 고정 기관), `name`=**`loginId`**, `password_hash`=**sentinel `'!pagoda-sso'`**(로컬 로그인 차단), `is_temp_password`=false, `role_code`=student. §6.1.

## 3. API별 인터페이스 매핑 (1~7)

| # | API | 방향/메서드 | 인터페이스 처리 |
|---|-----|-------------|-----------------|
| 1 | 수강신청 | 파고다→오이지 POST | userInfo → `pagoda_user_map` upsert. classInfo → `pagoda_enrollments` insert(**classId → courses.id**). comInfo.completion → 수강 스냅샷. processes[] → `pagoda_enrollment_processes` 다건(detailId = 파고다 동봉 `course_lessons` 코드) |
| 2 | 기수정보 변경 | 파고다→오이지 PATCH | comCd 기준 `pagoda_company_settings` upsert(subway·freeLearning·completion). 이 테이블이 수료 판정 소스 |
| 3 | 환불·수업취소 | 파고다→오이지 PATCH | (com_cd, class_id)로 찾아 `status_code`=Refund/Cancel. **부분환불 시** 진행분 있으면 `completed`(이력 보존, 코어 삭제 안 함) |
| 4 | 기간조정·서비스티켓 | 파고다→오이지 PATCH | **classInfo.classId(필수, v1.2)**로 대상 특정 → 내려온 필드만 갱신. **`classCnt`=최종 총 부여 횟수(grant) → `pagoda_enrollments.class_cnt` 절대값 갱신**(서비스 티켓 추가 반영). bgnDt/endDt=기간 변경 |
| 5 | 종료일 일괄변경 | 파고다→오이지 PATCH | comCd의 **active 수강 전체** `end_dt` 일괄 UPDATE + `default_end_dt` 기록 |
| 6 | 설문·공지 | 파고다→오이지 POST | insert 후 `is_new=true`. speaking 앱이 com_cd 스코프로 조회해 New 노출, 열람 시 false |
| 7 | 로그인 인증 | 오이지→파고다 POST | `partner_api_configs.login_page_url`(+auth_secret)로 파고다 POST. 식별자는 `pagoda_user_map`에서 복원. 응답(isAuthenticated·classStatus·classInfo.active[]/completed[])은 `partner_auth_logs` 감사 + `pagoda_enrollments.status_code` 대조·정합 |

> **참조 방향 주의**: #1~6은 파고다가 상태를 push하는 로컬 미러, #7은 로그인 순간 파고다가 권위 있는 active/completed 목록을 반환하는 실시간 확인. 두 소스가 어긋나면 **#7(파고다 응답) 우선**, 미러(pagoda_enrollments) 보정.

## 4. Prisma 스케치 (backoffice, 참조 컬럼 = soft FK)

```prisma
// backoffice/prisma/schema.prisma — 신규. 코어 테이블은 무변경.
model PagodaEnrollment {
  id                     String    @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  comCd                  String    @map("com_cd") @db.VarChar(50)
  classId                String    @map("class_id") @db.VarChar(64)
  pagodaUserId           String    @map("pagoda_user_id") @db.VarChar(255)
  picklassUserId         String?   @map("picklass_user_id") @db.Uuid        // → users.id (soft)
  picklassCourseId       String?   @map("picklass_course_id") @db.Uuid      // classId 주매핑 → courses.id
  picklassAccessCodeId   String?   @map("picklass_access_code_id") @db.Uuid
  bgnDt                  DateTime? @map("bgn_dt") @db.Date
  endDt                  DateTime? @map("end_dt") @db.Date
  classCnt               Int?      @map("class_cnt")
  classKind              String?   @map("class_kind") @db.VarChar(10)
  statusCode             String    @default("active") @map("status_code") @db.VarChar(20)
  // … completion snapshot, subway, free_learning, class_min/week/lang
  @@unique([comCd, classId])
  @@index([comCd, statusCode])
  @@map("pagoda_enrollments")
}
```

> **정본은 DDL** — `picklass-backoffice/prisma/manual-sql/2026-07-08_pagoda-interface.sql`(5종 CREATE TABLE). DB 정책상 `schema.prisma`는 DDL을 DBMS에서 실행한 뒤 `prisma:pull`로 생성(손편집 금지). 위 스케치는 pull 결과 예시.

## 6. 반영(Provisioning) 전략 — 파고다 데이터 → 픽클래스

> ⚠️ **갱신(2026-07-08)**: 아래 **§6.2 read-through(EnrollmentProvider 분기)안은 폐기**됨. 사용자 결정 "로직 분기 금지"에 따라 **네이티브 투영(materialize) 방식**으로 대체 → [네이티브 투영 전략(결정대기)](./2026-07-08_네이티브-투영-전략-결정대기.md). §6.1 신원 provisioning은 그대로 유효.

인터페이스 테이블은 파고다 원본을 **보관**만 한다. 실제 학습이 되려면 픽클래스 실체에 흘려보내야 하는데, **"픽클래스 테이블 유지 + 파고다용 참조"** 원칙을 지키기 위해 **코어에 INSERT하는 것은 신원(users)뿐**이고, 수강 자격·기간·수료는 `pagoda_*`를 read-through로 판단한다.

speaking 선행 설계([파고다 파트너 수강 연동](../../../speaking/features/learn페이지-실API연동/20260623_파고다파트너_수강연동_개발계획.md))의 `EnrollmentProvider` + Entitlement 골격을 재사용한다.

### 6.1 신원(Identity) — 로그인(#7) 시점 upsert (JIT provisioning)

**기본 룰: 로그인 시 계정 존재하면 update, 없으면 신규 등록.** #1~6은 미러에만 적재하고 코어에 쓰지 않는다.

| 시점 | 픽클래스 `users` | `pagoda_*` 미러 |
|------|------------------|------------------|
| #1~6 수신 | **안 씀** | `pagoda_user_map`·`pagoda_enrollments`·`_settings`·`_notices` 적재 (`picklass_user_id`=null) |
| #7 로그인 | **upsert** — 있으면 update, 없으면 insert | `pagoda_user_map.picklass_user_id` 바인딩 |

**존재 판정 키 & 동작** — `pagoda_user_map(com_cd, login_id)` → `picklass_user_id`
- `picklass_user_id` 있음 → 그 `users` 행 **update**(name·email·user_type·status)
- map은 있으나 `picklass_user_id` null(#1은 왔으나 첫 로그인) → `users` **insert** 후 map에 backfill
- map 자체가 없음(예외: #1 없이 #7 진입) → 로그인 데이터로 map + users 동시 생성

> #7 요청은 comCd/loginId/userId만 실어오므로, name·userType 등 프로필 값은 #1이 채워둔 `pagoda_user_map`/`pagoda_enrollments`에서 읽어 채운다.
>
> **provisioning 규칙 (확정)**
> - `user_id`(unique) = **`pagoda:{comCd}:{loginId}`** — 기업코드+키 네임스페이스. 네이티브 픽클래스 계정·타 comCd와 절대 충돌하지 않음.
> - `institution_id` = **`0364cb92-22e8-4a93-9a2b-4fc16ecbd183`** (파고다 전용 고정 기관 — `institutions`에 **이미 존재**). comCd별로 기관을 만들지 않고, 파고다 학습자 전체를 이 기관 하나에 고정. 코드 상수(`PAGODA_INSTITUTION_ID`)로 관리.
> - `role_code` = student(학습자). `status_code` = active.
> - `name` = **`loginId`** — `users.name`이 NOT NULL인데 파고다가 이름을 안 주므로 loginId로 채움.
> - `password_hash` = **고정 sentinel `'!pagoda-sso'`** — 검증 불가값이라 로컬 로그인 영구 차단. 파고다 학습자는 **#7 SSO로만 인증**. `users.password_hash` NOT NULL 충족.
> - `is_temp_password` = **false** — SSO 사용자라 로컬 비번 변경 흐름 비해당.
> - `updated_at`은 `prisma db pull` 시 `@updatedAt` 미추론 → 앱에서 명시적 갱신 또는 DB 트리거.
>
> ※ 기관 행이 이미 있으므로 시드 불요. 이 기관에 브랜딩(`institution_brands`)·설정을 붙이면 파고다 공통 화이트라벨도 가능.

### 6.2 수강 자격(Entitlement) — access_codes에 실체화하지 않고 참조

`PartnerEnrollmentProvider`가 `pagoda_enrollments`(+`_processes`)를 읽어 `Entitlement` 생성. 소진은 speaking 계획의 `enrollment_usage` 원장으로 계산(파고다=grant, 픽클래스=consumption).

| Entitlement 축 | 파고다 → pagoda_* | 판정 |
|---|---|---|
| **scope**(과정) | classId → `courses`, detailId → `course_lessons`(파고다 동봉) | 명시적 grant |
| **validity**(기간) | `bgn_dt`/`end_dt` | `now ∈ [bgn,end]` |
| **quota**(횟수) | `class_kind`=Regular→`class_cnt` / Free→무제한 | grant − 소진 |
| **completion**(수료) | `completion_criteria`(sentences/attendance) | attendance=진도율, 공통 평가기 |

> **횟수(quota)는 파고다 전용 개념** — 네이티브 픽클래스는 기간제만이라 항상 무제한(`access_codes`엔 회차 필드 없음).
> - **grant(총 부여 횟수) = `pagoda_enrollments.class_cnt`** — 파고다 데이터에서 관리. **#1 부여, #4(서비스 티켓)로 최종값 갱신**.
> - **used(소진) = `enrollment_usage`** — 픽클래스가 레슨 완료마다 집계.
> - **잔여 = `class_cnt − used`** (Regular). Free는 일반 레슨 무제한 + 나만의 수업 20회 cap.

- 소진 트리거: `lesson_results.completed_at` 최초 NULL→설정 시 `enrollment_usage` 1행(재수강 무차감).
- learn 페이지·"수업 시작" 게이트는 출처(access_code vs 파고다) 무관하게 동일 인터페이스 소비 → **본서비스 동작 무변경**.

> `enrollment_usage`(소진 원장)는 **횟수 게이트(Phase B) 전용** — #1~6 수신·로그인 upsert에는 쓰이지 않으므로 뒤로 미뤄도 된다.

### 6.3 생명주기(#3·#4·#5) — 미러 갱신만, 즉시 반영

Provider가 매 호출 현재 상태를 읽으므로 코어를 건드리지 않고 반영된다.
- **#3 환불/취소** → `pagoda_enrollments.status_code`=Refund/Cancel → 게이트 차단. `module_histories` 등 **이력 보존**.
- **#4/#5 기간·횟수** → `end_dt`/`class_cnt` 갱신 → 다음 게이트 평가에 즉시 반영.

### 6.4 설정·공지(#2·#6) — 순수 참조
- #2 → `pagoda_company_settings` read-through(완료 판정·모드)
- #6 → `pagoda_notices` speaking 앱 조회(New뱃지)

### 6.5 선행 설계 정합 (speaking 문서 갱신 필요)

이번 push 스펙이 speaking 문서의 미결을 해소·변경한다:
1. **D5(자격 전달 방식) 해소** — 파고다가 grant를 #1~5로 **push**해 `pagoda_enrollments`에 적재 → 별도 파고다 pull 불필요(#7로 reconcile).
2. **scope 방식 변경** — speaking 문서의 *"scope = 파트너 소유 L1 카테고리(`course_categories.partner_id`)"* 는 **comCd 기관 미매핑** 결정으로 성립 안 함 → scope는 `pagoda_enrollment_processes`의 **명시적 grant**로 대체.
3. **D5-a(파고다 user_pk_id)** — `pagoda_user_map.pagoda_user_id`로 해소.
