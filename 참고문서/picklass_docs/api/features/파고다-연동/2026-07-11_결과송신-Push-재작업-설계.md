## 1. 목표

명세 #8·#9·#10은 **픽클래스가 파고다로 POST** 하는 결과 송신 API다.

| # | 이름 | 시점 | 방향 |
|---|------|------|------|
| 8 | 출석 완료(history) | 수업(레슨 세션) 완료 시 | 픽클래스 → 파고다 |
| 9 | 수료 완료(completion) | 과정 수료조건 충족 시 | 픽클래스 → 파고다 |
| 10 | 평가(evaluation) | 평가(LT/MR) 산출 시 | 픽클래스 → 파고다 |

현행 `api.picklass.com`은 #8·#9를 **GET Pull**(파고다가 우리를 조회)로 임시 구현 → **방향·데이터가 명세와 불일치**. 본 문서는 Push 전환 설계.

## 4. 필드 매핑표 (명세 → 우리 소스)

| 명세 필드 | 우리 소스 | 상태 |
|---|---|---|
| userInfo.comCd / loginId | `pagoda_user_map`(picklass_user_id 조인) | ✅ 가용 |
| userInfo.userId | `pagoda_user_map.pagoda_user_id` | ✅ 가용 |
| userInfo.totSpeechCnt | `utterance_logs.sentence_count` 합(user) | ✅ 가용 |
| classInfo.classId | **`pagoda_enrollments.class_id`** (파고다 원본) | ✅ 가용 (현행 Pull은 course_lesson_id 사용 — **교체 필요**) |
| processes.processId / detailId | **역매핑**: `course_lesson_id` → `pagoda_content_map.detail_id` (+ process_id from `pagoda_enrollment_processes`) | ⚠️ 대응표 값 채워야 함(협의) |
| #8 classInfo.speechCnt (세션별) | `utterance_logs` ↔ 수업(레슨) 연결 필요 | 🔴 미보유 — `utterance_logs.course_lesson_id` 없음(협의/스키마) |
| #8 bgnDttm / endDttm | `module_histories.started_at` / `completed_at` | ✅ 가용 |
| #8/#10 todayExpression, corrections | 학습 세션 AI 피드백 산출물 | 🔴 미저장(§협의 — 저장 위치 정의 필요) |
| #9 (수료 판정) | `pagoda_enrollments.completion_criteria`(a&b/a\|b) + 달성값(발화/진도) | ⚠️ **AND/OR 판정 로직 신규**(§5) |
| #10 evalInfo(scores/memos/evalType/evalLevel) | 평가(LT/MR) 기능 산출물 | 🔴 평가 기능 미구축 — 대체로 future/협의 |

**요약**: **#9가 가장 완결 가능**(수료 판정만 붙이면 됨), #8은 일부 필드 소스 필요, #10은 평가 기능 선행.

## 5. 핵심 수정·신규

1. **classId 교체** — `course_lesson_id`(우리) → `pagoda_enrollments.class_id`(파고다). 우리 완료 레코드(레슨/모듈)에서 → 해당 course → `pagoda_enrollments`(picklass_course_id 매칭, 학습자) → class_id 역추적.
2. **processes 역매핑** — `pagoda_content_map`을 역방향 조회(course_lesson_id → detail_id), `pagoda_enrollment_processes`에서 process_id. (대응표 값 의존)
3. **userInfo 재구성** — `pagoda_user_map`으로 comCd/loginId/pagoda userId 복원(현행은 우리 userId만).
4. **#9 수료 AND/OR 판정 신규** — 네이티브 getProgram은 진행률만이라 PASS/FAIL 없음 → criteria(a&b/a|b) + 달성값으로 수료 여부 산정하는 판정기 신설. 수료 성립 시에만 #9 전송.

## 6. 아키텍처 — 트리거·전송

이벤트(#8 레슨 완료 / #9 수료 / #10 평가)는 **speaking 런타임**에서 발생, 전송·인증 설정은 **api(파고다 통합 계층)** 소유. 파고다 엔드포인트 가용성에 결합되지 않도록 **아웃박스(outbox) 패턴** 권장.

```
speaking(이벤트 발생) ──write──▶ pagoda_outbound_events(pending)
                                      │
                          api drainer(주기/워커)
                                      │ build payload(§4) + POST(파고다)
                                      ├─ 200 → status=sent
                                      └─ 실패 → attempts++/backoff, partner_*_logs 기록
```

- **신규 테이블 `pagoda_outbound_events`** — `id, event_type(#8/#9/#10), com_cd, class_id, picklass_user_id, course_lesson_id?, status(pending/sent/failed), attempts, last_error, payload_snapshot?, created_at, sent_at`. 멱등키(event_type, class_id, course_lesson_id)로 중복 방지.
- **페이로드 빌드는 drainer(api)** 에서 DB 조회로 수행(§4 매핑 재사용) → 로직 1곳 집중, speaking은 최소 이벤트만 적재.
- **인증/엔드포인트** — `partner_api_configs`: #8→`history_endpoint`, #9→`completion_endpoint`, #10→(신규 `eval_endpoint` 필요), 공통 `auth_secret`. base URL 운영/테스트 분기.
- **로깅·재시도** — `partner_completion_logs`(#9)·`partner_*_logs` 재사용 또는 통합. 지수 백오프 + 최대 시도.
- **현행 GET Pull(attendance/completion) 처리** — Push 개통 후 **폐기(deprecate)**. 매핑 로직은 drainer로 이전.

> 대안(단순): speaking이 api 내부 엔드포인트를 이벤트 시 동기 호출 → api가 즉시 POST. 재시도 버퍼 없음 → 파고다 장애 시 유실. **권장하지 않음**(outbox가 견고).

## 7. 미해결·협의

- **#10 평가(LT/MR) 기능** — 산출 주체·데이터 모델 미정(대체로 future).

- **수료 AND/OR 판정 소유·위치**(api drainer vs speaking).
