## 1. 개요

**알림 내역(PKS-MY-010)은 "설정에 따라 실제 발송된 알림"의 로그**다. 따라서 핵심 작업은
**알림 생성(발송) 파이프라인**이며, 내역은 그 기록 단계의 산물이다.

현재 상태: 화면(목록·상세)은 mock(`my/notifications/data.ts`), 생성 로직·발송·기록 모두 **없음**.
단, 공유 DB에 backoffice 소유 `notifications` 테이블은 **존재**.

---

## 2. 파이프라인 — 단일 관문

모든 알림은 하나의 관문 `NotificationService.create(userId, notif)`를 통과한다.

```
[Producer] ──▶ create(userId, notif)
   │
   ├─ ① Gate     : notification_settings 카테고리 ON? (OFF면 전체 중단)
   ├─ ② Record   : notifications 테이블에 1행 (= 알림 내역)
   └─ ③ Deliver  : push(FCM) — DND면 억제 / kakao·email — opt_in 시
```

**게이트 순서(확정)**
1. **카테고리 OFF → 전체 skip** (기록·발송 모두 안 함). 내역은 "실제 나간 것"만 남는다.
2. **Record는 항상 수행**(카테고리 ON인 경우). 인앱 내역 확보.
3. **DND 시간대 → 푸시(③)만 억제, 내역(②)은 기록**. 사용자는 앱을 열면 내역에서 확인.

## 5. 기록 위치 — 공유 `notifications` write (확정)

> 결정(2026-07-09): 신규 speaking 테이블을 만들지 않고 **공유 `notifications`(backoffice 소유)에 write**.
> 사용자 알림 인박스를 서비스 통합. **backoffice와 write 권한 정렬 필요.**

`notifications` 기존 컬럼: `id·user_id(UUID)·type·title·message·action_text·action_url·is_read·persistent·expires_at·metadata·created_at·updated_at`
(`user_id`가 UUID라 `users.id`와 정합 — 타입 불일치 없음)

speaking 기록 규칙:
- `type` = `'speaking.study_reminder'` 등 **네임스페이스 prefix**로 서비스 구분
- `metadata`(JSONB) = `{ category, source, refId }` 등 표시 외 부가정보
- `is_read=false`로 생성, 상세 진입 시 `true`
- speaking `schema.prisma`에 `notifications` 모델 **직접 작성**(READ + is_read/insert용, `prisma:pull` 금지)

## 6. 스케줄러 실행 — 외부 크론 (확정)

> 결정(2026-07-09): api 서버리스 가정 하에 **외부 크론이 보호된 내부 엔드포인트를 호출**.

- 엔드포인트: `POST /internal/notifications/dispatch/:type` (`study-reminder` | `review-quiz`)
- 보호: JWT 아님. **크론 시크릿 헤더**(`X-Cron-Secret` = env `CRON_SECRET`)로 검증하는 가드.
- 크론 소스: **Vercel Cron**(`vercel.json`) 또는 **Supabase pg_cron**(`net.http_post`).
- 주기: `study-reminder`는 분 단위 정밀 매칭이 이상적이나, 크론 granularity에 맞춰 **N분 윈도우 매칭**(`reminder_time`이 now±N분) 허용. `review-quiz`는 시간/일 단위.
