## 1. 의도·배경

### 왜 Speaking은 별도 파이프라인이 필요한가

튜터링의 Cache-Aside 패턴(첫 학습자가 생성 트리거)은 Speaking에서도 그대로 재사용된다.
그러나 Speaking은 튜터링에 없는 **선행 단계**가 필요하다.

| 구분 | 튜터링 | Speaking |
|------|--------|----------|
| 콘텐츠 원천 | 지문(texts) 전체 | 지문에서 추출한 **핵심문장 N개** + 각 문장의 **핵심표현 N개(원형)** |
| 모듈 간 관계 | 독립 | LRN·SHD·SFB·SMK가 **동일 N개 표현** 공유 |
| 대화문 | 없음 | RPB·RPF가 **동일 대화문 1편** 공유 |
| 생성 시점 결정 | 첫 학습 진입 시 자동 | 핵심표현·대화문 모두 **Studio 지문 등록 시 사전 생성** |

### 결정 배경

- LRN→SHD→SFB→SMK 체인이 동일 N개 표현을 소개→반복→변형→생성 순으로 내재화하는 구조이므로,
  모듈별로 독립 추출하면 표현이 달라져 학습 일관성이 깨진다.
- RPB·RPF의 대화문을 각자 생성하면 두 모듈이 다른 대화문을 사용하게 된다.
- `core_expressions`·`core_dialog`는 지문 자체의 속성이므로 모듈 배치와 무관하게
  지문 등록 시점에 확정 가능하다.

## 2. 전체 파이프라인 개요

```
[Studio — 지문 등록 시점]
  ↓
  1) 지문(texts) 등록
  2) 레벨 기반 핵심문장·핵심표현 N개 선정
  3) texts.core_expressions 저장
  4) core_expressions 기반 RPB·RPF 공용 대화문 생성 → texts.core_dialog 저장

[Speaking API — 첫 학습 진입 시점 (Cache-Aside)]
  ↓
  5) texts.core_expressions 기반
     LRN / SHD / SFB / SMK / RPF 문항 생성 → module_questions 저장
  6) texts.core_dialog 기반
     RPB 문항 생성 → module_questions 저장

[이후 학습자]
  ↓
  7) module_questions 캐시 히트 → 즉시 반환
```

## 3. Stage 1 — Studio: 핵심표현·대화문 사전 생성

### 3.1 핵심문장·핵심표현 선정 기준

**선정 순서**: 핵심문장을 먼저 추출하고, 각 문장에서 핵심표현을 식별한다.

- **핵심문장**: 지문에서 학습 가치가 높은 완성형 문장(full sentence) N개
  - CEFR 레벨 기반 N개 결정 (핵심문장 수 = 핵심표현 수)

    | CEFR 레벨 | N개 |
    |-----------|-----|
    | Pre-A1 ~ A1 | 3개 |
    | A2 | 3개 |
    | B1 | 4개 |
    | B2 | 4개 |
    | C1 ~ C2 | 5개 |

  - LRN 소개 → SHD 따라말하기 → SFB 빈칸 → SMK 재구성에 동일 문장을 사용하므로
    반드시 완성형 문장으로 선정한다.

- **핵심표현**: 각 핵심문장에 담긴 핵심 word / idiom / phrase
  - **원형(base form)**으로 표기한다 (동사 원형, 명사 단수형 등)
  - 예: `"make a reservation"`, `"in the wake of"`, `"sustainable"`
  - SFB 빈칸 채워말하기의 출제 대상이 되며, RPF 미션 목록으로도 활용된다.

### 3.2 texts 테이블 스키마 변경 (신규 필드 2개)

> **완료** — DDL 실행 및 schema.prisma 반영 완료.
> 변경 절차: [`../../operations/db-management.md`](../../operations/db-management.md)

```sql
ALTER TABLE texts
  ADD COLUMN IF NOT EXISTS core_expressions JSONB,
  ADD COLUMN IF NOT EXISTS core_dialog      JSONB;
```

#### core_expressions 스키마

```json
[
  {
    "seq": 1,
    "sentence": "I'd like to make a reservation at your hotel.",
    "translation": "호텔에 예약을 하고 싶습니다.",
    "expression": "make a reservation",
    "expression_meaning": "예약하다",
    "blank_version": "I'd like to ___ _ ___ at your hotel.",
    "blank_answer": "make a reservation"
  }
]
```

| 필드 | 용도 |
|------|------|
| `sentence` | LRN 카드 본문 / SHD 낭독 원문 / SMK 재구성 목표 |
| `translation` | LRN 한국어 해석 표시 |
| `expression` | **원형** — RPF 미션 목록 표시 |
| `expression_meaning` | LRN 핵심표현 강조 박스 |
| `blank_version` | SFB 문제 |
| `blank_answer` | SFB 정답 |

#### core_dialog 스키마

```json
{
  "topic": "호텔 체크인",
  "situation": "호텔 프런트에서 체크인하는 상황",
  "turns": [
    { "role": "guest", "line": "I'd like to make a reservation.", "translation": "예약하고 싶습니다." },
    { "role": "host",  "line": "Sure! May I have your name?",     "translation": "네! 성함을 알려주시겠어요?" }
  ]
}
```

#### core_dialog 레벨별 턴수 기준

| CEFR 레벨 | 턴수 |
|-----------|------|
| Pre-A1 ~ A1 | 6턴 |
| A2 | 8턴 |
| B1 | 10턴 |
| B2 | 10턴 |
| C1 ~ C2 | 12턴 |

### 3.3 구현 방식 (Studio)

`SpeakingCoreDataService.generateAll()` — fire-and-forget 패턴.
프롬프트는 `speaking_passage_prompts` 테이블에서 `code`로 조회 (backoffice 관리).

| `code` | 역할 |
|--------|------|
| `core-expressions` | 핵심문장·표현 추출 지시문 |
| `core-dialog` | 대화문 생성 지시문 |

## 4. Stage 2 — LRN·SHD·SFB·SMK 연계 생성 (Cache-Aside)

### 4.1 동일 N개 표현 공유 원칙

```
texts.core_expressions (N개)
  │
  ├── LRN (소개)       : sentence + expression + translation → 학습 카드 N장
  ├── SHD (따라말하기) : sentence → 낭독/발음평가 문항 N개
  ├── SFB (빈칸채우기) : blank_version + blank_answer → 빈칸 문항 N개
  └── SMK (문장만들기) : sentence 단어 분해 → 순서 맞추기 문항 N개
```

### 4.2 각 모듈의 content_generation_instruction 방향

| 모듈 | 전략 | content_generation_instruction 요지 |
|------|------|-------------------------------------|
| LRN | `instruct` | `sentence` + `expression` + `translation`을 카드 형태로 구성 |
| SHD | `extract` | `core_expressions[].sentence`를 그대로 낭독 문항으로 추출 |
| SFB | `extract` | `core_expressions[].blank_version`을 문제, `blank_answer`를 정답으로 추출 |
| SMK | `instruct` | `core_expressions[].sentence`를 단어 단위로 분해해 순서 맞추기 문항 생성 |

### 4.3 프롬프트 데이터 주입 구조

튜터링의 `textbookContext` 주입 패턴을 Speaking 전용으로 확장한다.

```
[지문]
{texts.title}
{texts.content}

[핵심문장·핵심표현 — N개]
{texts.core_expressions}

[콘텐츠 생성 지시문]
{ai_modules.content_generation_instruction}
```

`core_expressions`가 없는 지문은 기존 경로(지문 전체에서 LLM 자율 추출)로 폴백.

### 4.4 생성 시점

```
GET /lessons/:lessonId/module-data?moduleCode=SHD
  ↓ module_questions 조회 (module_id + text_id, status='active')
  ├── 캐시 HIT → 즉시 반환
  └── 캐시 MISS → Gemini 생성 → module_questions INSERT → 반환
```

LRN·SHD·SFB·SMK는 모듈별로 독립 캐시 관리.

## 5. Stage 3 — RPB·RPF 소비 구조

### 5.1 모듈 진행 구조

```
texts.core_expressions (N개)
  │
  ├── [대화문 생성 소스] ──▶ texts.core_dialog (1편)
  │                               │
  │                               ├── RPB (Role-Play Basic)
  │                               │     ├── 대화문 따라말하기
  │                               │     └── 역할극
  │                               │
  │                               └── RPF (Role-Play Free) ← 맥락 참조 표시용
  │
  ├── [미션] ──▶ RPF (Role-Play Free)
  │               └── 자유대화 — 미션: core_expressions N개 표현 활용
  │
  ├── (사전 데이터 무관) ──▶ FRT (Scenario Based Free Talking)
  │                          └── 시나리오 기반 자유회화 — core 데이터 불필요, Cache-Aside 패턴 유지
  │
  └── (사전 데이터 무관) OMP (One Minute Presentation)
                          └── 1분 스피치 — 자유 주제
```

- **RPB**: `core_dialog` 기반 역할극 문항 생성 (Gemini 주입).
- **RPF**: `core_expressions` N개를 미션으로 문항 생성 (Gemini 주입) + `core_dialog`를 화면에 맥락 참조용으로 표시 (API 미구현).
- **FRT**: `core_expressions`·`core_dialog` 사전 데이터 불필요. Cache-Aside 패턴으로 첫 진입 시 시나리오 기반 문항을 Gemini가 생성하는 방식이 가능하나, **현재 상태 유지 vs. 개선 여부 의사결정이 필요하다** (§8 #7 참조).
- **OMP**: 미션 표현 없이 자유 주제.

### 5.2 각 모듈의 content_generation_instruction 방향

| 모듈 | 주입 데이터 | content_generation_instruction 요지 |
|------|------------|--------------------------------------|
| RPB | `core_dialog` | 대화문의 각 턴을 `dialog-turn` 문항으로 변환. guest 턴은 answer에 원문, host 턴은 answer 빈 문자열 |
| RPF | `core_expressions` | 각 표현을 `expression-mission` 미션으로 변환. text = 표현 원형, options.meaning + sentence 포함 |

### 5.3 core_dialog 생성 시점

Studio 지문 등록 시 `core_expressions` 완료 직후 생성. RPB·RPF 첫 진입 시 이미 존재.
