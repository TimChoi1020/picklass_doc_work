## 1. 의도·배경

### 왜 사전 생성이 필요한가

Speaking은 튜터링과 달리 LRN → SHD → SFB → SMK → RPB → RPF 전 모듈이
**동일한 핵심표현 N개와 대화문 1편을 공유**한다.

```
texts.core_expressions (N개)
  ├── LRN (소개)       : sentence + expression 카드 학습
  ├── SHD (따라말하기) : sentence 낭독·발음 평가
  ├── SFB (빈칸채우기) : blank_version 문항
  ├── SMK (문장만들기) : sentence 단어 순서 맞추기
  └── RPF (자유대화)   : expression 미션 목록

texts.core_dialog (1편)
  ├── RPB (기본역할극) : 대화문 따라말하기·역할극
  └── RPF (자유대화)   : 대화문 맥락 참조
```

> **FRT·OMP·VLM**은 `core_expressions`·`core_dialog`를 사용하지 않아 본 문서 범위에서 제외된다.
> 단, **FRT**는 Cache-Aside 패턴으로 `module_questions` 생성이 가능하므로
> 현재 상태 유지 vs. 개선 여부 별도 의사결정이 필요하다 (파이프라인 문서 §8 #7 참조).

이 공유 데이터가 모듈 진입 시점에 없으면 캐시 미스 시 Speaking API가 지문 전체에서
LLM이 자율 추출하는 폴백 경로를 탄다. 일관성 보장과 비용 절감을 위해
**Studio 지문 등록 시점에 사전 생성**한다.

### 튜터링과의 차이

| 구분 | 튜터링 | Speaking |
|------|--------|----------|
| 콘텐츠 원천 | 지문 전체 | `core_expressions` N개 + `core_dialog` 1편 |
| 모듈 간 관계 | 독립 | LRN·SHD·SFB·SMK·RPB·RPF가 동일 데이터 공유 |
| 생성 시점 | 첫 학습 진입 시 (Cache-Aside) | **지문 등록 시** (사전 생성) |

## 2. 아키텍처 결정

### 2.1 서비스 분리 유지

기존 `SpeakingPassageService`(원문 → speaking용 지문 변환)와
신규 `SpeakingCoreDataService`(핵심표현·대화문 생성)는 **별도 서비스로 분리 유지**한다.

**분리 이유**: 목적이 다름(변환 vs. 구조 생성), 독립적 재시도·캐시 무효화 가능,
기존 동작 서비스에 변경 리스크 없음.

### 2.2 실행 패턴 — fire-and-forget

지문 INSERT 완료 즉시 200 응답 반환. Gemini 호출은 백그라운드 진행.

```
passages.service.ts: create()
  ├── texts INSERT
  ├── textAnalyses.runDefaults()          ← 동기 (level 보강 필요)
  ├── void speakingPassage.generate()     ← 기존 fire-and-forget
  └── void speakingCoreData.generateAll() ← 신규 fire-and-forget
                                            (level 보강 완료 후 호출)
```

### 2.3 순차 의존성

`core_dialog`는 `core_expressions` 완료 후 생성한다.
두 fire-and-forget(`speakingPassage`, `speakingCoreData`)은 서로 병렬 실행.

```
generateAll(textId, content, level)
  ├── Step 1: generateCoreExpressions() → texts.core_expressions 저장
  └── Step 2: generateCoreDialog()      → texts.core_dialog 저장
```

### 2.4 content 수정 시 재생성

`passages.service.ts` `update()`에서 content 변경 시:
null 초기화 완료 후 `speakingPassage.generate()`와 `speakingCoreData.generateAll()`을
`Promise.allSettled`로 병렬 실행한다. null 초기화 전에 생성이 시작되면
덮어쓰기 경합이 발생할 수 있으므로 반드시 null 초기화 `.then()` 안에서 시작.

### 2.5 프롬프트 관리

`SpeakingPassageService`와 동일하게 `speaking_passage_prompts` 테이블(backoffice 관리)에서
`code`로 조회한다.

| `code` | 용도 |
|--------|------|
| `core-expressions` | 핵심문장·핵심표현 추출 지시문 |
| `core-dialog` | 대화문 생성 지시문 |

프롬프트 미존재·`status != 'active'` 시 graceful skip (경고 로그만 남김).

## 3. DB 변경

> **공유 DB 주의**: `texts` 테이블은 tutoring과 동일 Supabase 인스턴스.
> DDL 실행 전 tutoring 팀 사전 정렬 필수.
> 실행 절차: [`../../operations/db-management.md`](../../operations/db-management.md)

### DDL

```sql
-- studio.picklass.com/apps/api/prisma/manual-sql/2026-06-16_texts_core_expressions_core_dialog.sql
ALTER TABLE texts
  ADD COLUMN IF NOT EXISTS core_expressions JSONB,
  ADD COLUMN IF NOT EXISTS core_dialog      JSONB;
```

nullable JSONB — tutoring 측 기존 쿼리에 영향 없음.

### core_expressions 스키마

```json
[
  {
    "seq": 1,
    "sentence": "I'd like to make a reservation at your hotel.",
    "translation": "호텔에 예약을 하고 싶습니다.",
    "expression": "make a reservation",
    "expression_meaning": "예약하다",
    "blank_version": "I'd like to ___ _ ___ at your hotel.",
    "blank_answer": "make a reservation"
  }
]
```

### core_dialog 스키마

```json
{
  "topic": "호텔 체크인",
  "situation": "호텔 프런트에서 체크인하는 상황",
  "turns": [
    { "role": "guest", "line": "I'd like to make a reservation.", "translation": "예약하고 싶습니다." },
    { "role": "host",  "line": "Sure! May I have your name?",     "translation": "네! 성함을 알려주시겠어요?" }
  ]
}
```

### level별 N개 기준

| CEFR 레벨 | 핵심문장·표현 N개 | 대화문 턴수 |
|-----------|------------------|------------|
| Pre-A1 ~ A1 | 3개 | 6턴 |
| A2 | 3개 | 8턴 |
| B1 | 4개 | 10턴 |
| B2 | 4개 | 10턴 |
| C1 ~ C2 | 5개 | 12턴 |

## 4. API

### 개별 재생성

```
POST /passages/:textId/core-data/generate
Body: { "force": false }   ← false: 이미 있으면 skip, true: 덮어쓰기
응답: { "textId": 42, "status": "started" | "skipped" }
```

Studio UI 지문 상세 페이지의 "핵심데이터 생성" 버튼으로 연결 (미구현).
