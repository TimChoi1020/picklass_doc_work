# 과정 탐색(explore) 페이지 성능 개선 — 검색 debounce + 파트너 카테고리 캐시

> **작성일**: 2026-07-09
> **서비스**: speaking.picklass.com
> **대상 화면**: `/learn/explore` (과정 탐색, PKS-CL-003)
> **목적**: 카테고리별 과정 검색이 느린 문제의 원인 분석 및 개선

---

## 1. 증상

과정 탐색 페이지에서 카테고리 선택·과정명 검색이 느리게 반응한다. 특히 검색어를
입력할 때 렉이 체감된다.

## 2. 원인 분석

경로: `explore/page.tsx` → `coursesService.getExploreCourses` → `GET /courses`
→ `courses.service.ts CoursesService.getCourses`

| # | 원인 | 위치 | 영향 |
|---|------|------|------|
| 1 | **검색어 입력마다 API 호출 (debounce 없음)** — `searchQuery`가 조회 effect 의존성에 직접 포함되어 키 입력 1회당 `GET /courses` 1회 발사. 이전 요청은 `cancelled` 플래그로 화면 반영만 막고 네트워크·DB 부하는 그대로 발생 | `apps/web/src/app/(tabs)/learn/explore/page.tsx` | **큼 (체감 주범)** |
| 2 | **요청 1건당 순차 DB 왕복 3회** — 인증 가드 `touchActivity` + 파트너 L1 카테고리 raw SQL(매번 재조회, 캐시 없음) + 과정 `findMany`. 원격 Supabase라 왕복당 수십 ms, 3배 누적 | `apps/api/src/courses/courses.service.ts:24` | 큼 (원인 1과 곱연산) |
| 3 | 검색이 `ILIKE '%..%'`라 선행 와일드카드로 인덱스 미사용 (데이터 증가 시 악화) | `courses.service.ts` `title.contains` | 중장기 |
| 4 | `ORDER BY student_count DESC` 정렬 커버 복합 인덱스 부재 | schema.prisma | 중장기 |

이번 작업은 **원인 1·2**를 처리한다(효과/비용 대비 최우선). 3·4는 데이터 증가 시 DB
인덱스(`pg_trgm` GIN, 복합 인덱스)로 후속 대응 — `manual-sql/`로 작성하고 공유 DB이므로
tutoring 팀 정렬 필요(§15).

## 3. 변경 내용

### ① 검색어 debounce (프론트)

`apps/web/src/app/(tabs)/learn/explore/page.tsx`

- `debouncedSearch` state 신설. `searchQuery` 입력을 **300ms 디바운스**한 값만 조회에 사용.
- 조회 effect 의존성을 `[selectedL1, selectedL2, searchQuery]` → `[selectedL1, selectedL2, debouncedSearch]`로 변경.
- 칩(L1/L2) 선택은 즉시 반영 유지, 텍스트 입력만 디바운스.
- 결과 파생 UI(`showRecommended`, `sectionTitle`, 빈 상태 메시지)도 `debouncedSearch` 기준으로 정렬해 표시-데이터 불일치(플리커) 방지.
- 효과: "패턴영어" 입력 시 6회 발사되던 요청이 1회로 감소 → 요청/DB 부하 약 1/5~1/6.

### ② 파트너 L1 카테고리 캐시 (백엔드)

`apps/api/src/courses/courses.service.ts`

- 파트너별 L1 카테고리 id 집합을 **in-memory TTL 캐시(60초)** 로 보관하는 `getPartnerL1Ids(partnerId)` private 메서드 신설. `getCourses`가 매 요청 실행하던 `$queryRawUnsafe` 왕복을 캐시 히트 시 제거.
- 카테고리는 거의 변하지 않으므로 60초 TTL로 안전(최대 60초 지연 반영). 타 파트너 누출 차단 로직(`l1_category_id IN partnerL1Ids`)은 그대로 유지.
- 효과: 반복 조회 시 요청당 DB 왕복 3 → 2.
