## 1. 배경 및 목적

> **주 목적**: 사용자가 **가장 최근 진행했던 과정과 레슨에 빠르게 접근**하도록, 최근 과정·레슨을
> 우선 노출하는 것이 learn 페이지의 핵심이다. (§9 최근 포커스 참조)

현재 `learn/page.tsx`는 하드코딩된 Mock 데이터(`CHAPTERS`, `COURSES`)로 동작하며 실 API 연동이 없다.

tutoring의 `my-classes` 페이지에서 검증된 로직을 이식하여:
- `access_codes` 기반 수강 계약 조회
- `status_code = 'active'` 기준 수강 중 과정 식별
- `usage_end_date` 기반 수강중/수강종료 구분
- `lesson_results` 기반 `completedLessons` 실계산

을 speaking learn 페이지에 적용한다.

### 1.1 수강 소스 두 갈래 (중요)

수강 권한은 사용자 유형에 따라 **출처가 다르다**:

| 구분 | 수강 권한 출처 | 수강 범위 | 본 문서 구현 상태 |
|------|---------------|----------|------------------|
| **픽클래스 기본 B2B** | `access_codes` (코드당 단일 과정) | 코드에 연결된 1과정 | ✅ 구현 완료 (§3~7) |
| **파트너 (파고다 등)** | **외부 수강내역 API** (access_codes 아님) | 파트너가 부여한 범위 | ⏳ **차후 개발 (§10)** |

본 문서의 §3~7(Phase 1~3)은 **기본 B2B(access_codes) 경로만** 구현한 상태다. 파트너 외부 API
경로는 **아직 구현되지 않았으며** §9(분기 골격)·§10(차후 개발)에서 분리해 설계한다.

### tutoring과의 차이점

| 항목 | tutoring | speaking |
|------|----------|---------|
| `course_type` 필터 | `tutoring`, `integrated` | `speaking`, `integrated` |
| UI 구조 | 웹 카드 그리드 (데스크탑) | 모바일 탭, 단일 과정 포커스 뷰 |
| 나머지 로직 | — | 동일 이식 |

## 3. Phase 1 — 백엔드

**파일**: `apps/api/src/lessons/lessons.service.ts`, `lessons.controller.ts`

### 3-1. `getEnrolledCourses()` 추가

tutoring `lessons.service.ts`의 동일 메서드를 복사 후 `course_type` 필터만 변경한다.

```sql
-- INTERNAL 수강 과정 (speaking 전용 필터)
SELECT DISTINCT
  c.id            AS course_id,
  c.title         AS course_title,
  c.level_code,
  c.total_lessons,
  ac.usage_start_date,
  ac.usage_end_date,
  c.course_type,
  c.genre_code
FROM access_codes ac
JOIN courses c ON ac.course_id = c.id
WHERE ac.status_code = 'active'
  AND ac.course_id IS NOT NULL
  AND ac.user_id = '${studentId}'
  AND (c.course_type IN ('speaking', 'integrated') OR c.course_type IS NULL)
  AND c.deleted_at IS NULL

UNION

SELECT
  c.id            AS course_id,
  c.title         AS course_title,
  c.level_code,
  c.total_lessons,
  NULL            AS usage_start_date,
  NULL            AS usage_end_date,
  c.course_type,
  c.genre_code
FROM courses c
WHERE c.created_by = '${studentId}'
  AND c.genre_code = 'custom'
  AND (c.course_type IN ('speaking', 'integrated') OR c.course_type IS NULL)
  AND c.deleted_at IS NULL

ORDER BY course_title
```

이후 각 과정별로:
- `course_lessons` 조회 (`lesson_order ASC`)
- `ai_modules` 코드 → `{name, skill}` 맵
- `lesson_results`에서 `completed_at IS NOT NULL` 레코드로 `completedSet` 구성
- `nextLesson`: 미완료 중 `text_id IS NOT NULL` 우선 → 첫 미완료 → 마지막 레슨

반환 타입:
```ts
{
  id: string;
  title: string;
  level: string;
  totalLessons: number;
  completedLessons: number;
  isCustom: boolean;
  courseType: string | null;
  usageStartDate: string | null;   // 'YYYY-MM-DD'
  usageEndDate: string | null;     // 'YYYY-MM-DD'
  nextLessonId: string | null;
  nextLessonTitle: string;
  nextLessonRound: number;
  lessons: {
    id: string;
    order: number;
    topic: string;
    textTitle: string | null;
    hasText: boolean;
    modules: { moduleCode: string; name: string; skill: string }[];
    isCompleted: boolean;
  }[];
}
```

## 9. 수강 소스 분기 설계 (EnrollmentProvider)

> 본 절은 기본 B2B(현행)와 파트너(차후)를 **하나의 골격**으로 묶기 위한 설계다.
> §9.1(분기 추상화)·§9.2(최근 포커스)는 **파트너 스펙과 무관하게 지금 구현 가능**하다.

### 9.1 분기 추상화

컨트롤러·웹 인터페이스는 그대로 두고, `getEnrolledCourses(userId)` 내부에서 **소스만 분기**해
동일한 `EnrolledCourse[]`를 반환한다.

```
getEnrolledCourses(userId, partnerId)
 ├─ partnerId != null  (파트너 관리 사용자)
 │     → PartnerEnrollmentProvider    ← 외부 API 직접 호출 (§10, 차후)
 └─ partnerId == null  (픽클래스 기본 B2B)
       → AccessCodeEnrollmentProvider  ← 현행 access_codes 쿼리 (§3-1 그대로 이동)
```

- **파트너 판정**: 별도 재계산 없이 **로그인 시 JWT 에 캐싱된 `req.user.partnerId`** 를 그대로 쓴다.
  (파트너 리졸브 CTE 는 로그인 1회로 이관됨 — 상세:
  [로그인 JWT partnerId 캐싱 설계](../../architecture/2026-06-22_로그인-JWT-partnerId-institutionId-캐싱.md).
  기관 계층 다단계 배경은 카테고리 개발계획 §10.1 오류 기록 참조)
- 컨트롤러에서 `req.user.partnerId` 를 서비스에 주입 → `getEnrolledCourses(userId, partnerId)` 가
  partnerId 유무로 Provider 를 고른다. 요청당 파트너 판정 쿼리는 없다.
- `AccessCodeEnrollmentProvider`는 현재 `getEnrolledCourses()` 본문을 거의 그대로 옮긴 것 →
  **기본 B2B 동작은 무변경**.

### 9.2 최근 과정/레슨 포커스 (주 목적 — 두 소스 공통)

현재 정렬은 `ORDER BY course_title`이라 "최근"이 아니다. 다음을 적용한다:

- 과정 정렬: **`MAX(lesson_results.completed_at) DESC`** (최근 학습 활동순)
- learn 진입 시 **가장 최근 과정을 자동 선택**(`selectedCourseId` 초기값)
- access_code / 파트너 양쪽 Provider 결과에 공통 적용

> 이것이 "최근 진행했던 과정·레슨에 빠르게 접근"이라는 §1 주 목적의 핵심 구현이다.

## 10. 차후 개발 — 파트너 외부 수강내역 API (미구현)

> ⚠️ **본 절은 아직 구현되지 않았다.** speaking이 파트너 API를 **직접 호출**하는 방향으로 결정됐으나,
> **외부 API 스펙과 파트너 진입 인증이 확정되지 않았다.** 따라서 구체 구현이 아니라 **seam(인터페이스)
> 설계와 선결 과제**만 정의한다. backoffice의 파트너 연동 코드/형태는 **확정 사항이 아니므로 참조하지
> 않는다.**

### 10.1 결정 사항

- **호출 주체**: speaking이 외부 파트너 API를 **직접 호출**한다 (backoffice 경유 아님).
- **식별자 확보**: 파트너 사용자 식별자도 **speaking에서 직접** 처리한다.

### 10.2 격리 seam (스펙 확정 시 구현부만 채움)

파트너 응답 매핑은 스펙 확정 전까지 **인터페이스만** 고정한다. 이렇게 하면 스펙이 나오기 전에도
§9.1 분기·learn UI·테스트를 **목업 Provider**로 완성할 수 있다.

```ts
// 파트너 API 스펙 확정 시 구현부 작성. 아래 형태는 '가정'이며 확정 시 교체한다.
interface PartnerEnrollmentPort {
  getEnrollments(ctx: PartnerContext): Promise<PartnerEnrollmentResult>;
}

interface PartnerEnrollmentResult {
  scope: 'ALL' | 'SPECIFIC';   // 가정 — 스펙 확정 시 교체
  courseIds: string[];         // SPECIFIC일 때 picklass course id 목록
  // 만료·수료조건 등은 스펙 확정 후 추가
}
```

### 10.3 learn vs explore 역할 분리 (파트너 'ALL' scope)

- **learn("내 수업")** = 실제 학습을 시작한 과정(`lesson_results` 활동 有) ∩ 수강 허용 범위, 최근순.
- **explore("과정 탐색")** = 전체 카테고리 탐색 (이미 구현).
- `SPECIFIC` scope면 시작 전이라도 해당 course를 learn에 미리 노출.

### 10.4 성능/장애 격리

외부 API는 learn 랜딩에서 **블로킹 금지**:

- user 단위 **단기 캐시(5~10분)** + 캐시 히트 시 즉시 렌더, 백그라운드 갱신.
- 외부 API 실패 시 **마지막값/빈 목록 폴백**, 학습 흐름 차단 없음.

### 10.5 선결 과제 (파트너 Provider 착수 전 필수)

- [x] **대상 파트너 식별(partnerId)** — ✅ 로그인 시 JWT 에 캐싱 완료(`req.user.partnerId`).
      어느 파트너인지는 이제 컨텍스트에서 바로 안다.
- [ ] **파트너 API 스펙 확정** — 엔드포인트·인증(키/서명)·요청·응답 형태 (speaking 기준으로 정의)
- [ ] **파트너 사용자 식별자(user_pk_id) 확보** — 외부 enrollment API 호출엔 *파트너 측 사용자 식별자*가
      필요한데, 이는 partnerId(기관)와 다른 값으로 **아직 speaking 에 없다**. 파트너 로그인/진입 인증
      설계에서 확보 경로를 정해야 함.
- [ ] 캐싱/만료 정책 확정
