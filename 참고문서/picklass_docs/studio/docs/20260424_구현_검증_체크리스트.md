# 구현 검증 체크리스트 — 같은 실수 반복 방지

**작성일**: 2026-04-24
**계기**: stage diversity 구현 시 단위 테스트 통과로 "완료" 보고했지만, 기존 `_topological_sort`가 stage 순서를 깨뜨리는 버그를 발견 못함. 사용자가 실제 사용 시 결과가 의도와 다름.
**목적**: 검증 없이 "완료" 보고하는 실수를 구조적으로 방지

---

## 1. 사례 분석 (이번에 발생한 실수)

### 1-1. 무엇을 했는가
- analyzer에 `ensure_stage_diversity` 함수 추가
- 단위 테스트 7건 작성, 모두 통과
- `pnpm build`/`tsc typecheck` 통과
- analyzer 서버 재시작 후 `/lesson-plan` 호출 1회만 확인
- "구현 완료" 보고

### 1-2. 무엇을 놓쳤는가
- `ensure_stage_diversity` 다음에 호출되는 `sort_sequence`의 내부 동작 (`_topological_sort`)을 트레이스하지 않음
- 보충된 모듈(FRT)이 prerequisites가 없는 상태에서 토폴로지 정렬을 거치면 어디에 배치되는지 검증하지 않음
- 단위 테스트는 `ensure_stage_diversity` 함수 자체만 검증, **다음 단계와의 결합** 미검증
- 실제 e2e 호출 결과의 sequence 순서를 사용자 요구사항(stage → cl 우선순위)과 라인별로 비교하지 않음
- 결과: `[1] PRD intro → [2] FRT closure → [3] SCN intro → [4] QAR body` (closure가 intro 사이에 끼어듦)

### 1-3. 근본 원인
| 원인 | 설명 |
|------|------|
| **단위 테스트 = 완료 착각** | 함수 단위 테스트만 통과해도 파이프라인 결합 시 새 버그가 생길 수 있음 |
| **다음 단계 코드 미열람** | 추가한 코드가 그 다음 단계로 흘러가는데, 다음 단계 코드를 안 읽음 |
| **e2e 검증 1회 + 표면적** | 1개 시나리오만 호출하고 "잘 나오는 듯" 정도로 끝냄 |
| **결과 line-by-line 미검증** | 응답 JSON을 받아도 사용자 요구사항(stage 순서)과 직접 비교하지 않음 |
| **"build/test pass = done" 등치** | TypeScript/pytest 통과 = 동작 검증 ❌ |

## 2. 향후 워크플로우 (단계별)

### Phase 0: 구현 전
- [ ] **변경하려는 코드의 이전/다음 단계** 모두 읽기
- [ ] **기존 코드의 부작용** 확인 (예: 토폴로지 정렬, 캐시, 미들웨어, 인터셉터)
- [ ] **데이터 형태**가 단계마다 어떻게 바뀌는지 그려두기
- [ ] **초기값/사전 채움 로직** 확인 (`Array(n).fill(...)`, `setX(default)` 등이 후속 로직에 영향 주는지)
- [ ] **참조 페이지의 초기 상태**도 그대로 복제 — UI만 같게 하고 빈 상태/로딩/추천 등을 다르게 두면 안 됨
- [ ] 단순 수정도 영향 범위가 클 수 있음을 가정

### Phase 1: 구현 중
- [ ] 함수 추가 시: 그 함수의 입출력이 **호출자(다음 단계)에서 어떻게 쓰이는지** 트레이스
- [ ] 새 필드 추가 시: 그 필드를 **소비하는 모든 위치** 검색
- [ ] 정렬/필터 로직 변경 시: **기존 정렬/필터** 동작과 충돌 안 하는지 검토

### Phase 2: 단위 테스트
- [ ] 새 함수의 happy path
- [ ] 새 함수의 edge case (빈 입력, null, 경계값)
- [ ] **이전 단계의 출력 → 새 함수 → 다음 단계 입력**으로 흐르는 통합 시나리오

### Phase 3: 통합 검증 (가장 자주 빠지는 부분)
- [ ] **실제 데이터로 e2e 호출** (운영 DB, 진짜 입력값)
- [ ] **여러 시나리오** 호출 (정상, 부족, 과다, 엣지)
- [ ] 응답을 **사용자 요구사항과 라인별로 직접 비교**:
  - "stage 우선순위 유지" → 결과 시퀀스의 stage 순서 확인
  - "각 stage 최소 1개" → stage_counts에 0 없는지 확인
  - "보충 모듈은 fallback 표시" → is_fallback_module=true 확인
- [ ] 예상과 다르면 **즉시 보고하지 말고 추가 검증**
- [ ] **Next.js / 프론트엔드 변경 시 추가 체크**:
  - [ ] dev 서버가 실행 중인지 확인. 실행 중이면 production `pnpm build` 후 dev에서 webpack chunk 충돌 가능
  - [ ] 프론트엔드 수정 후에는 가능하면 **dev 서버에서 직접 확인** (production build만 검증 X)
  - [ ] dev 서버 콘솔/네트워크에 런타임 에러(예: `Cannot find module './XXXX.js'`) 있는지 확인
  - [ ] 빌드 모드 충돌 의심 시 `.next/` 정리 후 재시작

### Phase 4: 보고
- [ ] 보고 형식: "테스트 X건 통과 + e2e 시나리오 Y개 직접 확인 결과 일치"
- [ ] **테스트 통과 = 완료**라고 적지 말 것
- [ ] 의심 가는 부분이 있으면 보고에 명시 ("X는 확인했지만 Y는 미확인" 등)
- [ ] 사용자가 "왜 이게 안 되냐?"고 물으면 본인 검증을 의심하라

## 3. 절대 하지 말 것 (Anti-patterns)

| ❌ Anti-pattern | ✅ 대안 |
|----------------|---------|
| "테스트 통과했으니 완료" | 실제 환경에서 e2e로 결과 직접 확인 |
| "build 됐으니 동작할 것" | build = 컴파일 OK, 동작 OK는 별개 |
| 1개 시나리오만 호출하고 OK | 정상/부족/과다/엣지 최소 3-4개 시나리오 |
| 응답을 받고 "잘 나옴" | 응답을 사용자 요구사항과 라인별 비교 |
| 의심스러워도 "일단 보고" | 의심 100% 해소 후 보고 |
| 함수만 단위 테스트 | 파이프라인 결합 통합 테스트 추가 |
| **production 빌드만 검증하고 완료** | **dev 서버 환경에서도 동작 확인 (or 빌드 후 dev 캐시 충돌 가능)** |
| **`.next/` 같은 빌드 캐시 무시** | **빌드 모드(prod/dev) 전환 시 캐시 정리 필요성 인지** |
| **참조 페이지(예: lesson-setup)의 초기 상태 미확인** | **참조 패턴은 단순 UI뿐 아니라 "초기값/빈 상태"까지 동일해야 함. 미리 채워두면 의도가 깨짐** |
| **사전 채워진 데이터 = OK 등치** | **`Array(n).fill(recommended)` 같은 사전 채움이 후속 로직(번호 부여, 자동 갱신)에 영향을 주는지 확인** |
| **사용자 요구사항을 추측으로 해석** | "**lesson-setup과 마찬가지 로직**" = UI + 데이터 흐름 + 초기 상태까지 모두 동일. 추측하지 말고 참조 페이지 동작 그대로 복제 |
| **`const next = [...prev]; setX(next)` 패턴 (비함수형 setState)** | **인덱스 갱신은 항상 `setX(prev => ...)` functional updater 사용**. 같은 사이클에 여러 회차/인스턴스가 동시에 호출하면 stale closure로 마지막 호출만 반영됨 |
| **"마지막만 반영" 증상 묵살** | **stale closure / setState race 의심 → functional updater로 교체** |

## 4. 자기 검증 질문 (보고 직전 체크)

이 6가지 질문에 모두 "예"여야 보고:

1. **이 변경이 그 다음 단계에 어떻게 흘러가는지 코드를 읽고 트레이스했는가?**
2. **실제 데이터로 e2e 호출을 최소 3개 시나리오로 했는가?**
3. **응답을 사용자 요구사항과 라인별로 비교했는가?**
4. **단위 테스트뿐 아니라 통합/시나리오 테스트도 작성했는가?**
5. **"build/test 통과"가 아닌 "동작 확인"으로 보고할 수 있는가?**
6. **(프론트엔드) 사용자가 실제 사용하는 환경(dev 서버)에서 페이지가 정상 로드되는가? `.next/` 캐시 충돌이 없는가?**

## 5. 사례별 보고 템플릿

### 좋은 보고
```
✅ 구현 완료
- 단위 테스트: 7건 추가, 모두 통과
- 통합 테스트: ensure_stage_diversity → sort_sequence 결합 시나리오 3건 추가, 통과
- e2e 검증:
  - Scenario 1 (어휘 KPI): 결과=[WSD,WRD,IMG,FRT] / 기대 stage순=intro,intro,body,closure ✓
  - Scenario 2 (단일 KPI): 결과=[WRD,SNR,FRT] / 기대 stage순=intro,body,closure ✓
  - Scenario 3 (prereq 있는 모듈): 결과=[PRD,SCN,QAR,FRT] / 기대 stage순=intro,intro,body,closure ✓
- 모든 시나리오 사용자 요구사항(stage 우선순위 유지)과 일치 확인
```

### 나쁜 보고 (이번에 한 것)
```
❌ 구현 완료
- 테스트 7건 추가, 모두 통과
- build 통과
- analyzer /lesson-plan 호출 결과 stage diversity 작동 확인
```
→ "stage diversity 작동 확인"이 막연함. **stage 순서**가 깨질 수 있음을 검증 안 함.

## 7. 핵심 한 줄

> **"단위 테스트 통과 + build 성공"은 "구현 완료"가 아니다. 실제 환경에서 e2e 호출 후 결과를 사용자 요구사항과 라인별로 비교했을 때만 "완료"라고 부른다.**
