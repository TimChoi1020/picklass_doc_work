### 적용 경로 (운영 메모)
- 1회차 적용 시: `pnpm exec prisma db execute --file ...`이 [apps/api/prisma/prisma.config.ts](../apps/api/prisma/prisma.config.ts)의 잘못된 위치/spread 패턴 datasource를 인식하지 못해, `pg` 클라이언트로 직접 BEGIN → SQL → `_prisma_migrations` 등록 → COMMIT 트랜잭션으로 적용. 일회용 스크립트는 적용 직후 삭제.
- **2026-04-23 후속 정비**: `prisma.config.ts`를 `apps/api/prisma/`에서 `apps/api/`로 이동하고 spread를 제거하여 `prisma migrate status`/`db execute`가 정상 동작하도록 보강 완료. 차후 마이그레이션은 표준 `pnpm prisma migrate deploy`로 처리 가능.

## 2. [P0] lesson 페이지 URL 파라미터 수신 처리 — **완료 (2026-04-23)**

**파일**: `apps/web/src/app/class/lesson/[passageId]/page.tsx`

**구현 내역**
- `?kpis=…&duration=…&modules=…` 3개 필수값 파싱
- 발신 측 1차 방어: `lesson-setup/[passageId]/page.tsx` `handleStartLesson`에서 빈 값 차단
- 수신 측 2차 방어: `lesson` 페이지 `useEffect`에서 각 누락 케이스별 전용 알럿 + `lesson-setup` 복귀
- 검증 기준: `modules.length ≥ 1`, `kpis.length ≥ 1`, `duration ∈ {15, 20, 25, 30}`

**작업 내용**
```typescript
const searchParams = useSearchParams();
const modules = searchParams.get('modules')?.split(',') ?? [];
const kpis = searchParams.get('kpis')?.split(',') ?? [];
const duration = Number(searchParams.get('duration')) || null;
```

**후속 연결**
- `kpis`, `duration`, `modules`, `passageId`를 시퀀싱 API 요청 페이로드로 사용
- **필수값 정책 (2026-04-23 확정)**: `kpis`와 `duration` 모두 필수. 미선택 시 폴백 없이 사용자에게 알럿을 띄우고 시퀀싱 호출을 중단한다.
  - `kpis.length === 0` → "KPI를 1개 이상 선택하세요" 알럿 후 lesson-setup으로 복귀
  - `duration === null` → "수업 시간을 선택하세요" 알럿 후 lesson-setup으로 복귀
  - 기본값(30분, 전체 KPI) 자동 설정하지 않음 — 교사의 명시적 선택을 강제

## 3. [P0] `generateAndSavePassage` 저장 경로 불일치 (버그) — **부분 완료 (2026-04-23)**

### 동일 인스턴스 확인됨
`apps/api/.env`의 `DATABASE_URL`이 `aws-0-ap-northeast-2.pooler.supabase.com:5432`(Supabase pooler)를 가리킴 → **Prisma와 Supabase가 같은 PostgreSQL 인스턴스의 같은 `texts` 테이블을 공유**. 데이터 마이그레이션 불필요, 코드 통일만으로 해결.

### 이번 세션 적용
- **NestJS** `apps/api/src/passages/passages.controller.ts` `apps/api/src/passages/passages.service.ts`에 `GET /passages/:textId` (`findOne`) 추가 — content/topic/text_type/origin_id/created_at/updated_at까지 반환
- **shared types** `packages/shared/src/types/course.ts`에 `TextDetail` 인터페이스 추가
- **studio-web** `apps/web/src/lib/api.ts` `passagesApi.get(id)` 추가
- **`useText` 훅 (`apps/web/src/hooks/useTexts.ts`)**: `/api/texts/:id`(Supabase) → `passagesApi.get`(NestJS Prisma)로 이전. `TextDetail` → `TextData` 매핑 포함
- 사용처: lesson 페이지, lesson-setup 페이지 — 양쪽 typecheck 통과

### 후속 PR로 분리한 이유
다음은 user_profiles join, content 필드 의존, id 타입(string ↔ number) 영향이 광범위하여 별도 PR에서 신중히 진행:
- `useTexts` (목록): `class/page.tsx`에서 `text.user_profiles.display_name`/`email` 사용 + `text.content` wordCount 계산. NestJS `findAll` select 확장 + user_profiles 별도 join 필요
- `useTwinTexts`: NestJS `/passages/:originId/twins` 엔드포인트 미구현
- `useCreateText`: 이미 `passagesApi.create` 존재하나 hook은 여전히 `/api/texts` 사용 — 이전 시 호출자 3곳(class/page, CreatePassageModal, text-creation-modal) 검증 필요
- `useUpdateText`/`useDeleteText`/`useDeleteTexts`: **호출자 0건 (dead hook)** — 이전 대신 #8에서 제거 권장

### 잔존 위치
- `apps/web/src/app/api/texts/**/route.ts`: 위 후속 hook이 의존하는 동안 유지. 모든 hook이 NestJS로 이전된 후 제거.

### 원래 증상
과정 생성 시 지문을 NestJS `/passages` (Prisma)로 저장하지만, `/class` 페이지의 `useTexts`는 Next.js `/api/texts` (Supabase admin client)를 읽음 → 과거에는 별개 DB 우려가 있었으나, 이번 세션에서 **두 경로가 동일 인스턴스의 동일 테이블을 가리키는 것으로 확인** → 데이터 분리 없음, 코드만 정리하면 됨.

## 6. [P1] 자동 시퀀싱 API (`/lesson-plan`) 구현 — **API/호출 경로 완료 (2026-04-23)**

**완료 내역**
- **analyzer** ([picklass-analyzer]): v3.2.0 시퀀싱 엔진 + `/lesson-plan` FastAPI 엔드포인트. `duration_min: Literal[15,20,25,30]` / `selected_kpi_codes: min_length=1` 필수값 강제, Pydantic 422 응답. 테스트 34건 통과.
- **studio-api**: `apps/api/src/lesson-plan/` 신규 모듈 (Controller + Service + DTO). `@ArrayMinSize(1)`, `@IsIn([15,20,25,30])` 2중 방어. `passage_id` → Prisma `texts` 조회 → `passage_level`/`content` 확보 후 analyzer 호출. `module_codes` 화이트리스트 필터 지원. `ANALYZER_BASE_URL` env 추가.
- **studio-web**: `lessonPlanApi` + `useGenerateLessonPlan` 훅. lesson 페이지에서 필수값 통과 시 1회 호출 + 결과/에러 콘솔 노출.

**남은 작업 (UI 통합)**
- lesson 페이지 progress bar를 analyzer 시퀀스로 교체 → **모듈 코드 컨벤션 통일 선행 필요** (analyzer는 `ai_modules.code`, 현재 lesson 페이지는 UI ID `prediction`/`skimming`…)
- summary/meta 표시, 경고 배너 노출

**초기 상태 (참고)**: lesson-setup의 KPI + duration 입력 파이프라인이 갖춰져 [lesson-plan-update.md](./lesson-plan-update.md) 구현 준비 완료

**입력** (lesson 페이지에서 전달 예정, 전부 필수)
- `passageId` (string, required)
- `modules: string[]` (교사 선택 모듈 코드, required, length ≥ 1)
- `kpis: string[]` (선택된 KPI 코드, **required**, length ≥ 1) — 프론트에서 미선택 차단, 백엔드에서도 400 응답으로 방어
- `duration: 15 | 20 | 25 | 30` (**required**) — null/undefined 허용하지 않음, 백엔드에서 enum 검증

**출력 (예상)**
- 회차 내 활동(activity) 순서 배열 + 각 활동의 예상 소요시간
- 선택 KPI/duration 조건에서 가용 모듈 필터링 결과
- 미달/초과 시 경고 메타데이터

**분담**
- 알고리즘: `picklass-analyzer` (현재 작업 중인 시퀀싱 로직)
- API 노출: `studio.picklass.com3/apps/api/src/lesson-plan/` (신규 모듈)

**선행 의존성**
- 작업 #1 (마이그레이션 실행) — `KPI_CATEGORY` 단일 소스 전제
- 작업 #2 (URL 파라미터 수신) — 호출 진입점

## 14. [P0] `auth.users(id)` FK 제약 제거 — **완료 (2026-04-23)**

### 배경 (인증 시스템 분리 미완)
2025-07-10 initial_schema 에서 `user_profiles` / `texts` / `async_tasks` / `notifications` 의 `user_id` 가 **Supabase `auth.users(id)`** 를 FK 로 참조하도록 만들어졌습니다. 이후 인증 시스템이 NestJS 자체 인증(`public.users`)으로 이전되었지만 FK 는 그대로 남아 있어, 신규 NestJS 사용자가 위 테이블에 INSERT 시 **`23503` FK 위반 + 500 에러** 발생.

대표 증상: dev 환경에서 `/api/strategic-reading` POST 시
```
code: 23503
details: Key (user_id)=(e959ffe1-18bf-471b-9589-0deba183e282) is not present in table "users".
message: insert or update on table "async_tasks" violates foreign key constraint "async_tasks_user_id_fkey"
```

### 진단 결과 (2026-04-23 운영 DB 실측)
| 항목 | 값 |
|---|---|
| `public.users` ∩ `auth.users` (UUID 동일) | **0건** |
| 두 시스템 사용자가 이메일로 매핑 | **4명** (예: `sniper4457@naver.com` auth=`80bd54a1-...`, public=`e959ffe1-...`) |
| `public.users` 22명 중 이메일 보유 | 8명 |
| `auth.users` 25명 중 이메일 보유 | 25명 |
| `texts` 보유하면서 매핑 불가 auth 사용자 | **11명** |
| `texts` 122건 중 auth-only | 84건 |
| `async_tasks` 117건 중 auth-only | 117건 (전부) |

### 단순 ALTER 불가 이유
FK 만 `public.users(id)` 로 ALTER 시 `texts` 84건 + `async_tasks` 117건 = **200+ 건이 orphan 으로 CASCADE 삭제 위험**.

### 결정: 옵션 D — FK 제약 제거 + 정합성은 application 레이어에서 보장
2026-04-23 사용자 confirm(옵션 D) 후 `apps/api/prisma/migrations/20260423000001_drop_auth_users_fk/migration.sql` 적용:

```sql
ALTER TABLE "user_profiles" DROP CONSTRAINT IF EXISTS "user_profiles_id_fkey";
ALTER TABLE "texts"         DROP CONSTRAINT IF EXISTS "texts_user_id_fkey";
ALTER TABLE "async_tasks"   DROP CONSTRAINT IF EXISTS "async_tasks_user_id_fkey";
ALTER TABLE "notifications" DROP CONSTRAINT IF EXISTS "notifications_user_id_fkey";
```

### 적용 결과
- 운영 DB 실 FK 2건 DROP: `async_tasks_user_id_fkey`, `notifications_user_id_fkey`
- `user_profiles_id_fkey` / `texts_user_id_fkey` 는 **이미 운영 DB 에 부재** (initial_schema.sql 과 운영 실제 schema 가 어긋나 있던 상태 — 어떤 시점에 누군가 수동 제거한 듯). `IF EXISTS` 가드로 무탈 통과.
- `_prisma_migrations` 테이블에 정상 등록
- INSERT 검증: `e959ffe1-...` 사용자로 `async_tasks` INSERT 가능 확인 (트랜잭션 + ROLLBACK 으로 실데이터 미저장)

### 14-후속 (작업 #15) — 사용자 데이터 통합 + 새 FK 재추가
FK 제거는 **응급조치**입니다. 정합성은 application(NestJS AuthGuard) 에서 보장하지만 raw SQL 또는 외부 도구로 잘못된 user_id 가 들어갈 위험이 남아 있음. 후속 PR 에서:

1. `auth.users` ↔ `public.users` 사용자 매핑 (이메일 기반, 매핑 불가 11명은 신규 row 생성 또는 데이터 archive)
2. 모든 `user_id` / `user_profiles.id` 를 `public.users.id` 로 일괄 변환 (`UPDATE ... SET user_id = mapping.public_id`)
3. 새 FK 를 `public.users(id) ON DELETE CASCADE` 로 재추가
4. (옵션) `auth.users` 자체를 단계적 폐기 + middleware.ts 의 `// TODO: [AUTH] Supabase middleware 복원` 주석 정리

이 작업은 데이터 마이그레이션 동반이라 별도 PR + 운영 점검 시간 확보 후 진행 권장.
