# 1. 과정 생성 시 지문 생성 재시도 + 전체 롤백

## 1-1. 배경 / 문제

과정 생성 마법사의 "완료" 단계에서 AI 회차별 지문을 순차 생성하는데, 일부 회차 지문 생성이 실패해도:

1. **오류가 사용자에게 노출되지 않음** — `console.warn`만 남기고 `text_id=null`로 진행
2. **재시도 없음** — 한 번 실패하면 바로 포기
3. **일부 지문만 DB에 저장되고 과정도 일부 지문 없이 생성됨** — 데이터 불일치

실제 DB 확인 결과: "수능 초급 마스터" 과정은 3개 AI 회차 중 1개만 지문이 있고, 2개는 `text_id=NULL`.

## 1-2. 정책

- **재시도**: 각 지문 생성당 최대 **3회 시도** (초기 1회 + 재시도 2회)
- **All-or-nothing**: 재시도 후에도 **하나라도 실패하면 전체 롤백** — 이미 저장된 지문 삭제 + 과정 미생성
- **사용자 알림**: 실패 시 **토스트 메시지**로 명확히 알림

# 2. 레슨 삭제 시 지문 동기화 (Class 리스트 잔존 문제)

## 2-1. 증상

과정 상세 페이지(`/course/[courseId]`)에서 **레슨을 삭제**한 후, Class 페이지(`/class` = My Library)에 해당 지문이 **여전히 노출**됨.

## 2-2. 테이블 구조 복기

```
courses (1) ─── course_lessons (N) ─── texts (1, optional)
                      │                     │
                 text_id (FK, nullable)   id (PK)
```

- `course_lessons`: 과정의 회차 (lesson_order, topic, skill_modules, text_id)
- `texts`: 실제 지문 본문 (title, content, level, category 등)
- **`course_lessons.text_id`는 nullable** — 회차와 지문은 느슨한 연결

## 2-3. 원인

`LessonsService.remove()`가 `course_lessons` row만 삭제하고 연결된 `texts` row는 그대로 둠.

결과:
- 과정 상세에서는 레슨이 사라짐 (✓ 정상)
- Class 페이지(My Library)는 `texts` 테이블을 그대로 조회하므로 지문이 계속 보임 (✗ 기대와 다름)

## 2-4. 확정 정책

**옵션 A 채택** — 레슨 삭제 시 연관된 지문도 함께 삭제.

**공유 지문 처리**: 다른 `course_lessons`에서 동일 `text_id`를 참조 중이면 **text 삭제 스킵** (참조 카운트 확인).

## 2-5. 구현 상세

### LessonsService.remove() 수정

```typescript
async remove(courseId: string, lessonId: string, userId: string) {
  const lesson = await this.findOne(courseId, lessonId);
  const textId = lesson.text_id;

  await this.prisma.$transaction(async (tx) => {
    await tx.course_lessons.delete({ where: { id: lessonId } });

    if (textId !== null && textId !== undefined) {
      // 다른 course_lessons에서 이 text_id를 쓰는지 확인
      const otherRefs = await tx.course_lessons.count({ where: { text_id: textId } });
      if (otherRefs === 0) {
        // 본인 소유 text만 삭제
        const text = await tx.texts.findFirst({
          where: { id: textId, user_id: userId },
          select: { id: true },
        });
        if (text) {
          await tx.texts.delete({ where: { id: textId } });
        }
      }
    }
  });

  await this.syncCourseTotalLessons(courseId);
  return { success: true };
}
```

### Controller 업데이트

`lessons.controller.ts` DELETE 핸들러에서 `CurrentUser` 주입 후 `remove(courseId, lessonId, user.id)` 호출.

### 프론트엔드 캐시 무효화

`useDeleteLesson` 의 `onSuccess`에서 `queryKeys.texts.all` 도 invalidate → Class 페이지 즉시 갱신.

# 4. SubscriptionGuard 로직 설명

## 4-1. 역할

특정 경로(`/class/lesson/*`, `/class/lesson-setup/*`) 진입 시 **사용자의 구독/무료체험 만료 여부를 체크**하여, 만료된 경우 페이지 접근을 차단하는 React 컴포넌트.

## 4-2. 구성 요소

### 입력 데이터

```typescript
const { profile, isLoading } = useUserProfile();
```

- `useUserProfile()` 훅이 `GET /api/user-profile` 호출
- `user_profiles` 테이블에서 현재 사용자의 프로필 조회
- 핵심 필드: `subscription_expires_at` (만료일 timestamp)

### 상태 관리

```typescript
const [isRedirecting, setIsRedirecting] = useState(false);
```

- 만료 감지 → 리다이렉트 진행 중 상태
- 리다이렉트 중에는 자식 컴포넌트 대신 스피너 표시

### 렌더 분기

| 조건 | 반환 |
|------|------|
| `isLoading === true` (프로필 로딩 중) | 스피너 |
| `isRedirecting === true` (만료 감지됨) | 스피너 |
| 만료됨 (두 번째 체크) | `null` (flicker 방지) |
| 그 외 (정상) | `{children}` |

## 4-3. 만료 체크 로직 (원래 동작)

### 흐름

```
1. useUserProfile로 profile 가져옴
2. useEffect 실행 (profile, isLoading 변경 시)
3. 조건 확인: !isLoading && profile 있음
4. expiresAt = profile.subscription_expires_at (없으면 null)
5. if (expiresAt && expiresAt < now):
     a. setIsRedirecting(true)  → 스피너 표시
     b. alert("무료 체험 기간이 종료되었습니다...")  → 대화상자
     c. router.push('/class')  → /class 페이지로 강제 이동
```

### 동시에 render 시점에도 한번 더 체크 ("Double check")

```typescript
if (expiresAt && expiresAt < now) return null;
```

**이유**: useEffect는 render 이후 실행되므로, 만료 상태에서도 children이 잠깐 렌더링될 수 있음 → flicker 방지용으로 render 함수에서 한 번 더 체크하여 null 반환.

## 4-4. 판정 기준

### 만료로 간주되는 경우
`expiresAt`이 존재하고 현재 시각보다 과거 → **만료**

### 만료 아닌 것으로 통과되는 경우
- `expiresAt === null` (구독 정보 없음)
- `expiresAt >= now` (아직 유효)

## 4-5. 프로필 생성 정책 (연관 로직)

`/api/user-profile/route.ts`에서 프로필이 없는 사용자에게 자동으로:
- `subscription_expires_at = NOW + 7일` (7일 무료체험)

→ 신규 가입 후 7일 뒤부터 `SubscriptionGuard`가 만료 판정.

## 4-6. 현재 상태 (원복됨)

**업데이트 (2026-04-12)**: 사용자가 **첫 번째 블록(useEffect alert + redirect)만 주석 해제**하여 원래 로직으로 복원. 두 번째 블록(render 시 null 반환)은 여전히 주석 유지.

| 블록 | 현재 상태 |
|------|----------|
| 블록 1 (useEffect alert + redirect) | **활성** — 만료 시 알림 + `/class` 이동 |
| 블록 2 (render 시 `return null`) | 주석 유지 — flicker 방지 생략 |

### 동작 영향

- 만료된 사용자는 alert 대화상자 표시 + `/class` 로 리다이렉트됨 (정상 동작)
- Effect가 render 이후 실행되는 동안 children이 잠깐 노출될 수 있음 (block 2 주석의 부작용 — flicker 가능)

### 남은 dead code 주의

- 두 번째 블록의 `now`, `expiresAt` 계산은 여전히 수행되지만 사용처 없음
- ESLint 경고(`no-unused-vars`)가 뜰 가능성 있음 → 해당 변수 2줄도 정리하거나 block 2도 복원 권장

## 4-7. 원래 로직의 잠재적 문제 (주석 해제 시)

1. `useRouter()` 의존성으로 effect 불필요 재실행 가능
2. `useUserProfile` 실패 시 UX 이상 (`isLoading=false, profile=null`이면 스피너 안 뜨지만 차단도 안 됨)
3. 클라이언트 시계 오차로 오판정 가능
4. `alert()`은 UX 나쁨 — `Dialog` 또는 `toast`로 교체 권장
5. useEffect + render 이중 체크 중복 역할

## 4-8. 권장 조치 (원복된 현재 상태 기준)

### 옵션 A: 두 번째 블록도 복원 (flicker 방지 완성)

```typescript
const now = new Date();
const expiresAt = profile?.subscription_expires_at ? new Date(profile.subscription_expires_at) : null;
if (expiresAt && expiresAt < now) {
    return null;
}
```

- useEffect 실행 전까지 children이 잠시 노출되는 문제 방지
- 만료 판정 이중 실행으로 안전

### 옵션 B: 두 번째 블록 완전 삭제

flicker 이슈가 실제로 미미하면, 주석된 블록과 `now`, `expiresAt` 변수 삭제로 코드 정리.

### 옵션 C: `alert()` 교체

UX 개선을 위해 `alert()` 대신 `Dialog` 컴포넌트 사용 (선택).

## 4-9. 3번 섹션 (알림 원인) 재정리

첫 번째 블록이 복원되었으므로, **현재 코드가 정상적으로 만료 체크를 수행함**. 즉 로컬에서 알림을 본다면 그것은 **정상 동작**.

- `user_profiles.subscription_expires_at < now` 인 사용자가 `/class/lesson/*` 진입 시 알림 표시
- sniper4457(e959ffe1) 계정의 `subscription_expires_at = 2026-04-18`이므로 **만료 전**이라 알림 안 떠야 함

### 알림이 뜬다면
