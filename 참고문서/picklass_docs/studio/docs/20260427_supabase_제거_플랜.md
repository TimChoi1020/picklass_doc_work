# Supabase 직접 호출 제거 → NestJS 일원화 플랜

**작성일**: 2026-04-27
**목적**: 웹 앱이 Supabase에 직접 말 거는 부분을 모두 없애고, NestJS API 한 곳으로 일원화한다.

---

## 1. 한 줄 요약

> "지금은 가게 손님(웹)이 부엌(Supabase 데이터베이스)에 직접 들어가서 음식을 가져오고 있다. 이걸 **반드시 종업원(NestJS API)을 거쳐서만** 받도록 바꾸는 작업이다."

- **Supabase 데이터베이스 자체는 그대로 둔다.** (이전하지 않음)
- 다만 웹이 그 데이터베이스에 **직접 접속하는 길**(Supabase JS SDK)만 막는다.
- 모든 데이터 요청은 NestJS를 통해서만 흘러가게 한다.

---

## 2. 왜 이렇게 바꾸고 싶은가 (배경)

현재 구조의 문제:

| 항목 | 현재 상태 | 왜 문제인가 |
|---|---|---|
| 데이터 접근 경로 | 웹 → Supabase 직접 / 웹 → NestJS → DB 두 갈래 | 권한 규칙·검증이 두 곳에 흩어짐 |
| 보안 | 웹이 Supabase 서비스 키를 사용 (Next.js API 라우트) | 키가 새면 DB 전체 노출 위험 |
| 디버깅 | 어디서 데이터가 잘못됐는지 두 군데 다 봐야 함 | 장애 추적이 느림 |
| 유지보수 | 같은 비즈니스 로직이 NestJS와 Next.js API 양쪽에 분산 | 수정 시 양쪽 다 손봐야 함 |

NestJS 한 곳으로 모으면:
- **보안 규칙 한 곳에서 관리** (이미 JWT + AuthGuard가 잘 동작 중)
- **로그/모니터링 한 곳에 집중**
- **나중에 데이터베이스를 바꾸더라도 웹은 영향 없음** (NestJS만 바꾸면 됨)

---

## 3. 다른 시스템(tutoring, backoffice) 로그인 연동에 미치는 영향

**👉 영향 없음.**

이유:
- 로그인은 이미 NestJS의 자체 JWT(토큰) 시스템으로 동작 중이다. (Supabase 인증을 안 쓴 지 한참 됨)
- tutoring/backoffice와는 같은 **JWT 시크릿 키**를 공유하고 있어서, 한 쪽에서 발급한 토큰을 다른 쪽이 그대로 인정한다.
- 이번 작업에서 **JWT 시크릿이나 토큰 형식은 일절 건드리지 않는다.**

> 즉, 이번 작업은 "데이터를 어디서 가져오는가"만 바꾸는 것이고, "누가 로그인했는가"를 다루는 부분은 건드리지 않는다.

---

## 4. 무엇을 옮겨야 하나 (작업 범위)

쉬운 것부터 어려운 것 순서로 4개 그룹으로 나눴다.

### 그룹 A — 단순 데이터 조회/저장 (쉬움) ⭐

**비유**: 메뉴판 보고 주문하는 것 같은 일. 종업원이 부엌 가서 가져다주면 됨.

| 다루는 데이터 | 현재 어디서 처리? | 옮길 곳 |
|---|---|---|
| 사용자 프로필 (`user_profiles`) | 웹의 `/api/user-profile` | NestJS `/user-profiles` |
| 텍스트/지문 (`texts`) | 웹의 `/api/texts`, `/api/texts/[id]`, `/api/texts/twins/[id]` | NestJS `/texts` |
| 단어 사전 (`word_dictionary`) | 웹의 `/api/word-definitions` | NestJS `/word-definitions` |
| 단어 빈도 (`words_6000`) | 웹의 `/api/text-analysis` | NestJS `/text-analysis` |
| 전략적 읽기 데이터 (`strategic_reading_data`) | 웹의 `/api/strategic-reading` + 웹 직접 호출 2곳 | NestJS `/strategic-reading` |

**예상 작업량**: 보통. 코드 옮기기 + 클라이언트 호출 경로 변경.
**리스크**: 낮음. 일대일 이전이라 기능 변경 없음.

---

### 그룹 B — 파일 저장소 (중간) ⭐⭐

**비유**: 부엌 창고에 보관된 큰 짐(음향 파일, 업로드 파일)을 어떻게 할 것인가.

현재 두 종류의 파일 저장소를 사용 중:

| 저장소 | 용도 | 누가 쓰는가 |
|---|---|---|
| `files` 버킷 | 사용자가 업로드한 파일 | 웹이 직접 |
| `tts-cache` 버킷 | 음성 합성(TTS) 결과 캐시 | 웹의 `/api/azure-speech`, `/api/tts-cache` |

**3가지 선택지**:

#### 선택지 B-1: NestJS가 임시 다운로드 링크만 발급 (권장)
- 클라가 NestJS에 "내 파일 받고 싶어요" 요청 → NestJS가 1시간짜리 임시 URL을 만들어 전달 → 클라는 그 URL로 직접 다운로드
- **장점**: 큰 파일이 NestJS 서버를 통과하지 않음 (서버 부담 적음)
- **단점**: NestJS 안쪽에는 여전히 Supabase Storage SDK가 남음
- **현실성**: ⭐⭐⭐ 가장 균형 잡힌 선택

#### 선택지 B-2: NestJS가 모든 파일 송수신을 직접 중계
- 클라 ↔ NestJS ↔ Supabase Storage
- **장점**: Supabase 흔적이 완전히 안쪽에 숨음
- **단점**: NestJS 서버 트래픽 부담 증가, 구현 복잡

#### 선택지 B-3: 다른 저장소(예: AWS S3)로 이전
- **장점**: Supabase에서 완전히 독립
- **단점**: 큰 작업, 기존 파일 이전 비용, 운영비 변동

---

### 그룹 C — 실시간 알림 (어려움) ⭐⭐⭐

**비유**: 주방장이 "음식 다 됐어요!"라고 손님에게 즉시 알리는 시스템.

현재 사용 중:
- 백그라운드 작업(예: 지문 분석, 전략적 읽기 생성)이 끝나면 화면에 즉시 결과 표시
- 알림 배지 실시간 업데이트
- Supabase Realtime이라는 WebSocket 기반 푸시 시스템을 사용 중

**문제**: NestJS에는 아직 실시간 푸시 기능이 전혀 없다.

**3가지 선택지**:

#### 선택지 C-1: NestJS WebSocket 도입 (강력하지만 큼)
- 새 라이브러리 설치 + 서버 구조에 새 컴포넌트 추가
- **장점**: 진짜 실시간, 양방향 통신
- **단점**: 가장 큰 작업, 운영도 복잡

#### 선택지 C-2: NestJS SSE(Server-Sent Events) 도입
- WebSocket보다 단순한 단방향 푸시
- **장점**: 구현 간단, NestJS에 기본 지원
- **단점**: 한 방향만 가능 (서버→클라)

#### 선택지 C-3: 폴링 (가장 단순)
- 클라가 3~5초마다 "끝났어요?"라고 물어봄
- **장점**: 구현 가장 단순, 장애 적음
- **단점**: "실시간"은 아님 (몇 초 지연)
- **현실성**: ⭐⭐⭐ async task 진행률 정도라면 충분

#### 선택지 C-4: Supabase Realtime만 예외로 유지
- 인증과 무관한 WebSocket 채널이라 영향 적음
- **장점**: 작업량 최소
- **단점**: "Supabase 완전 제거" 원칙에 어긋남

---

### 그룹 D — 죽은 코드 정리 (즉시 가능) ⭐

**비유**: 옛날에 쓰던 메뉴판이 아직 가게에 걸려 있지만 이미 무시되는 상태. 떼어내기만 하면 됨.

웹 코드 곳곳에 `supabase.auth.getUser()` 같은 호출이 남아있는데, 사용자가 Supabase로 로그인한 적이 없어서 **항상 빈 값**을 반환한다. 즉 사실상 기능을 막는 게이트로만 동작 중.

→ 그룹 A/B/C 작업하면서 자연스럽게 NestJS 인증 정보로 교체하면 끝.

---

## 5. 작업 순서 권장안

```
1단계 → 사전 확인
   - 데이터베이스 테이블이 NestJS 측에 모델로 등록돼 있는지 확인
   - 없으면 추가 (Prisma db pull)

2단계 → 그룹 A 진행 (1~2주)
   - 단순 CRUD 6개 엔드포인트를 NestJS로 옮김
   - 동시에 그룹 D 죽은 코드 정리

3단계 → 그룹 B 결정 및 진행 (1주)
   - 선택지 B-1 권장
   - 결정되면 Storage 관련 호출 이전

4단계 → 그룹 C 결정 및 진행 (1~2주)
   - 선택지 C-3(폴링) 또는 C-4(예외 유지) 권장
   - WebSocket 도입은 필요할 때 별도 프로젝트로

5단계 → 정리
   - Supabase SDK 의존성 제거
   - 환경변수 정리 (NEXT_PUBLIC_SUPABASE_*)
   - 사용 안 하는 파일 삭제
```

**전체 예상 기간**: 3~5주 (선택지에 따라 변동)

## 7. 자주 묻는 질문

**Q1. 작업 중에 서비스가 멈추나요?**
A. 아니요. 단계별로 옮기면 한 번에 한 기능씩만 영향을 받고, 옮긴 즉시 정상 동작합니다.

**Q2. 사용자 데이터는 안전한가요?**
A. 데이터베이스 자체는 건드리지 않으므로 데이터 손실 위험은 없습니다.

**Q3. tutoring이나 backoffice도 같이 수정해야 하나요?**
A. 아니요. 이번 작업은 studio 한 곳에 국한됩니다. 로그인 토큰 형식이 동일하므로 다른 시스템에는 변경이 없습니다.

**Q4. 비용이 늘어나나요?**
A. NestJS 서버를 거치는 트래픽이 약간 늘어날 수 있지만, 그룹 B에서 선택지 B-1을 고르면 큰 파일은 여전히 Supabase에서 직접 받으므로 거의 차이 없습니다.

**Q5. 나중에 Supabase에서 다른 데이터베이스로 옮기고 싶다면?**
A. 이 작업이 끝나 있으면 훨씬 수월해집니다. NestJS의 데이터 접근 부분만 바꾸면 웹은 그대로 동작합니다.

---

## 8. 안 하면 어떻게 되나요?

지금처럼 두 갈래로 운영해도 당장 큰 문제는 없습니다. 다만:

- 새 기능을 만들 때마다 "어디에 만들어야 하지?"를 매번 결정해야 함
- 보안 사고 발생 시 영향 범위가 더 큼 (서비스 키 노출 위험)
- 누군가 떠난 뒤 다음 사람이 코드 구조를 이해하기 더 어려움

**결론**: 급하지 않지만, 미루면 점점 더 큰 작업이 됨.
