## 1. 아키텍처 개요

### 1.1 역할 분리

오케스트레이터는 두 레이어로 역할을 분리한다:

```
[Orchestrator — 규칙 기반 흐름 제어]
  scoringMode         → 어떻게 평가할지 (exact / holistic / pronunciation / writing-eval)
  questionMaxAttempts → 문항당 최대 시도 횟수
  retryScope          → 재도전 기준 지표
  answerType          → 어떤 입력 UI를 쓸지
  passageMode         → 지문 노출 방식
  questionCount       → 단일/다중 문항 여부

[LLM — 자율 피드백 생성]
  pedagogyInstruction → 시스템 프롬프트 (피드백 형식·기준·KPI 지시)
  purpose             → 모듈 목적 요약 (greeting 생성에 활용)
  feedbackStyle       → 제거됨 (2026-05-12). pedagogyInstruction으로 통합
```

### 1.2 OrchestratorContext 핵심 필드

| 필드 | 타입 | 설명 |
|---|---|---|
| `pedagogyProfile` | `ModulePedagogyProfile` | ContentConfig 완전 대체 (2026-04-07) |
| `passage` | `PassageData` | 지문 데이터 |
| `questions` | `QuestionData[]` | 문항 목록 |
| `learnerState` | `LearnerState` | 학습자 상태 |
| `flags` | `AiModuleFlags` | `pedagogyProfile`에서 사전 계산된 불리언 술어 (`hasRightWrongConcept`, `hasHints`, `isMultiQuestion` 등) |
| `hasCelebrated` | `boolean` | celebrate 발화 여부 — ref 기반으로 `recentMessages` 타이밍 문제 방지 |
| `recentMessages` | `ChatMessage[]` | 최근 채팅 이력 |
| `passageShown` | `boolean` | 지문 노출 여부 |
| `passagePreviewOnly` | `boolean` | 미리보기 전용 여부 |
| `activeQuestionId` | `string \| null` | 현재 활성 문항 ID (2026-04-26 추가) |
| `eventFiredIds` | `Record<string, string[]>` | 이벤트 발화 추적 (중복 방지) |
| `feedbackGivenIds` | `Record<string, string[]>` | 피드백 제공 문항 추적 (키: `'holistic'` \| `'correctness'` \| `'pronunciation'` \| `'writing'`) |

### 1.3 설계 원칙

#### scoringMode 우선 원칙

`QuestionType`(입력 방식)과 `scoringMode`(채점 방식)는 독립적이다. 규칙 필터는 반드시 `scoringMode` 기준으로 판별한다.

```
WRD: answerType='short-text', scoringMode='exact'
GMN: answerType='short-text', scoringMode='holistic'
→ 같은 short-text 타입이지만 서로 다른 규칙이 적용됨
→ ruleHolisticFeedback 필터 조건은 q.type이 아닌 hasRightWrongConcept(context)로 판별
```

| 모듈 | answerType | scoringMode | ruleHolisticFeedback | ruleWrongAnswerFeedback |
|---|---|---|---|---|
| WRD | short-text | exact | ❌ skip | ✅ 적용 |
| GMN | short-text | holistic | ✅ 적용 | ❌ skip |
| PRD | essay | holistic | ✅ 적용 | ❌ skip |
| QAR | multiple-choice | exact | ❌ skip | ✅ 적용 |
| SWR | sentence-write | writing-eval | ❌ skip | ❌ skip (ruleWritingFeedback 처리) |

#### ref 동기화 패턴

OrchestratorContext에 새 필드를 추가할 때 React state 지연을 피하기 위해 ref를 사용한다:

```typescript
const newFieldRef = useRef<T>(initialValue);
useEffect(() => { newFieldRef.current = reactState; }, [reactState]);

const context: OrchestratorContext = {
  ...
  newField: newFieldRef.current,  // state 지연 없이 항상 최신값
};
```

`activeQuestionId`와 `hasCelebrated`가 이 패턴으로 추가된 사례.

#### 중복 발화 방지

`eventFiredIds` (이벤트), `feedbackGivenIds` (피드백)를 활용해 같은 트리거가 중복 발화되지 않도록 한다. 규칙 추가 시 반드시 해당 ref를 확인·업데이트해야 한다.

> **주의**: `hintButtonUsedIds`는 OrchestratorContext 필드가 **아니다**. Hook 내부 `hintButtonUsedRef`로만 관리되며, `ModuleOrchestratorHookState`를 통해 FeedbackPanel UI에 전달된다. Orchestrator 규칙에서 직접 참조 불가.

### Rule 3: ruleRepeatWrongAnswer

오답 횟수에 따라 단계적 에스컬레이션:

| 오답 횟수 | 조건 | 액션 | 피드백 케이스 |
|---|---|---|---|
| 1회 | `questionMaxAttempts >= 2` + exact 모듈 | `giveHint` (hints.direct) | b-2start |
| 2회 이상 | `questionMaxAttempts >= 2` | `revealAnswer` → 정답 공개 | d / d-end |

- **제외**: `audio-record`, `sentence-write` (전용 피드백 룰 존재)
- **activeQuestionId 필터**: 현재 활성 문항만 평가 — 이전 문항 오답이 현재 문항에 영향 방지
- `questionMaxAttempts`는 `Math.min(value, 2)`로 캡핑 — DB 값 무관하게 실질 최대 2회

```typescript
// activeQuestionId 필터 — questions.find() 내부
if (context.activeQuestionId && q.id !== context.activeQuestionId) return false;
```

### Rule 3b: ruleOfferHint

- **조건**: `(idleSeconds >= 20 && 미답변 문항) || (오답 상태 && feedbackGivenIds['correctness' | 'holistic'] 포함)` + `offerGiven` 미발화
- **액션**: `offerHint` → "막히셨나요? 힌트가 필요하면 버튼을 눌러보세요 💡" + 인라인 버튼

> ```typescript

### Rule 4a: ruleHolisticFeedback

- **조건**: `!hasRightWrongConcept(context)` (= `scoringMode === 'holistic'`) + 답변 제출 직후
- **제외**: `answerType === 'sentence-explain'` (CLR) / `answerType === 'sentence-write'` (PWR 미구현, 향후 추가)
- **액션**: `giveFeedback(holistic)` → LLM 피드백 생성
- `feedbackGivenIds['holistic']`으로 중복 방지

> `q.type`이 아닌 `scoringMode`로 판별하는 이유: WRD(`short-text` + `exact`)와 GMN(`short-text` + `holistic`)이 동일한 `q.type`을 가지므로, `q.type`으로 판별하면 WRD 오답에서 `ruleHolisticFeedback`이 발동되는 버그가 발생한다.

### Rule SHR-C: rulePronunciationFeedback

- **조건**: `q.type === 'audio-record'` + 음성 제출 직후 + `feedbackGivenIds['pronunciation']` 미포함
- **액션**: `giveFeedback(pronunciation)`
- **힌트 에스컬레이션** (Hook에서 처리, score < 70 시):
  - 1차 저점수: `hints.button` → `awaitingPronunciationConfirm` UI에 "💡 힌트 보기" 버튼 노출 (학습자 선택)
  - 2차+ 저점수: `hints.direct` 자동 표시 (없으면 `/ai/feedback` API 생성)
  - 판단 기준: `pronunciationHintOfferedRef`(questionId 이력) — Orchestrator 규칙 변경 없음

### Rule SWR-A: ruleWritingFeedback

- **조건**: `scoringMode === 'writing-eval'` + 답변 제출 직후 + `feedbackGivenIds['writing']` 미포함
- **액션**: `giveFeedback(writing)`

> **2026-06-09 변경**: 조건을 `q.type === 'sentence-write'` → `scoringMode === 'writing-eval'`로 전환. SWR 모듈에 `scoringMode='writing-eval'`을 명시하여 타입 역추론 제거. scoringMode 우선 원칙(§1.3) 일관 적용.

### Rule 4c: ruleWrongAnswerFeedback

- **조건**: `hasRightWrongConcept(context)` (exact 모듈) + 첫 오답 (`attemptHistory.length === 1`)
- **제외**: `essay`(holistic 전용), `scoringMode === 'writing-eval'`(ruleWritingFeedback 처리)
- **액션**: `giveFeedback(correctness)` → "아쉽네요! 다시 한번 생각해볼까요?"
- `feedbackGivenIds['correctness']`으로 중복 방지

> `short-text`를 제외하지 않는 이유: 이전에 `short-text`를 제외했을 때 WRD(`short-text` + `exact`) 오답이 이 룰을 건너뛰어 `ruleHolisticFeedback`까지 내려가는 버그가 있었다. `hasRightWrongConcept` 체크로 exact 모듈임을 보장하므로 `short-text` 별도 제외 불필요.

### Rule 6: ruleCompleteAfterCelebrate

- **조건**: `celebrate` 발화 완료 + 전체 문항 답변 완료
- **제외**: `answerType === 'sentence-explain'` (CLR은 explainedSentences 기준으로 완료)
- **exact 모듈**: celebrate 없이 즉시 `completeModule` (`skipCelebrateCheck = true`)
- **holistic 모듈**: 모든 문항 `feedbackGivenIds['holistic']` 확인 후 `completeModule`
- **writing-eval 모듈**: 모든 문항 `feedbackGivenIds['writing']` 확인 후 `completeModule`
  - `retryThreshold` 기반 재도전 판정 미구현 — 점수 무관 항상 완료

```typescript
const { scoringMode } = context.pedagogyProfile;
const skipCelebrateCheck = scoringMode === 'holistic' || scoringMode === 'writing-eval';
const hasCelebrated = skipCelebrateCheck || context.hasCelebrated;
if (!hasCelebrated) return null;
if (scoringMode === 'holistic') {
  const holisticGiven = context.feedbackGivenIds['holistic'] ?? [];
  if (!questions.every((q) => holisticGiven.includes(q.id))) return null;
} else if (scoringMode === 'writing-eval') {
  const writingGiven = context.feedbackGivenIds['writing'] ?? [];
  if (!questions.every((q) => writingGiven.includes(q.id))) return null;
}
```

### Rule 5: ruleCorrectAnswer

- **조건**: 마지막 답변 문항이 정답 판정
- **정답 판정** (scoringMode 우선):

```typescript
const isAnsweredCorrectly = hasRightWrongConcept(context)
  ? state.answers[lastId] === q.answer   // exact/pronunciation: 실제 정답 비교
  : !!state.answers[lastId];             // holistic: 답변 존재 여부
```

- holistic: `feedbackGivenIds['holistic']` 미포함 → null (Rule 4a에 양보)
- audio-record: `feedbackGivenIds['pronunciation']` 미포함 → null (Rule SHR-C에 양보)
- writing-eval: `feedbackGivenIds['writing']` 미포함 → null (Rule SWR-A에 양보)
- 정답 → 다음 문항 or `celebrate` (마지막 문항)
- 2차 정답: `attemptHistory[lastId].length > 1` → 케이스 c / c-end

### Rule 7: ruleInitialEntry

### Rule 7b: ruleClrIdle (CLR 전용)

- `answerType === 'sentence-explain'`이면 null 반환 — 오케스트레이터 무동작
- CLR은 학생이 문장을 자유 클릭하므로 추가 액션 없음

**CLR 간섭 방지 가드 — `sentence-explain`이 걸려 있는 룰:**

| 룰 | 가드 |
|---|---|
| Rule 4a `ruleHolisticFeedback` | `answerType === 'sentence-explain'` → null |
| Rule 6 `ruleCompleteAfterCelebrate` | 동일 |
| Rule 8 `rulePresentNextQuestion` | 동일 |
| Rule 7b `ruleClrIdle` | 항상 null (오케스트레이터 무동작) |

### Rule 8: rulePresentNextQuestion

- **조건**: 미답변 문항 존재
- **액션**: `askQuestion` → 첫 번째 미답변 문항 제시
- 미답변 0개 + exact/pronunciation 모듈 → `celebrate`
- 미답변 0개 + holistic/writing-eval 모듈 → null (Rule 6에서 처리)
- `answerType === 'sentence-explain'` → null (CLR 간섭 방지)

## 4. 힌트 시스템

### 4.1 힌트 3레벨 구조

```
[Level 0 — button] 학습자 버튼 클릭
  → ruleOfferHint: FeedbackPanel AI 메시지에 인라인 "💡 힌트 보기" 버튼 안내
  → 학생 클릭 → handleHintButtonClick(questionId, hints.button)
  → "💡 힌트: {hints.button}" AI 메시지 표시
  → hintButtonUsedIds에 questionId 기록

[Level 1 — direct] ruleRepeatWrongAnswer 자동 (b-2start)
  조건: questionMaxAttempts >= 2 + 정오답 모듈 + 오답 1회
  → giveHint { staticHint: hints.direct }
  → "아쉽게도 틀렸어요. 다시 한 번 생각해볼게요 💡\n\n힌트: {hints.direct}"

[Level 2 — answer] ruleRepeatWrongAnswer → revealAnswer (d / d-end)
  조건: 오답 2회 이상
  → answer 필드 기반 정답 제시 후 강제 완료
```

### 4.2 발동 조건

| 레벨 | 트리거 | 조건 |
|---|---|---|
| Level 0 (button) | 학생 직접 버튼 클릭 | ruleOfferHint 메시지 인라인 버튼 |
| Level 1 (direct) | ruleRepeatWrongAnswer 자동 | questionMaxAttempts >= 2 + 오답 1회 |
| Level 2 (answer) | revealAnswer | 오답 횟수 >= 2 (`questionMaxAttempts`를 2로 캡핑하므로 실질적으로 고정값) |

### 4.3 Eager 생성 정책

```
모듈 진입 → Gemini: 문항 + hints 동시 생성 → module_questions 저장
힌트 요청 → module_questions에서 즉시 반환 (API 0회)
```

`/ai/hint` API 실시간 호출 경로 제거 (2026-05-12). staticHint 없는 경우만 `buildHintMessage()` 폴백.

```typescript
staticHint 있음 → "💡 힌트: {hints.direct 값}"
staticHint 없음 → buildHintMessage() (범용 폴백)
```

### 4.4 SHR(발음) 모듈 힌트 전략 (2026-06-09 추가)

텍스트 문항과 달리 `audio-record` 문항은 "막혀서 못 쓰는" 상태가 없으므로 `ruleOfferHint` / `ruleRepeatWrongAnswer` 경로가 아닌 **피드백 직후 Hook에서 별도 에스컬레이션**으로 처리한다.

```
1차 녹음 제출 → score < 70
  → hints.button 있음 → awaitingPronunciationConfirm UI에 "💡 힌트 보기" 버튼 노출
  → pronunciationHintOfferedRef에 questionId 기록

2차+ 녹음 제출 → score < 70 (이미 button 제공됨)
  → hints.direct 자동 표시 "💡 발음 팁: ..."
  → hints.direct 없으면 /ai/feedback { generateHint: true } API 생성

score >= 70 → 힌트 없음
```

| 시도 | 조건 | 힌트 | 방식 |
|---|---|---|---|
| 1차 | score < 70 + `hints.button` 존재 | `hints.button` | UI 버튼 (학습자 선택) |
| 2차+ | score < 70 + button 이미 제공 | `hints.direct` | 피드백 직후 자동 |
| 2차+ | score < 70 + direct 없음 | API 생성 | `/ai/feedback generateHint=true` |

> 텍스트 힌트(Level 0/1/2)의 "버튼 → direct → answer" 에스컬레이션과 동일한 원칙.
> answer 공개가 없는 이유: 발음은 정해진 정답이 없고 점수로만 판정하기 때문.

**구현 파일**

| 파일 | 변경 내용 |
|---|---|
| `useModuleOrchestrator.ts` | `pronunciationHintOfferedRef`, `pronunciationButtonHint` state, 에스컬레이션 로직, `handlePronunciationHintButtonClick` |
| `panels.tsx` | `awaitingPronunciationConfirm` 블록에 `pronunciationButtonHint` 버튼 추가 |
| `MobileSplitLayout.tsx` | props 전달 |
| `LessonSession.tsx` | hook 구조분해 + 데스크톱·모바일 양쪽 전달 |

### 4.5 holistic 모듈 힌트 전략

정해진 정답이 없는 holistic 모듈(PRD, SUM 등)에서 힌트는 "작성 시작 촉진" 역할:
- 미답변 상태: 힌트 발화 O
- 답변 후: 힌트 발화 X → `ruleHolisticFeedback`에 위임

### 4.5 힌트 시스템 — 문항 패널 분기 요약

트리거와 타이밍은 문항 패널 유형으로 분기되며, 힌트 표시는 두 경로 모두 FeedbackPanel(AI 채팅)에서 이루어진다.

### 5.5 timed-select 모듈 (SKM)


| done 상태 | blur 복원 | blur 없음 |

### 6.4 답안 제출 누락 방지 패턴 (2026-06-02)

#### 발생 원인

`orchestrate()`는 동시 실행 방지를 위해 `isLoadingRef` 뮤텍스를 사용한다. LLM API 응답 대기 중(`isLoadingRef = true`) 학생이 답안을 제출하면 `submitAnswer()` 내부의 `orchestrate()` 호출이 즉시 return되어 **답안이 상태에는 기록되지만 오케스트레이터가 처리하지 못하는 누락**이 발생했다.

또한 `awaitingFeedbackConfirm` 상태(피드백 확인 대기)에서 학생이 새 답안을 제출하면 `ruleCorrectAnswer`가 발동해 다음 문항으로 이동하지만 `awaitingFeedbackConfirm`이 클리어되지 않아 **UI 불일치**(피드백 확인 버튼 잔류)가 발생했다.

#### 해결: `pendingOrchestrateRef` + `awaitingFeedbackConfirm` 즉시 해제

**파일**: `useModuleOrchestrator.ts`

```typescript

// ② orchestrate() finally 블록 — 차단 중 요청을 LLM 완료 후 재실행

    pendingOrchestrateRef.current = false;
    orchestrateRef.current(true);  // 최신 answers/attemptHistory 기준으로 재실행

}

// ③ submitAnswer() — 두 가지 수정
const submitAnswer = useCallback((questionId, answer) => {
  // 버그 2: 새 답안 제출 = 피드백 확인 대기 해제 (학생이 적극적으로 진행 의사 표시)
  if (awaitingFeedbackConfirmRef.current) {
```

### retryThreshold — 모듈 재도전 판정 (미구현)

#### 개념 정의

모듈 완료 후 학습자의 성취도가 `retryThreshold`에 미달하면 같은 모듈을 재시작하도록 신호를 보내는 기능이다.

- `retryThreshold` — 재도전 진입 임계값 (%). 이 값을 **넘으면** 정상 완료, **미달하면** 재도전
- `retryScope` — 어떤 지표로 점수를 계산하는지 (모듈별 상이)

`questionMaxAttempts`(문항 단위 재시도)와 다른 개념이다. `retryThreshold`는 **모듈 전체** 재도전 판정이다.

#### 모듈별 retryScope · retryThreshold

전체 값은 `apps/web/src/lib/pedagogy/picklass_pedagogy_profiles.ts`에 정의되어 있다.

| 모듈 | scoringMode | retryScope | retryThreshold |
|---|---|---|---|
| WRD | exact | `spelling-accuracy` | 80% |
| WSD | pronunciation | `pronunciation-accuracy` | 75% |
| GMN | holistic | `inference-accuracy` | 70% |
| WWB | holistic | `semantic-relevance` | 70% |
| PRD | holistic | `inference-accuracy` | 60% |
| SCN | holistic | `keyword-hit-rate` | 65% |
| SKM | holistic | `main-idea-accuracy` | 75% |
| CLR | holistic | `comprehension-depth` | undefined (판정 없음) |
| SUM | holistic | `summary-completeness` | 60% |
| QAR | holistic | `evidence-quality` | 65% |
| SWR | holistic | `writing-quality` | (profiles 파일 참조) |
| PWR | holistic | `logical-coherence` | (profiles 파일 참조) |
| RRD | pronunciation | `pronunciation-accuracy` | (profiles 파일 참조) |

#### score 계산 경로 — retryScope별

`retryThreshold`와 비교할 `score`를 어떻게 구하느냐가 핵심 설계 결정이다.

| retryScope 유형 | 해당 모듈 | score 계산 방법 | 구현 난이도 |
|---|---|---|---|
| `spelling-accuracy` | WRD | `calcScore()` 정답률 | ✅ Phase 1 |
| `pronunciation-accuracy` | WSD, RRD | `calcScore()` 발음 점수 평균 | ✅ Phase 1 |
| holistic 계열 전체 | GMN, PRD, WWB, SCN, SKM, SUM, QAR, SWR, PWR | LLM 피드백 시 수치 추출 필요 | ⚠️ Phase 2 |
| `comprehension-depth` | CLR | engagement time 기반 또는 미적용 | ⚠️ Phase 2 |

**Phase 1 문제점**: `calcScore()`는 holistic 모듈에서 `!!answers[q.id]`(제출 여부)로만 계산해 항상 100%가 나온다. holistic retryScope를 평가하려면 LLM이 피드백 생성 시 점수를 함께 반환하고, 이를 별도 ref에 저장하는 메커니즘이 필요하다.
