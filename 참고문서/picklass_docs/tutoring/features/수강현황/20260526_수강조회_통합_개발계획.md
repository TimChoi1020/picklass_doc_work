# tutoring INTERNAL 수강 조회 정합성 수정

> **관련 문서**: 백오피스 `docs/accesscode/20260526_액세스코드_B2B통합_수정완료.md`
>
> 이 문서는 백오피스 access_codes 정리 작업이 완료된 후 진행하는 tutoring 측 후속 작업을 다룹니다.  
> **선행 조건**: 백오피스 Phase A~D 완료 → ✅ 완료 (2026-05-26)

---

## 배경 및 목적

현재 tutoring의 수강 조회 로직에서 `status_code='inactive'`가 "등록 완료"를 의미하는 관례가 새 설계(`inactive`=미사용, `active`=수강 중)와 충돌합니다. 데이터 마이그레이션 후 쿼리와 등록 처리 로직을 새 설계에 맞게 교체합니다.

```sql
-- 현재 getEnrolledCourses() 조회 조건 (lessons.service.ts:82~113)
WHERE ac.status_code = 'inactive'   -- 의미상 "등록 완료"를 inactive로 표현 (혼란)
  AND ac.course_id IS NOT NULL
  AND ac.user_id = :studentId
```

### 백오피스 완료 작업 참고

백오피스 Phase A~D 완료로 아래 사항이 이미 반영되어 있습니다:

| 항목 | 내용 |
|------|------|
| `access_codes.usage_start_date` / `usage_end_date` | 관리자가 코드 생성 시 직접 사전 지정 가능 (미지정 시 학습자 등록 시점 자동 계산) |
| `source_type`, `auth_key`, `partner_member_id` 컬럼 | ✅ DROP 완료 |
| `access_code_options`, `frt_lesson_options` 테이블 | ✅ DROP 완료 |

## Phase E-1: status_code 데이터 마이그레이션

### 변경 내용

| 조건 | 현재 status_code | 변경 후 |
|------|-----------------|---------|
| `source_type='INTERNAL'` AND `user_id IS NOT NULL` (학습자 등록 완료) | `inactive` | `active` |
| `user_id IS NULL` (미사용) | `inactive` | `inactive` (유지) |

### DDL 파일

`apps/api/prisma/manual-sql/2026-05-26_migrate_access_codes_status.sql` ✅ 작성 완료

```sql
BEGIN;

-- 학습자가 등록 완료한 access_codes 레코드를 active로 통일
-- (구 관례: inactive+user_id = 등록 완료 → 신 설계: active = 수강 중)
-- source_type 컬럼은 Phase A에서 이미 DROP됨
UPDATE access_codes
SET status_code = 'active'
WHERE status_code = 'inactive'
  AND user_id IS NOT NULL;

COMMIT;
```

> **주의**: access_codes 테이블은 tutoring·speaking이 공유합니다. 실행 전 영향 행 수를 확인하십시오.

### 실행 방법

1. 실행 전 영향 행 수 확인:
   ```sql
   SELECT COUNT(*)
   FROM access_codes
   WHERE status_code = 'inactive'
     AND user_id IS NOT NULL;
   ```
2. pgAdmin / DBeaver / psql에서 SQL 직접 실행
3. 실행 후 확인:
   ```sql
   SELECT COUNT(*) FROM access_codes
   WHERE user_id IS NOT NULL AND status_code = 'active';
   ```

## Phase E-2: `getEnrolledCourses()` INTERNAL 쿼리 교체

**파일**: `apps/api/src/lessons/lessons.service.ts`

### 현재 코드 (lines 82–113)

```sql
-- INTERNAL 수강 중 (현재: inactive + user_id 조건)
SELECT DISTINCT
  c.id as course_id,
  c.title as course_title,
  c.level_code,
  c.total_lessons
FROM access_codes ac
JOIN courses c ON ac.course_id = c.id
WHERE ac.status_code = 'inactive'
  AND ac.course_id IS NOT NULL
  AND ac.user_id = '${studentId}'
  AND c.deleted_at IS NULL

UNION

-- 나만의 수업 (custom 과정)
SELECT c.id, c.title, c.level_code, c.total_lessons
FROM courses c
WHERE c.created_by = '${studentId}'
  AND c.genre_code = 'custom'
  AND c.deleted_at IS NULL

ORDER BY course_title
```

### 변경 후 (2-way UNION)

```sql
-- ① INTERNAL: status_code='active' (source_type 컬럼 삭제됨)
SELECT DISTINCT
  c.id            AS course_id,
  c.title         AS course_title,
  c.level_code,
  c.total_lessons
FROM access_codes ac
JOIN courses c ON ac.course_id = c.id
WHERE ac.status_code = 'active'
  AND ac.course_id IS NOT NULL
  AND ac.user_id = '${studentId}'
  AND (ac.usage_end_date IS NULL OR ac.usage_end_date > NOW())
  AND c.deleted_at IS NULL

UNION

-- ② 나만의 수업 (custom 과정, 기존 로직 유지)
SELECT
  c.id            AS course_id,
  c.title         AS course_title,
  c.level_code,
  c.total_lessons
FROM courses c
WHERE c.created_by = '${studentId}'
  AND c.genre_code = 'custom'
  AND c.deleted_at IS NULL

ORDER BY course_title
```

### 변경 시 주의사항

- Phase E-1(status_code 마이그레이션)이 **반드시 선행**되어야 합니다.  
  마이그레이션 전에 쿼리만 교체하면 기존 INTERNAL 수강자의 과정이 조회되지 않습니다.
- `source_type` 컬럼이 삭제되므로 쿼리에서 해당 조건을 제거합니다.
- `usage_end_date` 만료 체크를 쿼리 조건에 포함합니다.
  만료된 코드(`usage_end_date < NOW()`)는 수강목록에서 제외됩니다.
  백오피스에서도 동일한 조회 시점 계산 방식을 사용합니다
  (참고: `packages/core/src/access-code/access-code.service.ts` `effectiveStatus()`).

### Prisma 스키마 동기화

백오피스 Phase A에서 테이블/컬럼 DROP이 이미 완료됐으므로 아래 명령으로 로컬 스키마를 동기화합니다.

```bash
pnpm --filter @tutoring/api prisma:pull
pnpm --filter @tutoring/api prisma:generate
```

## Phase E-3: `registerAccessCode()` 활성화 처리 수정

**파일**: `apps/api/src/lessons/lessons.service.ts` (line 738~)

### 현재 문제점

```typescript
// 현재 UPDATE (3가지 누락)
UPDATE access_codes
SET status_code = 'inactive',   -- ❌ 새 설계와 반대 (active여야 함)
    user_id = '${targetUserId}',
    updated_at = NOW()           -- activated_at, usage_start_date, usage_end_date 미설정
WHERE id = '${record.id}'
```

또한 "이미 사용된 코드" 판별 조건도 구 관례 기준:
```typescript
// 현재: inactive + user_id = 사용됨 (구 관례)
if (record.status_code === 'inactive' && record.user_id) { ... }
```

### 변경 내용

#### ① SELECT 쿼리에 필드 추가

```typescript
// 현재
SELECT id, code, status_code, course_id, user_id, institution_id

// 변경 후
SELECT id, code, status_code, course_id, user_id, institution_id,
       usage_period_days, usage_start_date, usage_end_date, registration_expiry
```

타입 정의도 함께 추가:
```typescript
{
  id: string;
  code: string;
  status_code: string;
  course_id: string | null;
  user_id: string | null;
  institution_id: string;
  usage_period_days: number;
  usage_start_date: Date | null;   // 추가
  usage_end_date: Date | null;     // 추가
  registration_expiry: Date;       // 추가
}[]
```

#### ② "이미 사용된 코드" 판별 조건 수정

```typescript
// 현재 (구 관례)
if (record.status_code === 'inactive' && record.user_id) { ... }

// 변경 후 (새 설계)
if (record.status_code === 'active') { ... }
```

#### ③ 등록 만료일 체크 추가 (신규)

```typescript
// 현재: 만료일 검사 없음
// 추가
if (new Date() > new Date(record.registration_expiry)) {
  throw new BadRequestException('액세스코드 등록 기간이 만료되었습니다.');
}
```

#### ④ UPDATE SQL 수정 — 활성화 처리 완전화

```sql
-- 변경 후
UPDATE access_codes
SET status_code     = 'active',
    user_id         = '${targetUserId}',
    activated_at    = NOW(),
    usage_start_date = COALESCE(usage_start_date, NOW()),
    usage_end_date   = COALESCE(usage_end_date,
                         NOW() + INTERVAL '${record.usage_period_days} days'),
    updated_at      = NOW()
WHERE id = '${record.id}'
```

> `COALESCE` 사용: 관리자가 백오피스에서 사전 설정한 날짜가 있으면 그대로 유지,  
> 없으면 등록 시점(NOW())을 기준으로 자동 계산.

### 실행 순서 제약

```
Phase E-1 (status_code 마이그레이션)
    ↓  반드시 선행
Phase E-3 (registerAccessCode 수정)
    ↓  이후 진행 가능
Phase E-2 (getEnrolledCourses 쿼리 교체)
```

Phase E-1 완료 전에 Phase E-3만 먼저 배포하면:
- 기존 등록 완료 코드(`inactive+user_id`)가 "사용 가능" 상태로 오인되어 중복 등록이 허용될 수 있음

| `usageEndDate` 만료 시 자동 status 변경 | ✅ 조회 시점 계산으로 구현 완료 — 백오피스 `effectiveStatus()`, Phase E-2 쿼리 조건(`usage_end_date > NOW()`)으로 처리. DB `status_code`는 변경하지 않음 |
