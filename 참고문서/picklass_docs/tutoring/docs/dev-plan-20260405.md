## 개발 규칙 (Development Rules)

### R1. Prisma ORM 전용 — Supabase API 사용 금지

- 모든 DB 접근은 **Prisma Client**를 통해서만 수행한다.
- Supabase JavaScript Client(`@supabase/supabase-js`)의 `supabase.from().select()` 등 **Supabase API 직접 호출 금지**.
- RLS(Row Level Security) 정책은 Supabase 대시보드에서 설정하되, 런타임 데이터 접근은 NestJS + Prisma `service_role` 기반.
- 마이그레이션: Prisma `migrate dev` 우선. Supabase 환경 제약 시 직접 SQL + `prisma generate`.

### R2. 타입 안전성 — `any` / `unknown` 사용 금지

- TypeScript `any` 타입 사용 금지. `@ts-ignore`, `@ts-expect-error` 사용 금지.
- `unknown` 타입 사용 금지. JSONB 필드 등 동적 데이터는 반드시 **구체적 인터페이스/타입을 정의**하여 사용.
- 공유 타입은 `packages/types/src/index.ts`에서 관리 (backoffice 기존 패턴 준수).
- Prisma 모델에서 `Json` 타입으로 정의된 필드(`questionData`, `contentConfig`, `skill_modules` 등)는 프론트/백엔드 양쪽에서 **동일한 TypeScript 인터페이스**로 캐스팅하여 사용.

### R3. NestJS 백엔드 아키텍처

- 모든 API는 NestJS Controller → Core Service → Prisma 3계층 구조로 구현.
- 비즈니스 로직은 `packages/core`에 작성. `apps/*/backend`는 API Gateway 역할만.
- `packages/core` 수정 후 반드시 `pnpm run build` + 백엔드 재시작.
- 프론트엔드 API 호출 시 `fetchApi` 유틸리티 사용 필수 (backoffice 기존 패턴).

### R4. 어댑티브 화면 구성 — 핵심 설계 원칙

> **현재 16개 모듈은 물론, 아직 존재하지 않는 신규 모듈이 추가되더라도 백오피스에서 DB 등록만으로 튜터링 학습 화면이 자동 구성되어야 한다. 모듈별 전용 코드를 작성하지 않는 것이 기본 원칙.**

#### R4-1. 현재 하드코딩 문제점 분석

현재 코드에 3가지 레벨의 하드코딩이 존재한다:

| 레벨 | 위치 | 문제 |
|------|------|------|
| **어댑터 레지스트리** | `adapters/index.ts` | 모듈코드별 어댑터 클래스를 수동 매핑. 미등록 모듈은 PRD fallback |
| **어댑터 내부 Mock** | 각 `*Adapter.ts` | `fetchModuleData()`, `buildContentConfig()`, `buildPedagogyProfile()` 모두 하드코딩 |
| **UI 분기 하드코딩** | `LessonSession.tsx:161-192` | `moduleData.code === 'PWR'` / `=== 'SCN'`으로 특수 흐름 분기 |

#### R4-2. 목표 아키텍처: GenericAdapter + flowType 기반 화면 분기

**원칙 1: `ai_modules` 테이블 = Single Source of Truth**
- 40+ 필드가 모듈의 유일한 정의. 프론트엔드에 모듈별 하드코딩 금지.
- `contentConfig`(JSONB)로 UI 배치 정책, `questionData`(JSONB)로 문항 템플릿 관리.

**원칙 2: GenericAdapter — 모듈별 어댑터 파일 불필요**
- 현재 5개 어댑터(`PredictionAdapter`, `ShadowReadingAdapter` 등)가 각각 Mock 데이터 + `buildContentConfig()` + `buildPedagogyProfile()`을 하드코딩하고 있음.
- 이를 **`GenericAdapter` 1개**로 통합. 모든 데이터를 DB(`ai_modules` + `texts` + `module_questions`)에서 조회.

```
GenericAdapter (신규, 모든 모듈의 기본 어댑터)
  ├─ fetchModuleData(lessonId, moduleCode)
  │   → GET /api/lessons/:id/module-data?moduleCode=XXX
  │   → texts + module_questions + ai_modules 조인 결과 반환
  │
  ├─ buildContentConfig()
  │   → ai_modules.contentConfig JSONB 그대로 반환
  │
  ├─ buildPedagogyProfile()
  │   → ai_modules의 answerType, scoringMode, feedbackStyle, feedbackType,
  │     pedagogyInstruction, hintTypes, retryScope, inputLanguage,
  │     passageRole, questionMaxAttempts 필드에서 직접 구성
  │
  ├─ calculateScore(questions, answers)
  │   → ai_modules.scoringMode에 따라 분기:
  │     'exact' → 정답 비교 / 'holistic' → 내용 있으면 정답 / 'pronunciation' → 점수 평균
  │
  └─ buildKpis(questions, answers, pronunciationScores)
      → ai_modules.selectedKpiCodes + POST /api/agent/kpi/{moduleCode}
```

**원칙 3: flowType 기반 UI 분기 — 모듈코드 하드코딩 제거**
- 현재 `moduleData.code === 'PWR'` 같은 코드값 분기를 **`flowType` 필드**로 대체.
- `flowType`은 `ai_modules.contentConfig` JSONB 또는 별도 필드로 관리.

```
flowType 값        → UI 컴포넌트                           해당 모듈 예시
─────────────────────────────────────────────────────────────────────
'orchestrator'     → ModuleRunnerInner (표준 Orchestrator)  PRD, SHR, SWR, SKM, QAR, CLR, SUM 등 대부분
'step-workflow'    → ProcessWritingFlow (다단계 수동 흐름)   PWR
'timed-gate'       → ScanningGate → ModuleRunnerInner      SCN
```

변경 전 (하드코딩):
```typescript
if (moduleData.code === 'PWR') return <ProcessWritingFlow />;
if (moduleData.code === 'SCN') return <ScanningGate />;
return <ModuleRunnerInner />;
```

변경 후 (데이터 기반):
```typescript
const flowType = moduleData.flowType ?? 'orchestrator';
if (flowType === 'step-workflow') return <ProcessWritingFlow />;
if (flowType === 'timed-gate') return <ScanningGate><ModuleRunnerInner /></ScanningGate>;
return <ModuleRunnerInner />;
```

**원칙 4: answerType 기반 자동 패널 렌더링**
- `QuestionsPanel`은 이미 `question.type`으로 분기하여 MC/essay/short-text/sentence-write를 자동 렌더
- `VoiceQuestionPanel`은 `audio-record` 타입이면 자동 노출
- Orchestrator 규칙도 `answerType`별로 동작 (essay→holistic, audio→pronunciation, write→writing)
- **→ 기존 5종 answerType을 사용하는 신규 모듈은 코드 변경 0으로 화면 자동 구성**

**원칙 5: 커리큘럼 배치 자동 반영**
- `roles`, `passageExposure`, `cognitiveLevel`, `suitableLevelMin/Max`, `estimatedMinutesMin/Max`, `prerequisites`, `incompatibleWith` 등이 CurriculumPlannerAgent의 모듈 필터링·시퀀싱에 자동 반영.

**원칙 6: JSONB 필드의 타입 안전성**
- `questionData`, `contentConfig`, `skill_modules` 등 JSONB 필드는 R2 규칙에 따라 구체적 인터페이스를 정의하고, DB 조회 시 타입 캐스팅하여 사용.

#### R4-3. 16개 모듈 + 미래 모듈의 UI 패턴 분류

현재 QuestionsPanel이 지원하는 answerType(multiple-choice, essay, short-text, sentence-write, audio-record) + flowType(orchestrator, step-workflow, timed-gate)으로 **16개 중 12개는 커버 가능**하지만, Vocabulary 계열 4개는 완전히 다른 UI가 필요하다.

**→ 완벽한 어댑티브는 불가능. `uiTemplate` 구분 값을 도입한다.**

#### R4-4. `uiTemplate` 설계 — UI 레벨 템플릿 분류

`ai_modules` 테이블에 `uiTemplate` 필드를 추가(또는 `contentConfig` JSONB 내부)하여, 페이지 수준의 UI 구조를 결정한다.

| uiTemplate | UI 구조 | 해당 모듈 | QuestionsPanel 지원 |
|------------|--------|----------|-------------------|
| `passage-qa` | 지문 + 문항 패널 + 피드백 (표준 Orchestrator) | PRD, SKM, QAR, CLR, SUM, SXP | ✅ answerType으로 자동 분기 |
| `voice-practice` | 지문 + VoiceQuestionPanel + 피드백 | SHR, SHD, ORL, LR | ✅ audio-record면 자동 노출 |
| `sentence-writing` | 지문 + 영작 패널 + 피드백 | SWR | ✅ sentence-write면 자동 |
| `timed-reading` | 타이머 게이트 → 지문 숨김 → 문항 | SCN | ✅ ScanningGate 래퍼 |
| `step-workflow` | 다단계 수동 흐름 (Orchestrator 미사용) | PWR | ✅ ProcessWritingFlow |
| `vocab-card` | **카드 덱 UI** (플래시카드, 넘기기) | WRD, WSD | ❌ **신규 컴포넌트 필요** |
| `interactive-match` | **매칭/선택 UI** (이미지↔단어, 웹 연결) | IMG, WW | ❌ **신규 컴포넌트 필요** |
| `scenario-dialog` | **대화 시뮬레이션** (역할극, 턴제 대화) | SNR | ❌ **신규 컴포넌트 필요** |

**핵심 인사이트:**
- `passage-qa`, `voice-practice`, `sentence-writing`은 모두 `flowType=orchestrator`이지만 **QuestionsPanel 내부에서 `answerType`으로 자동 분기**되므로 사실상 같은 uiTemplate이다.
- 즉, `uiTemplate`은 **QuestionsPanel의 answerType 분기로 커버할 수 없는 경우에만** 새 값이 필요하다.

#### R4-5. 실제 필요한 `uiTemplate` 값 (최소 설계)

위 분석을 정리하면, 실제로 필요한 uiTemplate은 **5개**다:

```
uiTemplate 값          구현 컴포넌트                         커버 범위
──────────────────────────────────────────────────────────────────────
'standard'             ModuleRunnerInner                     PRD, SKM, QAR, CLR, SUM, SXP,
                       (Orchestrator + answerType 자동 분기)   SWR, SHR, SHD, ORL, LR
                                                             → 기존 answerType이면 DB 등록만으로 동작

'timed-gate'           ScanningGate → ModuleRunnerInner      SCN + 미래 타이머 기반 모듈

'step-workflow'        ProcessWritingFlow                    PWR + 미래 다단계 작문 모듈

'vocab-deck'           VocabDeckFlow (신규)                  WRD, WSD + 미래 어휘 카드 모듈

'interactive'          InteractiveFlow (신규)                IMG, WW, SNR + 미래 매칭/대화 모듈
```

#### R4-6. uiTemplate별 상세 설계

**`standard` (11개 모듈 커버) — 코드 변경 없이 DB 등록만으로 동작**

```
ModuleRunnerInner
  ├─ ContentPanel (passage: passageExposureMode에 따라 hidden/preview/full)
  ├─ QuestionsPanel (answerType에 따라 자동 분기)
  │   ├─ multiple-choice → A/B/C/D 버튼
  │   ├─ essay / short-text → textarea + 제출
  │   └─ sentence-write → 한글 안내 + 영작 textarea
  ├─ VoiceQuestionPanel (answerType=audio-record면 자동 노출)
  │   └─ 듣기 → 말하기 → 녹음듣기
  ├─ FeedbackPanel (feedbackType에 따라 자동 분기)
  │   ├─ correctness → 정오답 즉시 판정
  │   ├─ holistic → AI 홀리스틱 평가
  │   ├─ pronunciation → 발음 점수 + 재시도
  │   └─ writing → 영작 채점 + 다음 문항
  └─ AIQuestionPanel (항상 노출)
```

DB에서 읽는 값으로 자동 구성되는 항목:
- `answerType` → 어떤 문항 패널을 보여줄지
- `passageExposureMode` → 지문 노출 방식
- `scoringMode` → 정답 판정 방식
- `feedbackStyle` / `feedbackType` → 피드백 톤과 유형
- `pedagogyInstruction` → AI 시스템 프롬프트
- `hintTypes` → 힌트 제공 방식
- `questionMaxAttempts` → 재시도 횟수 제한
- `questionCount` → 단일/다중 문항

**`timed-gate` (SCN 등) — 코드 변경 없이 DB 등록만으로 동작**

```
ScanningGate (범용화)
  ├─ 읽기 전: 지문 노출 + "읽기 시작" 버튼
  ├─ 읽기 중: 타이머 표시 + "리딩 완료" 버튼
  ├─ 읽기 후: 지문 숨김 → ModuleRunnerInner (standard와 동일)
  └─ contentConfig에서 타이머 설정 읽기 (제한시간, 자동종료 여부 등)
```

**`step-workflow` (PWR 등) — Flow 컴포넌트 범용화 필요**

```
StepWorkflowFlow (ProcessWritingFlow 범용화)
  ├─ contentConfig.steps[] 배열에서 단계 정의 읽기
  │   예: [{ type: 'outline', label: 'Outlining' },
  │        { type: 'edit', label: 'Self-Check' },
  │        { type: 'edit', label: '1st Draft' },
  │        { type: 'final', label: 'Final Draft' }]
  ├─ StepIndicator (단계 수 자동 반영)
  └─ 각 단계별 UI는 step.type으로 분기
```

**`vocab-deck` (WRD, WSD 등) — 신규 컴포넌트 필요**

```
VocabDeckFlow (신규)
  ├─ 카드 덱 UI (넘기기/뒤집기 인터랙션)
  ├─ questionData에서 카드 데이터 읽기
  │   예: [{ front: 'commerce', back: '상업, 무역', audio?: 'url' }]
  ├─ answerType=audio-record면 발음 녹음 카드
  ├─ answerType=multiple-choice면 의미 선택 카드
  └─ 완료 시 Orchestrator completeModule 호출
```

**`interactive` (IMG, WW, SNR 등) — 신규 컴포넌트 필요**

```
InteractiveFlow (신규)
  ├─ contentConfig.interactiveType으로 세부 분기
  │   ├─ 'image-match' → 이미지↔단어 드래그앤드롭
  │   ├─ 'word-web' → 단어 네트워크 시각화 + 연결
  │   └─ 'dialog' → 턴제 대화 시뮬레이션
  ├─ questionData에서 인터랙션 데이터 읽기
  └─ 완료 시 Orchestrator completeModule 호출
```

#### R4-8. DB + 백오피스 변경 제안

**Prisma 스키마** — `ai_modules`에 `uiTemplate` 필드 추가:

```prisma
model AiModule {
  // ... 기존 필드 (기본 정보 탭1 영역에 배치)

  // ── UI 템플릿 (신규, 기본 정보 탭1) ──
  uiTemplate    String    @default("standard") @map("ui_template") @db.VarChar(30)
}
```

**코드관리 시드** — `code_groups`에 `UI_TEMPLATE` 그룹 추가:

| code | name | description |
|------|------|-------------|
| `standard` | 표준 (지문+문항+피드백) | Orchestrator 기반. answerType으로 문항 패널 자동 분기 |
| `timed-gate` | 타이머 읽기 | 읽기 시간 측정 후 지문 숨김 → 표준 문항 진행 |
| `step-workflow` | 단계별 작문 | Orchestrator 미사용. 다단계 수동 흐름 (예: Outlining→Draft→Final) |
| `vocab-deck` | 어휘 카드 | 플래시카드 덱 (넘기기/뒤집기) |
| `interactive` | 인터랙티브 | 매칭, 연결, 대화 시뮬레이션 |

**모듈 등록 페이지** — 탭1(기본 정보)에 `uiTemplate` select 추가:

```
[기본 정보 탭]
  ├─ Skill:       [select] ← code_groups SKILL에서 로드
  ├─ Module Code: [input]  ← 대문자 3자
  ├─ Module Name: [input]
  └─ UI Template: [select] ← code_groups UI_TEMPLATE에서 로드 (신규)
       └─ 선택지: 표준 / 타이머 읽기 / 단계별 작문 / 어휘 카드 / 인터랙티브
```

> 관리자가 모듈 등록 시 `uiTemplate`을 선택하면, 튜터링 앱이 해당 값에 맞는 UI를 자동 렌더링. 코드관리에서 새 `UI_TEMPLATE` 값을 추가하고, 튜터링에 해당 Flow 컴포넌트를 구현하면 신규 UI 패턴 확장 가능.

#### R4-9. 최종 UI 분기 코드 (목표)

```typescript
// LessonSession.tsx — 모듈코드 하드코딩 완전 제거
const uiTemplate = aiModuleData.uiTemplate ?? 'standard';

switch (uiTemplate) {
  case 'step-workflow':
    return <StepWorkflowFlow {...commonProps} />;
  case 'timed-gate':
    return <ScanningGate><ModuleRunnerInner {...commonProps} /></ScanningGate>;
  case 'vocab-deck':
    return <VocabDeckFlow {...commonProps} />;
  case 'interactive':
    return <InteractiveFlow {...commonProps} />;
  default: // 'standard'
    return <ModuleRunnerInner {...commonProps} />;
}
// → 신규 모듈이 기존 uiTemplate을 사용하면 이 코드 변경 불필요
// → 새로운 uiTemplate이 필요한 경우에만 case 1줄 + Flow 컴포넌트 추가
```

#### R4-4. 어댑터 레지스트리 전환 계획

```
현재: ADAPTER_REGISTRY = { PRD: new PredictionAdapter(), SHR: new ShadowReadingAdapter(), ... }
      getAdapter(code) → 수동 매핑 / 미등록 시 PRD fallback

목표: getAdapter(code, aiModuleData) → GenericAdapter(aiModuleData) 반환
      aiModuleData = DB에서 조회한 ai_modules 레코드
      GenericAdapter가 aiModuleData의 속성값으로 모든 메서드 동작
```

기존 어댑터 5개(`PredictionAdapter` 등)는 **GenericAdapter 안정화 후 삭제**. 전환 기간에는 기존 어댑터와 GenericAdapter를 병행 운영 가능.

```
 3. ruleRepeatWrongAnswer  — 2회+ 오답 (essay/audio/write 제외) → giveHint (레벨 상승)
 4. ruleHolisticFeedback   — essay 제출 직후 → giveFeedback(holistic)
 5. ruleRevealFullPassage  — PRD: 피드백 완료 후 지문 전체 공개
 6. [SHR-C] rulePronunciationFeedback — audio 제출 직후 → giveFeedback(pronunciation)
 7. [SWR-A] ruleWritingFeedback       — sentence-write 제출 직후 → giveFeedback(writing)
 8. ruleWrongAnswerFeedback — 객관식 첫 오답 → giveFeedback(correctness)
 9. ruleCompleteAfterCelebrate — celebrate 후 → completeModule or signalReplan
10. [SHR-A] rulePlayModelAudio       — 미재생 오디오 → playModelAudio
11. [SHR-B] ruleStartRecordingAfterAudio — 재생 완료 → startRecording
12. ruleCorrectAnswer       — 정답 → 다음 문항 or celebrate
13. ruleInitialEntry        — 첫 진입 → showPassage(greeting)
14. rulePresentNextQuestion — fallback → 미답변 문항 제시
```

> **R4 어댑티브 동작**: 규칙은 `answerType`별 분기로 동작하므로, 기존 5종 answerType(essay/audio-record/sentence-write/multiple-choice/short-text)을 사용하는 **신규 모듈은 Orchestrator 코드 변경 없이 자동 적용**. 예: 백오피스에서 `QAR` 모듈을 `answerType=multiple-choice`로 등록하면, ruleCorrectAnswer(정답 비교) + ruleWrongAnswerFeedback(오답 피드백) + ruleRepeatWrongAnswer(힌트 상승)이 자동 적용됨. `pedagogyInstruction`에 모듈 고유의 교수법 지시문을 입력하면 AI 피드백 톤이 자동 반영.

```
[백오피스 관리자] (picklass-backoffice)
  ├─ 코드관리 페이지: code_groups/code_items CRUD (선택지 관리)
  ├─ 모듈 등록 페이지: ai_modules 생성/수정
  │   └─ contentConfig (JSONB), questionData (JSONB) 포함
  └─ 시드 데이터: 16개 모듈 초기 데이터

[교사 스튜디오] (studio.picklass.com)
  ├─ 지문 관리: texts 생성/수정 (AI 생성 or 직접 입력)
  ├─ 과정 관리: courses 생성 → course_lessons (레슨 편집, skill_modules 설정)
  ├─ 클래스 관리: classes 생성 → class_students (학생 배정)
  └─ TTS 캐시: tts_cache (음성 파일 캐시)
       ↓
[PostgreSQL DB (Supabase)] — 동일 DB 공유
  ├─ ai_modules (모듈 마스터) ← backoffice 관리
  ├─ code_groups / code_items (공통 코드) ← backoffice 관리
  ├─ texts (지문) ← studio 관리
  ├─ courses (과정) ← studio 관리
  ├─ course_lessons (레슨 플랜) ← studio 관리
  ├─ classes / class_students (클래스·학생 배정) ← studio 관리
  ├─ tts_cache (TTS 캐시) ← studio 관리
  ├─ module_questions (지문별 문항) ← 신규
  ├─ module_histories (모듈 상세 이력) ← 신규
  └─ student_learning_records (학습 기록 집계) ← studio 기존
       ↓
[tutoring 앱 - 학습 실행] (tutoring.picklass.com)
  ├─ fetchLessonPlan(lessonId)
  │   → course_lessons JOIN texts JOIN ai_modules
  │   → skill_modules(JSONB)에서 moduleSequence 조회
  ├─ ai_modules.uiTemplate로 UI 분기 결정
  │   → 'standard' → ModuleRunnerInner (대부분)
  │   → 'timed-gate' → ScanningGate → ModuleRunnerInner
  │   → 'step-workflow' → StepWorkflowFlow
  │   → 'vocab-deck' → VocabDeckFlow
  │   → 'interactive' → InteractiveFlow
  ├─ GenericAdapter.fetchModuleData()
  │   → texts + module_questions 조회
  │   → ai_modules.contentConfig로 UI 배치, answerType으로 문항 패널 자동 결정
  ├─ ModuleOrchestratorAgent.decideNextAction()
  │   → ai_modules.pedagogyInstruction, scoringMode, feedbackStyle 참조
  ├─ playModelAudio()
  │   → tts_cache 조회 (캐시 히트 시 파일 재생)
  └─ saveModuleHistory()
      → module_histories 저장
      → student_learning_records 집계 업데이트
```

## 8. 리스크 & 주의사항

| 리스크 | 대응 |
|--------|------|
| AiModule의 `questionData`(JSONB) ↔ `module_questions` 테이블 이중 관리 | `questionData`는 모듈 템플릿(문항 메타), `module_questions`는 지문별 실제 문항으로 역할 분리 |
| 3개 프로젝트 DB 동일 여부 | 동일 Supabase PostgreSQL 확인 필수 — backoffice(`ai_modules`, `code_groups/items`, `users`), studio(`texts`, `courses`, `course_lessons`, `classes`, `tts_cache`), tutoring(`module_questions`, `module_histories`) 모두 같은 DB |
| `texts.id`가 SERIAL(INT) vs UUID | `module_questions.text_id`는 INT FK. 기획서의 UUID 기반 설계와 다름. studio 기존 스키마에 맞춰 INT 사용 |
| `course_lessons.skill_modules` JSONB 구조 확정 | studio에서 이미 사용 중인 구조 확인 후 tutoring의 `PlannedModule[]`과 호환되도록 조율 |
| KPI 그룹코드 불일치 | 코드관리는 `KPI_CATEGORY`, 등록페이지는 `KPI_ITEMS` 혼용 중 → `KPI_CATEGORY`로 통일 |
| Supabase 환경 마이그레이션 제약 | `prisma migrate dev` 불가 → 직접 SQL 실행 + `prisma generate` |
| Claude API 비용 | Haiku 우선 사용 (Orchestrator), 피드백만 Sonnet, 캐싱 전략 적용 |
| 프론트 stale closure | 비동기 API 콜백 내 `xxxRef.current` 패턴 유지 필수 |
| Rule-based → LLM 전환 시점 | 마일스톤 3 완료 후 A/B 비교 시작 (기획서 Phase 2, 2026 Q3) |
| `contentConfig` JSONB 구조 불일치 | tutoring의 `ai-module.ts` 타입과 백오피스 저장 형식 일치 확인 필수 |
| Core 빌드 누락 | `packages/core` 수정 후 반드시 `pnpm run build` + 백엔드 재시작 |

## 9. 요약 타임라인

```
Day 1~3:  마일스톤 0 — 백오피스 잔여 (uiTemplate 필드 + 선택지 이관)
```
