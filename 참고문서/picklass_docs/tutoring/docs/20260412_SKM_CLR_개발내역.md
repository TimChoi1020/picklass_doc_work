#### 3-2. SentenceExplainPopover 컴포넌트

**파일**: `tutoring/src/app/modules/[lessonId]/_components/panels.tsx`

- 클릭된 문장이 속한 단락 바로 아래 인라인으로 렌더링 (플로팅 X)
- **기본 상태**: 해석만 표시 (원문은 지문에서 이미 보이므로 중복 제거)
- **상세설명 버튼**: 클릭 시 문법 + 주요표현 토글 확장 (`ChevronDown` / `ChevronUp`)
- **질문하기 버튼**: 팝오버 닫고 AI 채팅에 자동 프롬프트 submit
- **닫기 버튼**
- 문법/주요표현 데이터 없으면 상세설명 버튼 미표시

```
[기본]  해석 | [상세설명↓] [질문하기] [닫기]
[확장]  해석
        ─────────────
        📐 문법: ...
        💡 주요표현: 칩1 칩2 칩3
        | [간략히↑] [질문하기] [닫기]
```

**플로팅 미채택 이유**: 줄바꿈 span rect 계산 복잡도, overflow 컨테이너 클리핑, 모바일 가변 패널 높이 충돌, 스크롤 동기화 등 문제

#### 3-5. GenericAdapter 파싱

**파일**: `tutoring/src/lib/adapters/GenericAdapter.ts`

**최종 결정**: `options` 필드(JSONB)에 JSON 객체로 저장

```json
{
  "해석": "국문 해석 텍스트",
  "문법설명": "문법 구조 설명",
  "주요표현": ["표현1: 설명", "표현2: 설명"]
}
```

**채택 이유**:
- `options`는 이미 `JsonB?` 타입 → DB 스키마 변경 불필요
- `answer` 필드를 비워두면 LLM 출력 템플릿의 `"answer": "정답"` 설명과 충돌 없음
- JSON 직접 파싱으로 정규식 불필요, 가장 단순한 파싱

```typescript
const data = q.options as { 해석?: string; 문법설명?: string; 주요표현?: string[] };
explanation = {
  해석: data.해석 ?? '',
  문법: data.문법설명 ?? '',
  주요표현: Array.isArray(data.주요표현) ? data.주요표현 : [],
};
```

**변천 과정** (오늘 시행착오):
1. 최초: `hint`에 JSON 문자열 → LLM이 JSON 이스케이프 불안정
2. 2차: `answer`에 해석, `hint`에 문법+주요표현 구조화 텍스트 → LLM 템플릿(`"answer": "정답"`) 충돌로 해석 미생성
3. **최종**: `options`에 JSON 객체 → LLM 템플릿 충돌 없음, 파싱 단순

#### 3-6. question-generation.ts CLR 전용 JSON 템플릿

**파일**: `tutoring/apps/api/src/ai/prompts/question-generation.ts`

`answerType === 'sentence-explain'`일 때 `[출력 형식]` 블록을 CLR 전용으로 분기:

```typescript
${params.answerType === 'sentence-explain' ? `{
  "questions": [{
    "text": "지문 원문 문장 (절대 수정 금지)",
    "options": { "해석": "...", "문법설명": "...", "주요표현": ["..."] },
    "answer": "",
    "hint": null
  }]
}` : `{ /* 일반 문항 형식 */ }`}
```

**배경**: 공통 템플릿의 `"options": ["A. ...", "B. ..."]` 설명이 CLR의 JSON 객체 형식과 충돌하여 LLM이 잘못된 형식으로 생성하던 문제 수정.

#### 3-7. seed.ts CLR 모듈 설정

**파일**: `picklass-backoffice/prisma/seed.ts`

```typescript
{
  code: 'CLR',
  answerType: 'sentence-explain',
  feedbackStyle: 'sentence-explain',
  scoringMode: 'holistic',
  passageMode: 'full',
  questionGenerationStrategy: 'extract',
  questionMinCount: 5,
  questionMaxCount: 20,
  contentGenerationInstruction: `...`,  // 아래 참조
  pedagogyInstruction: `...`,
}
```

**contentGenerationInstruction 최종 형식**:
- 1문장 = 1레코드 (지문 전체 문장 수만큼 반복)
- `text`: 지문 영어 원문 (프론트 매칭용, 절대 수정 금지)
- `options`: `{"해석": "...", "문법설명": "...", "주요표현": [...]}`
- 레벨별 어휘 수준 및 문법설명 깊이 가이드 포함 (Lv.1~18)

#### 3-8. 오케스트레이터 CLR 가드

**파일**: `tutoring/src/lib/agents/orchestrator/ModuleOrchestratorAgent.ts`

CLR은 학생이 답안을 제출하지 않으므로 오케스트레이터 간섭 방지:

| 룰 | 가드 |
|----|------|
| `ruleHolisticFeedback` | `answerType === 'sentence-explain'` → null 반환 |
| `ruleCompleteAfterCelebrate` | 동일 |
| `rulePresentNextQuestion` | 동일 |
| `ruleClrIdle` | CLR 전용 — greetingShown 이후 null 반환 (오케스트레이터 무동작) |

#### 3-9. 오케스트레이터 null 에러 수정

**파일**: 
- `tutoring/src/lib/agents/orchestrator/ModuleOrchestratorAgent.ts`
- `tutoring/src/lib/hooks/useModuleOrchestrator.ts`

**원인**: CLR에서 모든 규칙이 null 반환 → `!` 단언으로도 null이 `executeToolCall`에 전달됨 → `Cannot read properties of null (reading 'tool')`

**수정**:
- `decideNextAction` 반환 타입: `Promise<OrchestratorToolCall>` → `Promise<OrchestratorToolCall | null>`
- `orchestrate()`: `if (!toolCall) return;` null 가드 추가
- `!` 단언 제거

## 주요 설계 결정 기록

| 결정 | 선택 | 이유 |
|------|------|------|
| CLR 해설 저장 위치 | `options` JSONB | `answer`는 LLM 템플릿 충돌, `hint`는 텍스트 파싱 불안정 |
| CLR 팝오버 위치 | 인라인 (단락 아래 DOM 삽입) | 플로팅은 스크롤 동기화·overflow 클리핑·모바일 패널 충돌 문제 |

| CLR 완료 기준 | `passage.content` 파싱 기준 문장 수 80% | `questions.length` 기준 시 최초 진입(questions 1개)에 즉시 완료 버그 |
