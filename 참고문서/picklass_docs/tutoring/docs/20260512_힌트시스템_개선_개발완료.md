# 힌트 시스템 개선 개발완료

> 최초 작성일: 2026-04-26 | 최종 업데이트: 2026-05-12
> 대상 프로젝트: tutoring.picklass.com
> 관련 모듈: WRD, WSD, GMN, SCN, SKM, PRD, SUM, QAR, CLR, SWR, PWR, RRD, SHR

---

## 1. 설계 원칙

### 1-1. 힌트 생성 시점 — Eager (문항 생성 시 동시 생성)

```
모듈 진입 → Gemini: 문항 + hints 동시 생성 → module_questions 저장
힌트 요청 → module_questions에서 즉시 반환 (API 0회)
```

**Lazy 생성을 채택하지 않은 이유:**
- 힌트 사용 빈도가 높은 모듈(WRD, GMN 등)은 Eager가 더 비용 효율적
- Lazy는 첫 번째 요청자에게 LLM 응답 지연이 발생
- 결국 두 방식 모두 1회 API 호출 후 캐시 — 차이는 타이밍뿐

### 1-2. 힌트 데이터 구조 — module_questions 단일 테이블로 완결

| 필드 | 레벨 | 내용 |
|---|---|---|
| `hints.button` | Level 0 | 학습자가 버튼 클릭 시 표시하는 힌트 텍스트 |
| `hints.direct` | Level 1 | 오답 누적 시 자동 표시되는 직접 힌트 |
| `answer` | Level 2 | 정답 제시 (`revealAnswer`) |

별도 힌트 생성 API(`/ai/hint`) 호출 불필요. 모든 힌트 데이터는 문항 생성 시 함께 생성되어 `module_questions`에 저장되므로 런타임에서 추가 LLM 호출 없이 처리 가능.

### 1-3. 학습자 주도 힌트

자동 힌트 발화(`ruleIdleHint`) 대신 학습자가 스스로 버튼을 누르도록 유도한다.

**교육학적 근거:**
- **바람직한 어려움(Desirable Difficulties)**: 적절한 어려움은 장기 기억 형성에 도움
- **인출 연습 효과(Testing Effect)**: 스스로 답을 끌어내려는 시도 자체가 학습
- **메타인지 훈련**: "나는 지금 막혀있다"를 스스로 인식하고 도움을 요청하는 과정이 학습

## 2. 힌트 발동 흐름 (최종)

```
[Level 0] 학습자 버튼 클릭
  → ruleOfferHint가 FeedbackPanel AI 메세지에 인라인 버튼으로 안내
  → 학생이 버튼 클릭 → handleHintButtonClick(questionId, hints.button)
  → "💡 힌트: {hints.button}" AI 메시지 표시
  → hintButtonUsedIds에 questionId 기록

[Level 1] ruleRepeatWrongAnswer 발동 (b-2start)
  조건: questionMaxAttempts >= 2 + 정오답 모듈 + 오답 1회
  → giveHint { staticHint: hints.direct }
  → "아쉽게도 틀렸어요. 다시 한 번 생각해볼게요 💡\n\n힌트: {hints.direct}" 표시

[Level 2] ruleRepeatWrongAnswer → revealAnswer 발동 (d / d-end)
  조건: 오답 2회 이상
  → answer 필드 기반 정답 제시 후 강제 완료
```

### 힌트 버튼 위치 — FeedbackPanel 인라인 (2026-05-12 변경)

힌트 버튼은 `questionFlowMode`와 무관하게 FeedbackPanel의 AI 안내 메세지(`ruleOfferHint`)에 인라인으로 표시된다. QuestionsPanel에는 힌트 버튼 없음.

```
ruleOfferHint 발화
  → postAiMessage(안내 텍스트, { hintOffer: { questionId, buttonHint } })
  → FeedbackPanel 메세지 버블 하단에 "💡 힌트 보기" 버튼 렌더링
  → 클릭 시 handleHintButtonClick → hintButtonUsedIds 기록 → 버튼 숨김
```

## 3. 피드백 케이스 프레임워크

한 문항에 대한 피드백은 5가지 케이스로 구분된다.

| 케이스 | 조건 | 메세지 |
|---|---|---|
| **a** | 1차 정답, 문항 더 있음 | `잘했어요! 이제 Q${n}번 차례예요.` |
| **a-end** | 1차 정답, 마지막 문항 | celebrate 메세지 |
| **b-end** | 오답 + maxAttempts=1 | `아쉽네요! Q${n}번을 틀렸어요.` |
| **b-2start** | 오답 + maxAttempts=2, 1차 오답 | `아쉽게도 틀렸어요. 다시 한 번 생각해볼게요 💡\n\n힌트: [hint]` |
| **c** | 2차 정답, 문항 더 있음 | `이번엔 맞혔어요! ✅ Q${n}번으로 넘어가볼게요.` |
| **c-end** | 2차 정답, 마지막 문항 | celebrate 메세지 |
| **d** | 2차 오답, 문항 더 있음 | `이번엔 아쉬웠어요. 정답은 "X"예요. 다음 문항에서 만회해봐요! 💪` |
| **d-end** | 2차 오답, 마지막 문항 | `이번엔 아쉬웠어요. 정답은 "X"예요. 수고했어요! 🙏` |

**c 케이스 구분 방법**: `ruleCorrectAnswer`에서 `state.attemptHistory[lastId]?.length > 1` 확인

## 4. 모듈별 힌트 적합성

| 모듈 | 목적 | 힌트 적합성 |
|---|---|---|
| WRD / WSD | 철자·발음 기억 | 적절 — 명확한 정답, 반복 연습이 목적 |
| SCN / QAR | 정보 탐색·추론 | 가능 — 오답 후 유예를 두고 제공 |
| GMN | 어휘 의미 유추 | 가능 — 단계적 힌트 유효 |
| PRD / SKM / SUM | 예측·훑기·요약 | 부적절 — 정답이 없으므로 힌트 개념 자체가 맞지 않음 |
| CLR / SWR / PWR | 이해·영작·글쓰기 | holistic 평가 → 피드백이 더 적합, 힌트 불필요 |

힌트 활성화 여부는 백오피스 `ai_modules.hint_types` 설정으로 제어. `['none']`이면 힌트 버튼 미표시.

- `POST /ai/hint/generate` (신규): on-demand 힌트 생성 + DB 저장 엔드포인트

### Phase 3 — Hook 변경 ✅

**`apps/web/src/lib/hooks/useModuleOrchestrator.ts`**

- `postAiMessage`: `hintOffer?: { questionId, buttonHint }` 옵션 파라미터 추가
- `offerHint` 케이스: `input.questions`에서 `hints.button` 조회 후 메세지 메타데이터로 첨부
- `giveHint` 케이스 (b-2start):
  - staticHint: `"아쉽게도 틀렸어요. 다시 한 번 생각해볼게요 💡\n\n힌트: ${hint}"`
  - on-demand: 동일 포맷 적용
- `revealAnswer` 케이스:
  - 마지막 문항 여부(`answeredCount === questions.length - 1`) 판단
  - d: `"이번엔 아쉬웠어요. 정답은 "X"예요. 다음 문항에서 만회해봐요! 💪"`
  - d-end: `"이번엔 아쉬웠어요. 정답은 "X"예요. 수고했어요! 🙏"`
- `hintButtonUsedIds`, `handleHintButtonClick`: FeedbackPanel로 전달 대상 변경 (QuestionsPanel에서 제거)
- **인사 메세지 개선**:
  - 프롬프트: `"인사말이나 자기소개 없이, 지금 이 활동에서 학생이 무엇을 할지 한 문장으로만 안내해 주세요."`
  - `passageContent` 슬라이스: 500자 → 300자
  - 타이밍 재구성: LLM 응답 이후 다음 오케스트레이트 실행 (순서 보장), 두 메세지 간 최소 600ms 간격

## 6. 폐기된 계획

| 항목 | 폐기 사유 |
|---|---|
| Lazy 힌트 생성 (클릭 시 LLM 호출) | Eager 생성이 비용·UX 모두 유리. module_questions에 이미 저장됨 |
| `/ai/hint` API 런타임 호출 | module_questions의 hints.button/direct로 완전 대체 |
| `questionAnswer` API payload 전송 | API 호출 제거로 자동 해결 (정답 노출 위험 없음) |
| `hintTypes[]` → 단일값 변경 | API 제거로 불필요 |
| `hintLevels` 상태 관리 | hints.button/direct 두 단계 + revealAnswer로 충분 |
| `explicit` 3단계 힌트 | revealAnswer가 동일 역할 수행 |
| QuestionsPanel 힌트 버튼 | FeedbackPanel 인라인 버튼으로 통합 (2026-05-12) |
| `correctness` 타입 `/ai/hint/generate` on-demand | 피드백 케이스 A 템플릿으로 대체 |
