## 7. "다시 설명해주세요" 버튼 제거 및 AI 자유질문 유도

### 배경

피드백 후 "이해했어요 / 다시 설명해주세요" 두 버튼을 표시했으나:
- "다시 설명해주세요" 클릭 시 모듈이 종료되는 버그 발생 (후술)

```typescript
// 버그: 텍스트 무관 confirmFeedback 호출
onQuickReply={confirmFeedback}

// 임시 수정 (이후 버튼 제거로 단순화):
onQuickReply={(text) => text === '이해했어요' ? confirmFeedback() : submitUserMessage(text)}
```

## 8. timed-then-blur 모드 Blur 처리 수정

### 버그 상세

Scanning 등 `passageMode: 'timed-then-blur'` 모듈에서 읽기 완료 버튼 클릭 시 지문이 Blur가 아닌 Preview(2문장)로 바뀌는 오작동.

### 원인 분석

```
usePassageMode → passageVisibleOverride = false (done 상태)
    ↓
ModuleRunnerInner → previewOnly={!passageVisible || ...} = true
    ↓
ContentPanel → previewOnly=true → 2문장 preview 표시 (blur 아님)
```

`passageVisible=false`가 `previewOnly=true`로 연결되는 로직 문제.

### 해결: blurActive 플래그 분리

`passageVisibleOverride`는 항상 `true` 유지, `blurActive` 플래그를 별도 반환하여 `ContentPanel`의 `exposureMode="blurred"`로 직접 전달.

```
done + 미제출 → passageVisible = true (지문 패널 유지)
               + blurActive = true → exposureMode="blurred" → CSS blur 처리
done + 제출   → blurActive = false → 지문 정상 표시
```

### 수정 파일

#### `apps/web/src/app/modules/[lessonId]/_components/LessonSession.tsx`
```typescript
// usePassageMode 수정
if (passageMode === 'timed-then-blur') {
  const blurActive = readingPhase === 'done' && !firstAnswerSubmitted;
  return { passageVisibleOverride: true, floatingTimer, blurActive, contentPanelFooter: undefined };
}

// ContentPanel 전달
<ContentPanel
  ...
  exposureMode={blurActive ? 'blurred' : undefined}
/>

// MobileSplitLayout 전달
<MobileSplitLayout
  ...
  passageBlurActive={blurActive}
/>
```

#### `apps/web/src/app/modules/[lessonId]/_components/MobileSplitLayout.tsx`
```typescript
// prop 타입 추가
passageBlurActive?: boolean;

// ContentPanel 전달
<ContentPanel
  ...
  exposureMode={passageBlurActive ? 'blurred' : undefined}
/>
```

> **참고:** `ContentPanel`의 `exposureMode="blurred"` 렌더링 로직은 기존에 이미 구현되어 있었음. 단순히 연결 경로가 없었던 문제.

## 9. greet 툴 독립 분리 — passageExposureMode 무관 인사 보장

### 배경

`passageExposureMode: 'hidden'` 모듈(SCN, WRD 등)은 `showPassage`가 스킵되어 피드백 패널에 모듈 목적/인사 메시지가 전혀 표시되지 않는 문제.

### 근본 원인

`greeting`이 `showPassage` 툴 파라미터에 종속되어 있어, 지문을 표시하지 않는 모듈은 인사도 함께 생략됨.

### 해결 방향

`greet` 툴을 독립 분리하여 **Rule 0**으로 모든 모듈에서 항상 1회 발화 보장.

```
Rule 0: ruleGreet       → greet 툴 (모든 모듈, 항상 첫 번째)
Rule 7: ruleInitialEntry → showPassage 툴 (지문 표시만, greeting 제거)
```

### 수정 파일

#### `apps/web/src/lib/agents/agent-types.ts`

**OrchestratorToolCall 유니온에 greet 추가:**
```typescript
| ({
    tool: 'greet';
    params: {
      /** 모듈 목적 한 줄 요약 (pedagogyProfile.purpose). fallback 메시지로 사용 */
      purpose: string;
    };
  } & BaseToolCall)
```

**showPassage에서 greeting 파라미터 제거:**
```typescript
// 제거된 파라미터
greeting?: string;
```

**OrchestratorContext에 greetingShown 추가:**
```typescript
export interface OrchestratorContext {
  greetingShown: boolean; // 추가
  passageShown: boolean;
  ...
}
```

#### `apps/web/src/lib/agents/orchestrator/ModuleOrchestratorAgent.ts`

**ruleGreet 추가 (체인 맨 앞):**
```typescript
function ruleGreet(
  state: LearnerState,
  context: OrchestratorContext,
): OrchestratorToolCall | null {
  if (context.greetingShown) return null;
  if (Object.keys(state.answers).length > 0) return null;
  if (state.questionsAsked.length > 0) return null;

  return {
    tool: 'greet',
    params: { purpose: context.pedagogyProfile.purpose },
    reason: '첫 진입 — 모듈 인사 및 목적 안내',
```

### Orchestrator 규칙 추가 시 체크리스트

1. **중복 발화 방지**: `context.eventFiredIds` 또는 `context.feedbackGivenIds` ref 활용

### greet 툴 설계 원칙

- `greet`는 항상 Rule 0 — 어떤 모듈 타입이든 첫 번째로 발화
- `showPassage`는 지문 표시만 담당 (greeting 로직 없음)
- 새 모듈 추가 시 greeting 처리를 별도로 구현할 필요 없음

- `blurActive = true` → `ContentPanel`에 `exposureMode="blurred"` 전달
- `passageVisibleOverride`는 항상 `true` (지문 패널 자체는 유지)
- 답안 제출 후 `firstAnswerSubmitted = true` → `blurActive = false` → blur 자동 해제

### revealPassage 플래그

- `passageExposureMode: 'preview'` 모듈(PRD 등)에서만 실질적으로 동작
- Agent가 `giveFeedback` holistic 발화 시 `revealPassage: true` 포함하면 hook이 동시에 지문 공개
- 모듈별 특수 분기 없이 Agent 제어만으로 처리 가능

## 12. SKM/SCN Blur 상태 개선 — before 페이즈도 blur 처리

### 배경

기존에는 `readingPhase === 'done'`일 때만 blur가 적용되었으나, 모듈 시작 직후(`before` 페이즈)에도 지문이 그대로 노출되는 문제. SKM/SCN의 핵심 컨셉은 **읽기 시작 전까지 지문을 보여주지 않는 것**.

### 수정 내용

#### `apps/web/src/app/modules/[lessonId]/_components/LessonSession.tsx`

```typescript
// 수정 전
const blurActive = readingPhase === 'done' && !firstAnswerSubmitted;

// 수정 후
// before: blur(읽기 전) | reading: 정상 표시 | done+미제출: blur 복원 | done+제출: blur 해제
const blurActive = readingPhase === 'before' || (readingPhase === 'done' && !firstAnswerSubmitted);
```

### 동작 흐름

| 페이즈 | blurActive | 설명 |
|--------|------------|------|
| `before` | `true` | 모듈 시작 → 지문 blur |
| `reading` | `false` | "지문읽기" 클릭 → 지문 공개 |
| `done` + 미제출 | `true` | "읽기완료" 클릭 → blur 복원 |
| `done` + 제출 | `false` | 답안 제출 후 → blur 해제 |

## 13. Floating Timer 단계별 UI 재설계 — overlay / header 분리

### 배경

기존 Floating Timer(우측 하단)가 `before` 페이즈에서 지문 위에 떠 있어 지문 일부를 가리는 문제. `before` 페이즈에서는 어차피 지문이 blur되어 있으므로 전체 overlay로 대체하는 것이 더 자연스러운 UX.

### 재설계 방향

| 페이즈 | 이전 | 변경 후 |
|--------|------|---------|
| `before` | 우측 하단 floating 버튼 | 패널 전체 overlay (중앙 버튼) |
| `reading` | 우측 하단 floating (타이머+완료) | 헤더 우측 inline (타이머+완료) |
| `done` | 미표시 | 미표시 (동일) |

### 수정 파일

## 15. HOLISTIC_TYPES 상수화 — keyword-chips LLM 피드백 누락 수정

### 버그

`keyword-chips` 타입 문항 제출 시 LLM 피드백이 발화되지 않고 곧바로 모듈 완료 처리되는 현상.

### 원인

`ModuleOrchestratorAgent.ts`의 holistic 타입 체크가 `essay | short-text`만 포함하고 `keyword-chips`를 누락:

```typescript

```

총 6곳(calcScore, ruleHintForWrongAnswer, ruleHolisticFeedback, ruleCorrectAnswer×2, ruleCompleteAfterCelebrate)에 동일 패턴 반복.

### 해결: HOLISTIC_TYPES 상수 + isHolisticType 헬퍼

#### `apps/web/src/lib/agents/orchestrator/ModuleOrchestratorAgent.ts`

```typescript
// 파일 상단에 추가
const HOLISTIC_TYPES = ['essay', 'short-text', 'keyword-chips'] as const;

function isHolisticType(type: string): boolean {
  return (HOLISTIC_TYPES as readonly string[]).includes(type);
}
```

6개 체크 포인트 모두 `isHolisticType(q.type)` 으로 교체:

```typescript
// 수정 후

```

## 16. Phase 1: 피드백 아키텍처 개선 — pedagogyInstruction 단일 소스화

### 배경 및 문제

기존 피드백 프롬프트는 `feedbackStyle` 값에 따라 **형식을 코드에서 강제**:
- `correct-wrong` → 정답/오답 형식
- `wpm-pronunciation` → WPM/발음 형식
- 기타 → 강점/개선점 2섹션 형식 (하드코딩)

`pedagogyInstruction`에 상세한 평가 지침을 작성해도 코드의 형식 강제가 우선하여 DB 설정이 무시되는 구조.

### 아키텍처 결정

**`pedagogyInstruction`을 피드백 형식·평가 기준·KPI의 단일 소스로 지정.**
- `feedbackStyle`은 LLM에 참고 힌트로만 전달 (형식 강제 없음)
- KPI 계산도 LLM이 raw 데이터(지문, 답안, 읽기 소요 시간)에서 직접 계산
- 모든 모듈이 동일한 코드 경로 사용, 동작 차이는 DB(pedagogyInstruction)로 제어

### 수정 파일

```typescript
[교수법 지시문 — 피드백 형식·평가 기준·KPI 모두 이 지시문을 따름]

}
```

### KPI 활용 방향 (추후 구현 예정)

DB에 `selectedKpiCodes`(성과KPI) 가 모듈별로 등록되어 있음. 이를 피드백에 활용하는 방안:

| 옵션 | 방법 | 장점 | 단점 |
|------|------|------|------|
| **A** | `selectedKpiCodes`를 피드백 API에 전달 | 구현 최소 | KPI 코드만으로 LLM이 해석해야 함 |
| **B** | KPI 메타데이터(이름/단위/측정방법)까지 전달 | LLM이 정확히 이해 | 백오피스 API 연결 필요 |
| **C** | 피드백 + KPI 평가 통합 1회 LLM 호출 | LLM 호출 절감 | 응답 구조 변경 필요 |

권장: **B 옵션** — `pedagogyInstruction`에 KPI 정의가 내포되는 현재 구조에서, KPI 코드+메타데이터를 별도 섹션으로 추가하면 LLM이 어떤 지표를 계산해야 하는지 명확히 파악 가능.
