# 수강 인원 · 배포 횟수 — 비정규화 컬럼 → 액세스코드 실시간 집계 전환

**작성일**: 2026-06-23
**대상**: picklass-backoffice (admin)
**범위**: 과정목록·과정상세의 **수강 인원 / 배포 횟수** 값 산출 방식 변경
**상태**: ✅ 구현 완료

## 1. 배경 — 검토 결과 (문제)

과정목록/상세의 **수강 인원(`studentCount`) / 배포 횟수(`deploymentCount`)**는 `courses` 테이블의 비정규화 컬럼(`student_count`/`deployment_count`, `@default(0)`)을 그대로 읽어 표시하고 있었다. 검토 결과:

- **코드 어디에서도 이 두 컬럼을 갱신(update)하지 않음** — `course.service.toResponse`에서 읽기만 함.
- 실제 DB 값(과정 39건 기준):
  - `studentCount`: **전부 0** (39/39, max 0) — 게다가 파생 후보였던 `classes`/`class_students`도 **0행**(원천 데이터 자체 부재).
  - `deploymentCount`: 29건 0 / 10건만 값 존재(max 4, 합 17) — 과거 1회 채워진 뒤 방치된 stale 값.
- 기존 문서(backoffice `docs/courses/20260520_콘텐츠관리_역할분리_개발완료.md`)는 배포 횟수를 "액세스코드 발급 수"로 정의했으나, 저장값(합 17)과 실제 액세스코드(75)가 불일치 → **정의대로 유지되지 않음**.

→ 두 값 모두 **유지 주체가 없는 비정규화 카운터**로, 화면에 오해를 유발하는 값(수강 인원 항상 "0명")을 노출하고 있었다.

---

## 2. 결정 — 액세스코드 기준 실시간 집계

비정규화 컬럼 읽기를 중단하고, **응답 시점에 `access_codes`를 실시간 집계**한다.

| 표시 항목 | 산출 기준 |
|-----------|-----------|
| **배포 횟수** `deploymentCount` | 해당 과정(`courseId`)에 연결된 액세스코드 **전체 수** |
| **수강 인원** `studentCount` | 그중 **활성화된**(= `statusCode = 'active'`) 액세스코드 수 |

- "활성화" 기준: 액세스코드 활성화 시 `statusCode → 'active'` + `activatedAt` 세팅(`access-code.service.ts`)되므로 `statusCode='active'`로 판정. 목록 화면의 "수강 중" 정의와 일관.
- `courseId`가 없는 액세스코드(기관 단위 발급분)는 어떤 과정에도 집계되지 않음(정상).

## 3. 구현

### 백엔드 — `packages/core/src/course/course.service.ts`

- `AccessCodeCounts` 타입 추가(`{ studentCount, deploymentCount }`).
- `resolveAccessCodeCounts(courseIds)` 추가 — **N+1 방지**를 위해 `accessCode.groupBy({ by: ['courseId'] })`를 전체/활성 2회 배치 조회 후 Map 구성.
- `toResponse(course, hierarchy?, counts?)` — `studentCount`/`deploymentCount`를 `counts`에서 채움(비정규화 컬럼 더 이상 읽지 않음, 미전달 시 0).
- `findAll`: 페이지 과정 id로 `resolveAccessCodeCounts` 호출 후 행별 전달.
- `findById`: 단건 과정 집계 후 전달(과정 상세 화면 반영).

### 프론트엔드

- **변경 없음**. `CourseResponse`의 `studentCount`/`deploymentCount` 필드를 그대로 사용하므로, 값만 실데이터로 바뀐다.
  - 과정목록 `app/(admin)/admin/courses/page.tsx` (목록·다운로드)
  - 과정상세 `app/(admin)/admin/courses/[id]/page.tsx`

### DB

- `courses.student_count` / `deployment_count` 컬럼은 **삭제하지 않고 보존**(마이그레이션 정책 준수). 단, API 응답 산출에서는 더 이상 사용하지 않는다.

## 4. 검증

- `@repo/core` build(tsc) 통과 — `groupBy` 사용 타입 정상.
- 읽기 전용 DB 대조(2026-06-23): 액세스코드 75개 = 과정연결 40 / 미연결 35, 과정연결 16건(활성 14건). 샘플에서 저장컬럼(stale) → 신규집계로 정정 확인(예: "식당에서 음식주문하기" 배포 0→1·수강 0→1).
- ⚠️ **런타임 반영**: `@repo/core` 변경 → 빌드 후 백엔드(admin backend) 재시작 필요(stale JS 방지).
