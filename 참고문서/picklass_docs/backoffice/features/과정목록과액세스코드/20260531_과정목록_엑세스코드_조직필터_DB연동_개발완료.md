## 0. 한눈에 보기

과정목록·엑세스코드 화면 상단의 **상위 파트너 / 상위 그룹 / 소속기관** 필터는 지금 "껍데기"입니다.
- 자유 입력 텍스트칸으로 만들어져 있고(코드에 `HARD` 뱃지로 표시됨),
- 입력해도 **실제로 백엔드로 전달되지 않아 검색이 안 됩니다.**
- 과정목록의 "파트너 / 그룹" 컬럼은 항상 `-`(하드코딩)로만 표시됩니다.

이걸 **계층 드롭다운(파트너 → 그룹 → 기관 순서로 좁혀지는 선택창)** 으로 바꾸고, 선택값을 백엔드로 보내 실제로 필터링되게 만드는 작업입니다.

> **좋은 소식**: 백엔드에 이미 필요한 재료가 대부분 있습니다(아래 §2). 그래서 새 테이블·새 API는 거의 필요 없고, "이미 있는 것을 이어붙이는" 작업이 중심입니다.

## 2. 이미 있는 재료 (재사용 — 신규 개발 최소화)

| 재료 | 위치 | 용도 |
|------|------|------|
| `GET /institutions` 필터 `type` · `parentId` · `partnerId` · `groupId` | `InstitutionQueryDto` (이미 존재) | **계층 드롭다운 옵션 로드** — 새 API 불필요 |
| `AuthUser.orgContext` (`UserOrgContext`) | `/auth/me` 응답에 이미 포함 | partnerId/groupId/institutionId·이름·`fixedLevel` → **역할별 잠금**에 사용(추가 호출 불필요) |
| 과정 `findAll`의 역할 스코프 | `course.service.ts` (line 30–65) | 이미 `institutionId in scope` 적용 중 — 여기에 "선택 필터"만 끼우면 됨 |
| 엑세스코드 `findAll(query, scope)` | `access-code.service.ts` | 이미 스코프 적용 중 |
| 기관 계층 재귀 조회 | `InstitutionService.resolveDescendants` | 선택한 파트너/그룹 → 하위 기관 id 집합 |

**핵심 설계 원칙**: 역할 스코프(내가 볼 수 있는 범위)와 사용자가 선택한 필터를 **교집합**으로 적용한다. (예: 파트너 관리자가 자기 파트너 밖을 조회 못 하게)

## 3. 목표 화면 동작 (역할별)

조직 계층: **파트너 > 그룹 > 기관(학원)**. 드롭다운은 왼쪽부터 선택하면 오른쪽 옵션이 좁혀지는 방식(cascading).

| 역할 | 상위 파트너 | 상위 그룹 | 소속 기관 |
|------|:----------:|:--------:|:--------:|
| system_admin | 선택 가능 (전체) | 파트너 선택 시 옵션 표시 | 그룹 선택 시 옵션 표시 |
| partner_admin | **고정**(본인 파트너) | 선택 가능 | 그룹 선택 시 표시 |
| group_admin | **고정** | **고정**(본인 그룹) | 선택 가능 |
| academy_admin | **고정** | **고정** | **고정**(본인 기관) |

- 고정 칸은 `orgContext` 값으로 채우고 비활성화(읽기 전용).
- 선택 가능한 칸의 옵션은 `GET /institutions?type=...&parentId=...` 로 로드.
- 최종적으로 화면은 선택된 **institutionId**(또는 partnerId/groupId)를 백엔드에 전달.

## 4. 작업 단계 (순서대로)

### Phase 1 — 백엔드·타입 (먼저: 이게 돼야 프론트가 의미 있음)

**1-A. 공용 스코프 해석 헬퍼** (`InstitutionService`)
- `resolveSelectionScope({ partnerId?, groupId?, institutionId? }): Promise<string[]>`
  - 가장 좁은 선택값 기준으로 `resolveDescendants` 호출 → 기관 id 집합 반환.
- `resolveHierarchyNames(institutionIds): Promise<Map<id, { partnerName, groupName, institutionName }>>`
  - 각 기관의 상위 그룹·상위 파트너 이름을 배치로 해석(과정/코드 목록 컬럼 표시용).
  - 참고: `auth.service.getOrgContext`가 이미 부모 2단계(`parent.parent`)를 거슬러 올라가는 로직을 갖고 있음 → 동일 패턴 재사용.

**1-B. 과정목록**
- `CourseQueryDto`에 `institutionId?` · `partnerId?` · `groupId?` 추가.
- `course.service.findAll`: 역할 스코프와 **선택 필터 스코프를 교집합** → `where.institutionId in (교집합)`.
- 과정 행 응답에 `partnerName` · `groupName` 추가(`resolveHierarchyNames` 사용).

**1-C. 엑세스코드 목록**
- `AccessCodeQueryDto`에 `partnerId?` · `groupId?` 추가(`institutionId`는 이미 있음).
- `access-code.service.findAll`: 동일하게 교집합 적용.
- `AccessCodeResponse`에 `partnerName` · `groupName` 추가(선택 — 컬럼 표시용).

### Phase 2 — 프론트 공용 컴포넌트
- `components/OrgFilter.tsx`(가칭) 신규: 파트너/그룹/기관 cascading 드롭다운.
  - `orgContext`로 고정 칸 잠금, 선택 가능 칸은 `getInstitutions({type, parentId})`로 옵션 로드.
  - 값 변경 시 `{ partnerId, groupId, institutionId }` 콜백.
  - 과정목록·엑세스코드 양쪽에서 공용 사용.

### Phase 3 — 과정목록 적용
- 자유 텍스트 3칸(`HARD`) → `OrgFilter`로 교체.
- `fetchCourses`에 선택 id 전달(line 88 TODO 해소).
- 파트너/그룹 컬럼을 행 데이터(`partnerName`/`groupName`)로 표시('-' 하드코딩 제거), 다운로드도 동일 반영.

### Phase 4 — 엑세스코드 목록 적용
- 자유 텍스트 3칸 + `getInstitution` 자동입력 → `orgContext` + `OrgFilter`로 교체.
- `getAccessCodes`에 선택 id 전달, group_admin 상위 파트너 자동세팅(line 85 TODO 해소).
- 컬럼에 파트너/그룹 표시(선택).

### Phase 5 — 통계 화면 적용 (과정목록과 동일 작업 반복)
- **기관 학습 현황** `stats/institutions/page.tsx`: 자유 텍스트 → `OrgFilter` 교체, `fetchSearchLearners`에 partnerId/groupId/institutionId 전달(line 305 `TODO[HARD]` 해소).
  - 백엔드 `institution-stats.service.searchLearners`: 선택 필터 교집합 적용(이미 역할 스코프는 있음).
- **출석률** `stats/attendance/page.tsx`: 동일하게 `OrgFilter` 교체 + 백엔드 `attendance.service` 선택 필터 적용.
- 두 화면 모두 Phase 1의 `resolveSelectionScope`와 Phase 2의 `OrgFilter`를 그대로 재사용 → 추가 신규 로직 거의 없음.

### Phase 6 — 엑세스코드 생성 (선택 → 완료)
- 기관 단일 셀렉트 앞에 파트너/그룹 cascading 추가.
- **구현 방식**: `OrgFilter`와 동일한 cascading 로직을 generate 페이지에 인라인 구현.
  - 목록 화면의 OrgFilter(필터용, 미선택 시 전체)와 달리 생성 화면은 **소속 기관이 필수값**이므로 별도 구현.
  - `partnerLocked`/`groupLocked`/`institutionLocked` 는 `orgContext.fixedLevel` 기준으로 동일 패턴 적용.
