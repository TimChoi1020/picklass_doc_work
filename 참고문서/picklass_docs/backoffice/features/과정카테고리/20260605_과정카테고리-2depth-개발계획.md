## 1. 배경 및 목표

backoffice에서 두 가지 역할을 수행한다.

1. **카테고리 구조 관리**: 파트너 단위 L1/L2 카테고리 생성·수정·삭제
2. **과정-카테고리 배정**: 파트너 소속 기관의 과정을 카테고리에 직접 배정

강사는 studio에서 배정할 수 있고, backoffice 관리자는 backoffice에서 배정할 수 있다. 두 경로 모두 동일한 `courses.l1_category_id` / `l2_category_id` 컬럼을 업데이트한다.

### 1.1 카테고리 용도

- 학습자 탐색: 과정 목록 필터·검색 기반
- B2B 리포트: 카테고리별 집계·분석 기반
- 과정 라이브러리 구조화: studio CourseSidebar 2-depth 폴더 UI

### 1.2 설계 원칙 — 파트너 단일 소유

카테고리는 **파트너가 소유하고 관리**한다. platform 공통 카테고리는 존재하지 않는다.

| 주체 | 카테고리 구조 관리 | 과정 배정 |
|------|-----------------|----------|
| 파트너 관리자 | 자기 파트너 L1/L2 생성·수정·삭제 | 자기 파트너 소속 과정 배정 |
| backoffice 관리자 | 모든 파트너 카테고리 열람·관리 | 모든 파트너 소속 과정 배정 |
| 기관 강사 (studio) | **없음** | 자기 기관 과정 배정 (studio에서) |

**파트너 없는 독립 기관**: 카테고리 사용 불가 — 과정 목록에서 카테고리 필터가 표시되지 않는다.

## 2. DB 설계

### 2.1 course_categories 테이블 신설

```sql
-- apps/api/prisma/manual-sql/2026-06-05_course_categories.sql
BEGIN;

CREATE TABLE course_categories (
  id            SERIAL PRIMARY KEY,
  partner_id    UUID NOT NULL REFERENCES institutions(id) ON DELETE CASCADE,  -- 소유 파트너
  depth         INT NOT NULL CHECK (depth IN (1, 2)),   -- 1=L1, 2=L2
  parent_id     INT REFERENCES course_categories(id),   -- L2면 L1 id, L1이면 NULL
  code          TEXT NOT NULL,             -- 식별 코드 (예: 'daily', 'business')
  label         TEXT NOT NULL,             -- 표시명 (예: '생활영어')
  label_en      TEXT,                      -- 영문 표시명 (선택)
  series_code   TEXT,                      -- L2 시리즈 묶기용 코드
  series_volume INT,                       -- L2 권호 (1, 2, 3 ...)
  sort_order    INT NOT NULL DEFAULT 0,
  is_active     BOOLEAN NOT NULL DEFAULT true,
  created_at    TIMESTAMPTZ DEFAULT NOW(),
  updated_at    TIMESTAMPTZ DEFAULT NOW()
);

-- 같은 파트너 내 코드 중복 방지
CREATE UNIQUE INDEX idx_course_categories_partner_code
  ON course_categories(partner_id, code) WHERE depth = 1;

CREATE INDEX idx_course_categories_partner ON course_categories(partner_id);
CREATE INDEX idx_course_categories_parent  ON course_categories(parent_id);

-- courses 테이블 카테고리 컬럼 추가
ALTER TABLE courses
  ADD COLUMN l1_category_id INT REFERENCES course_categories(id),
  ADD COLUMN l2_category_id INT REFERENCES course_categories(id);

CREATE INDEX idx_courses_l1_category ON courses(l1_category_id);
CREATE INDEX idx_courses_l2_category ON courses(l2_category_id);

COMMIT;
```

초기 seed 데이터 없음 — 각 파트너가 직접 카테고리를 생성한다.

## 3. API 설계

### 3.1 엔드포인트 목록

**카테고리 구조 관리**

| Method | Path | 설명 | 권한 |
|--------|------|------|------|
| `GET` | `/course-categories` | 카테고리 목록 조회 | 인증 필요 |
| `POST` | `/course-categories` | 카테고리 생성 | 관리자 |
| `PATCH` | `/course-categories/:id` | 카테고리 수정 | 관리자 |
| `DELETE` | `/course-categories/:id` | 카테고리 삭제 (소프트) | 관리자 |
| `PATCH` | `/course-categories/reorder` | 정렬 순서 일괄 변경 | 관리자 |

**과정 배정 (기존 courses API 확장)**

| Method | Path | 설명 | 권한 | 상태 |
|--------|------|------|------|------|
| `GET` | `/courses?partnerId=&l1_category_id=&l2_category_id=&unassigned=` | 카테고리별·미배정 과정 조회 | 관리자 | ✅ 구현 |
| `PATCH` | `/courses/:id/category` | 과정 카테고리 단건 배정·해제 | 관리자 | ✅ 구현 |
| `POST` | `/courses/bulk-assign-category` | 과정 다건 카테고리 일괄 배정 | 관리자 | ❌ 미구현 |

> **주의**: 과정 목록 조회 시 파트너 필터는 `partnerId`(camelCase)로 전달. 프론트 `fetchCoursesByCategory`에서 자동 변환.

### 3.2 bulk-assign-category 요청 바디

```ts
interface BulkAssignCategoryBody {
  course_ids: string[];          // 배정할 과정 ID 목록
  l1_category_id: number | null;
  l2_category_id: number | null;
}
```

`null`로 전송하면 배정 해제.

### 3.3 GET /course-categories 쿼리 파라미터

```
?partner_id=5                  → 파트너 5번 카테고리 전체 (backoffice 관리자용)
?for_institution=12            → 기관 12번 소속 파트너의 카테고리 (studio용)
?depth=1                       → L1만
?parent_id=3                   → L1 id=3의 L2 목록
```

- `partner_id`: backoffice 관리자가 특정 파트너 카테고리를 조회·관리할 때 사용
- `for_institution`: studio가 사용. API가 기관 → 파트너를 내부적으로 resolve하여 해당 파트너 카테고리 반환. 파트너 없는 기관이면 빈 배열 반환.

### 3.4 응답 타입

```ts
interface CourseCategoryItem {
  id: number;
  partner_id: string;  // UUID (institutions.id)
  depth: 1 | 2;
  parent_id: number | null;
  code: string;
  label: string;
  label_en: string | null;
  series_code: string | null;
  series_volume: number | null;
  sort_order: number;
  is_active: boolean;
  children?: CourseCategoryItem[]; // L1 조회 시 L2 포함 옵션
}
```

### 5.2 카테고리 구조 섹션

```
[카테고리 구조]
```

### 5.5 과정 배정 섹션

카테고리 구조 섹션에서 L1 또는 L2를 선택하면 우측에 해당 카테고리의 과정 배정 패널이 표시된다.

```
[과정 배정]  선택: 생활영어 > 매일사용하는 패턴영어 1권

  배정된 과정 (3)                         [+ 과정 추가]
  ──────────────────────────────────────────────────────
  ☑ 패턴영어 기초반 (A2 · 강사: 김철수)   [배정 해제]
  ☑ 패턴영어 완성반 (B1 · 강사: 이영희)   [배정 해제]
  ☑ 패턴영어 특강    (A2 · 강사: 박민준)   [배정 해제]
  ──────────────────────────────────────────────────────

  미배정 과정 (검색 후 선택)
  ┌─────────────────────────────────────────┐
  │ 🔍 과정명 검색...                        │
  └─────────────────────────────────────────┘
  □ 영어 첫걸음 (A1 · 강사: 최지원)         [이 카테고리에 추가]
  □ 비즈니스 이메일 영어 (B2 · 강사: 강동현) [이 카테고리에 추가]
```

**인터랙션 흐름**:
1. 좌측 카테고리 트리에서 L1 또는 L2 선택
2. 우측 패널 — 해당 카테고리에 배정된 과정 목록 + 미배정 과정 검색
3. [이 카테고리에 추가]: `PATCH /courses/:id` 호출 → 즉시 반영
4. [배정 해제]: `PATCH /courses/:id` (`l1_category_id: null`) 호출
5. [+ 과정 추가] 버튼: 미배정 과정 전체 목록 모달 → 다건 선택 → `POST /courses/bulk-assign-category`

**L1 선택 시**: 해당 L1에 배정된 과정을 표시(조회·해제만 가능). **과정 추가는 불가** — L2를 선택해야 미배정 과정 추가 UI가 활성화된다 (§5.8). L2 선택 시 해당 L2에 배정된 과정만 표시.

**미배정 과정**: `l1_category_id = null`인 파트너 소속 과정 전체를 검색 가능.

> **주의(2026-07-09~)**: 과정은 **L2에만** 배정한다. L1만 선택한 상태에서는 [추가]/[+ 과정 일괄 추가]가 비활성화된다. 상세는 §5.8.

### 5.6 과정타입 뱃지 (2026-06-23 추가)

과정 제목 옆에 과정타입(`courses.course_type`) 뱃지를 표시한다. Tutoring 과정과 Speaking 과정이 한 파트너에 섞여 있을 때 식별하기 위함. 적용 위치:

- **과정 카테고리 화면**: 과정 배정 패널의 배정된 과정 / 미배정 과정 / 일괄 추가 모달 세 곳 — `.../admin/content/categories/page.tsx`, `.../components/admin/CourseCategoryTab.tsx`
- **과정목록 화면**: 과정명 옆 **별도 `과정타입` 컬럼**으로 분리 — `.../admin/courses/page.tsx`. 다운로드(xlsx/csv)에도 `과정타입` 필드 포함(라벨 값)

| course_type | 라벨 | 색상 (color / bg) |
|-------------|------|-------------------|
| `tutoring`  | Tutoring | `#1e40af` / `#dbeafe` |
| `speaking`  | Speaking | `#9a3412` / `#ffedd5` |
| (그 외)     | 원본 값 그대로 | `#374151` / `#e5e7eb` |

**데이터 흐름 / 케이싱 정렬 (버그 수정 포함)**

뱃지 작업 중, `/courses` 응답을 카테고리 화면이 **snake_case로 잘못 읽고 있던 기존 결함**을 함께 정렬했다. 백엔드는 `CourseResponse`(camelCase)를 반환하는데 프론트 `CategoryCourseItem` 타입이 `level_code`·`institution_name`·`teacher_name`(snake_case)로 선언되어 있어, 부제(`{level_code} · {institution_name}`)가 `undefined`로 렌더링되던 상태였다.

- `CourseResponse`에 `courseType: string` 필드 추가 — `packages/types/src/index.ts`
- `toResponse()`에 `courseType: course.course_type` 매핑 추가 — `packages/core/src/course/course.service.ts`
- 프론트 `CategoryCourseItem`을 camelCase(`levelCode`·`institutionName`·`courseType`)로 정렬하고, 응답에 없던 `teacher_name`·`l1_category_id`·`l2_category_id` 제거 — `apps/admin/frontend/src/lib/api/course-category.ts`

### 5.7 교차 파트너 배정 버그 + 가드 (2026-06-23)

**증상**: 특정 회원(teacher.choi@oizi.net)이 만든 과정이 카테고리 관리의 "미배정 과정"에도, "배정된 과정"에도 보이지 않음.

**원인**: 해당 과정 5건 중 4건이 **자기 파트너(팀초이파트너스)가 아닌 다른 파트너(파고다 교육그룹)의 카테고리에 배정**돼 있었다. 미배정 목록은 `l1_category_id = null`만 보여주므로 제외되고, 배정된 목록은 "선택 파트너의 카테고리 + 선택 파트너 스코프의 과정"만 보여주므로:
- 팀초이파트너스 선택 시: 배정된 카테고리(파고다 소유)가 목록에 없어 제외 → 안 보임
- 파고다 교육그룹 선택 시: 과정 기관이 파고다 스코프 밖 → 제외 → 안 보임
- 결과적으로 **양쪽 파트너 화면 어디에도 표시되지 않는 고아 상태**.

**근본 원인**: 배정 API(`updateCategory`/`bulkAssignCategory`)가 "카테고리 소유 파트너 == 과정 파트너"를 검증하지 않아, 과정이 타 파트너 카테고리에 배정될 수 있었다.

**조치 ① — 데이터 정리**: 잘못 배정된 4건의 `l1_category_id`/`l2_category_id`를 `null`로 해제(트랜잭션). 해제 후 팀초이파트너스 미배정 목록에 정상 노출됨. (해제 기준: 과정의 소유 파트너 ≠ 배정 카테고리의 `partner_id`)

**조치 ② — 가드 추가** (`packages/core/src/course/course.service.ts`):
- `InstitutionService.resolvePartnerId(institutionId)` 추가 — 기관→그룹→파트너 계층을 거슬러 소유 파트너 id 해석.
- `CourseService.assertCategoryPartnerMatch(courseIds, l1, l2)` 추가 — 배정 대상 카테고리의 `partner_id`가 각 과정의 소유 파트너와 일치하는지 검증, 불일치 시 `BadRequestException`. 존재하지 않는 카테고리는 `NotFoundException`. **배정 해제(l1/l2 모두 null)는 검증하지 않음**.
- `updateCategory`·`bulkAssignCategory` 진입부에서 호출.

**재발 방지 체크리스트**:
- [ ] 과정 카테고리 배정은 반드시 **같은 파트너 소유 카테고리**로만 한다(가드가 강제).
- [ ] studio 등 다른 경로에서 배정할 때도 동일 서비스 메서드를 거치는지 확인.

**검증**: `@repo/core` build(tsc) 통과. 데이터 정리 전/후 DB 대조로 4건 해제 확인(2026-06-23).

> **monorepo 주의**: `@repo/core` 변경 → 빌드 후 admin backend 재시작 필요.

### 5.8 L1 단독 배정 금지 — 과정은 L2에만 배정 (2026-07-09)

**배경**: DB(`l1_category_id`/`l2_category_id` 둘 다 nullable) · 백엔드 · 프론트 어디에도 depth 제약이 없어, 과정이 L1에만 배정(`l1 != null, l2 = null`)될 수 있었다. 카테고리 체계상 과정은 항상 L2(중카테고리) 단위로 분류되어야 하므로 이를 강제한다.

**유효 배정 상태 (강제 규칙)**
- **미배정**: `l1 = null, l2 = null`
- **배정**: `l2 = <L2 id>` (+ 그 부모 `l1`) — L2는 `depth = 2`, L1이 함께 오면 `l2.parent_id == l1`
- **금지**: `l1 != null && l2 == null` (L1 단독 배정)

**조치 ① — 백엔드 가드** (`packages/core/src/course/course.service.ts`, `assertCategoryPartnerMatch`):
- 배정 해제(둘 다 null)는 검증하지 않음(기존 유지).
- `l2 == null && l1 != null` → `BadRequestException` (L1 단독 배정 금지).
- 지정 L2가 `depth = 2`인지 검증, L1이 함께 오면 `l2.parent_id == l1` 계층 정합성 검증.
- 기존 파트너 일치 검증(§5.7)은 그대로 유지. → backoffice의 `updateCategory`·`bulkAssignCategory` 양 경로에 자동 적용된다. **studio 배정 경로가 동일 `@repo/core` 메서드를 거치는지는 미확인**(§5.7 체크리스트와 동일한 미결) — 별도 백엔드를 통한다면 그쪽에도 동일 가드가 필요하다.

**조치 ② — backoffice UI** (`.../admin/content/categories/page.tsx`):
- `handleAssignCourse`·`handleBulkAssign` 가드를 `selectedL1` → **`selectedL2`** 기준으로 강화.
- `canAssign = !!selectedL2`. L1만 선택 시 미배정 과정 패널은 *"과정은 L2(중카테고리)에만 배정할 수 있습니다"* 안내로 대체하고, [+ 과정 일괄 추가] 버튼 비활성화.
- **배정된 과정 목록 + [해제]는 L1 선택 상태에서도 유지** — 혹시 남은 L1-only 배정을 찾아 정리할 수 있도록.

**조치 ③ — 기존 위반 4건 데이터 정리** (각 과정의 현재 L1 하위 L2로 이동, 트랜잭션):

| 과정 | course_type | L1 (유지) | → L2 (신규) |
|------|-------------|-----------|-------------|
| 영어생활 24시 | speaking | 1 일상회화 | 10 일상회화 기초 |
| 중등 입시 준비과정 | tutoring | 12 초급 리딩 | 17 수능 초급 읽기 |
| 초등 저학년 읽기 과정 | tutoring | 12 초급 리딩 | 13 기초 읽기 1 |
| 임직원 초급 영어 과정 1 | tutoring | 14 비즈니스 | 18 비즈니스 회화 1 |

- 정리 후 `l1 != null && l2 = null` 위반 **0건** 확인. speaking/tutoring 혼재이므로 공유 DB 정책(§15)상 tutoring 팀 정렬 필요.

**미채택**: DB CHECK 제약(`CHECK (l1_category_id IS NULL OR l2_category_id IS NOT NULL)`)은 이번 범위에서 제외(애플리케이션 가드로 강제). 추후 직접 SQL 우회까지 막으려면 `NOT VALID`로 추가 후 `VALIDATE` 절차로 도입 가능.

**재발 방지 체크리스트**:
- [ ] 과정 배정은 반드시 **L2 단위**로만 한다(백엔드 가드가 강제).
- [ ] studio 등 다른 경로도 동일 `CourseService` 메서드를 거치는지 확인.

**검증**: `@repo/core` build(tsc) 통과, admin frontend `tsc --noEmit` 통과, 데이터 정리 전/후 DB 대조로 위반 0건 확인(2026-07-09).

> **monorepo 주의**: `@repo/core` 변경 → 빌드 후 admin backend 재시작 필요.

### 5.9 배정 화면 성능 개선 (2026-07-09)

**증상**: 과정 카테고리 관리 페이지가 느림.

**원인 (두 축)**
1. **프론트 과다 재요청** — `loadCourses`가 `courseSearch`를 deps로 가진 채 디바운스 없이 실행되어, 미배정 검색창 키 입력마다 `/courses`를 **assigned+unassigned 2회씩** 재호출. 검색어와 무관한 배정 목록까지 매번 재조회. Bulk 모달도 동일.
2. **백엔드 과잉 계산** — `/courses`(`CourseService.findAll`)는 요청당 `resolveUserScope`·`resolveSelectionScope`(재귀 CTE 2회) + `resolveHierarchyNames`(기관 join) + `resolveAccessCodeCounts`(groupBy 2회)를 수행. 그러나 배정 화면이 쓰는 필드는 `id·title·levelCode·institutionName·courseType`뿐이라 **hierarchyNames·accessCodeCounts는 전부 낭비**(institutionName은 `include`로 이미 존재).

**조치 ① — 백엔드 경량 전용 경로**
- `CourseService.findForCategoryAssignment(params, roleScope)` 신설 (`packages/core/src/course/course.service.ts`).
  - assigned + unassigned를 **한 번에** 반환 → 스코프 재귀 해석 **1회**(기존 2회).
  - `resolveHierarchyNames`·`resolveAccessCodeCounts` **미호출**, `select`를 5개 컬럼(+institution.name)으로 축소.
  - 미배정: `l1_category_id = null` + 제목 검색, `unassignedLimit`(기본 50, 최대 200) + `unassignedTotal`·`unassignedHasMore` 반환.
  - 반환 타입 `CategoryAssignmentResult`/`CategoryAssignmentCourse` export.
- `GET /courses/category-assignment` 컨트롤러 추가 (`apps/admin/backend/src/course/course.controller.ts`). `@Get(':id')`보다 위에 선언(라우트 충돌 방지). `partnerId` 필수, 역할 스코프는 기존 `resolveUserScope` 재사용.
- 요청당 쿼리 **약 6~7개 → 3개**(assigned findMany + unassigned findMany + unassigned count). 재귀 CTE 절반, groupBy·hierarchy join 제거.

**조치 ② — 프론트 디바운스 + 단일 호출**
- `courseSearch`/`bulkSearch`에 **300ms 디바운스** 상태 추가. `loadCourses`/`loadBulkCourses`를 새 `fetchCategoryAssignment` **단일 호출**로 전환(`apps/admin/frontend/.../categories/page.tsx`, `.../lib/api/course-category.ts`).
- 결과: "검색어 5글자 입력 = 10요청" → **1요청**(디바운스 후). 각 요청도 경량.

**조치 ③ — 상한/힌트 (조용한 20건 상한 해소)**
- 기존 `fetchCoursesByCategory`가 `limit` 미전달로 백엔드 기본 `limit=20`에 걸려 목록이 조용히 잘리던 문제를, 명시적 `unassignedLimit`(50) + `unassignedHasMore` 플래그로 대체. 잘릴 경우 UI에 *"상위 결과만 표시됩니다. 검색어로 좁혀주세요"* 힌트 표시(배정 패널·Bulk 모달).

**미채택(범위 외)**: `title` 검색용 `pg_trgm` GIN 인덱스는 데이터 증가 시점에 재검토. (제안 (5))

**검증**: `@repo/core` build(tsc) 통과, admin backend `tsc --noEmit` 통과, admin frontend `tsc --noEmit`·`next lint` 통과(2026-07-09).
