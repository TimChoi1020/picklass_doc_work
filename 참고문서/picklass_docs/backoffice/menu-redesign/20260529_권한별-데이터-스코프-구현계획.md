## 1. 개요

백오피스의 모든 목록 페이지는 로그인한 관리자의 역할에 따라 **볼 수 있는 데이터를 제한**해야 한다.  
UI에서 메뉴를 숨기는 것만으로는 부족하며, **백엔드에서도 쿼리 단위로 강제 적용**해야 한다.

### 1.1 역할별 데이터 범위

| 역할 | 데이터 범위 |
|------|-----------|
| `system_admin` | 전체 데이터 |
| `partner_admin` | 자기 파트너 + 산하 모든 그룹·기관 |
| `group_admin` | 자기 그룹 + 산하 모든 기관 |
| `academy_admin` | 자기 기관 1개 |

### 1.2 구현 원칙

- **백엔드 강제**: `resolveUserScope()`가 허용 기관 ID 목록을 반환 → `WHERE id IN (...)` 적용
- **프론트엔드 UX**: 역할 이상은 LOCK 표시, 역할 미만은 드롭다운으로 검색 가능
- **단일 컨텍스트 소스**: `/auth/me` 응답의 `orgContext`를 Zustand store에 저장 → 전 페이지 공유

## 2. 아키텍처

### 2.1 전체 흐름

```
로그인 → GET /auth/me
  → authService.getOrgContext(userId, roleCode)
  → { partnerId, partnerName, groupId, groupName, institutionId, institutionName, fixedLevel }
  → useAuthStore.user.orgContext 에 저장

목록 API 요청
  → AdminAuthGuard (JWT 검증, req.adminUserId / req.adminRole 주입)
  → Controller: institutionService.resolveUserScope(adminUserId, adminRole)
      → null (system_admin) 또는 string[] (허용 기관 ID 목록)
  → Service: findAll(query, scope)
      → WHERE id IN (scope) + 추가 필터
```

### 2.2 핵심 타입 (`packages/types/src/index.ts`)

```typescript
export interface UserOrgContext {
  partnerId: string | null;
  partnerName: string | null;
  groupId: string | null;
  groupName: string | null;
  institutionId: string | null;
  institutionName: string | null;
  // null=system_admin(제한 없음)
  // 'partner'=파트너 고정, 'group'=파트너+그룹 고정, 'institution'=전체 고정
  fixedLevel: 'partner' | 'group' | 'institution' | null;
}

// AuthUser에 orgContext 추가됨
export interface AuthUser {
  id: string;
  userId: string;
  email: string | null;
  name: string;
  roleCode: string;
  institutionId: string | null;
  orgContext?: UserOrgContext;
}
```

### 2.3 필터 UI 렌더링 규칙

| 필드 | system_admin | partner_admin | group_admin | academy_admin |
|------|:----------:|:----------:|:----------:|:----------:|
| 파트너 | 드롭다운 검색 | LOCK 고정 | LOCK 고정 | LOCK 고정 |
| 그룹 | 드롭다운 검색 | 드롭다운 검색 | LOCK 고정 | LOCK 고정 |
| 기관 | 텍스트 검색 | 텍스트 검색 | 텍스트 검색 | LOCK 고정 |

`fixedLevel` 기준으로 판단:
- `null` → 모두 검색 가능
- `'partner'` → 파트너만 LOCK, 그룹·기관은 검색
- `'group'` → 파트너·그룹 LOCK, 기관은 검색
- `'institution'` → 전체 LOCK

## 4. 다른 페이지 적용 가이드

### 4.1 백엔드 — 공통 패턴

> `institution.service.ts`의 `resolveDescendants` / `resolveUserScope`는 **이미 존재**하므로 재사용.  
> 새 엔티티의 Service는 아래 패턴만 추가하면 된다.

#### ① 컨트롤러: Guard + scope 주입

```typescript
// apps/admin/backend/src/[entity]/[entity].controller.ts

import { UseGuards, Req } from '@nestjs/common';
import { AdminAuthGuard } from '../auth/admin-auth.guard';
import { InstitutionService } from '@repo/core'; // resolveUserScope 재사용

type AuthRequest = Request & { adminUserId: string; adminRole: string };

@UseGuards(AdminAuthGuard)     // ← 반드시 추가
@Controller('[entity]')
export class SomeController {
  constructor(
    private readonly someService: SomeService,
    private readonly institutionService: InstitutionService, // scope 계산용
  ) {}

  @Get()
  async findAll(@Query() query: SomeQueryDto, @Req() req: AuthRequest) {
    const scope = await this.institutionService.resolveUserScope(
      req.adminUserId,
      req.adminRole,
    );
    return this.someService.findAll(query, scope);
  }
}
```

> **주의**: `@UseGuards(AdminAuthGuard)` 추가 시 해당 모듈에 `CoreAuthModule`과 `AuthModule`을 반드시 함께 import해야 한다. 누락되면 서버 시작 시 크래시 → 로그인 "Failed to fetch" 발생.

```typescript
// apps/admin/backend/src/user/user.module.ts
import { UserModule as CoreUserModule, InstitutionModule as CoreInstitutionModule, AuthModule as CoreAuthModule } from '@repo/core';
import { AuthModule } from '../auth/auth.module';

@Module({
  imports: [
    CoreUserModule,
    CoreInstitutionModule,  // ← resolveUserScope 재사용
    CoreAuthModule,         // ← AdminAuthGuard 의존성 (AuthService)
    AuthModule,             // ← AdminAuthGuard provider/export
  ],
  controllers: [UserController],
})
export class UserModule {}
```

#### ② 서비스: scope → WHERE 조건 적용

엔티티가 `institutionId`를 가진 경우 (과정, 액세스코드, 학습자 등):

```typescript
// packages/core/src/[entity]/[entity].service.ts

async findAll(
  query: SomeQueryDto,
  scopeInstitutionIds?: string[] | null,
): Promise<SomeListResponse> {
  const where: Prisma.SomeWhereInput = { deletedAt: null };

  // scope 적용 — null이면 전체(system_admin), 빈 배열이면 접근 불가
  if (scopeInstitutionIds !== null && scopeInstitutionIds !== undefined) {
    where.institutionId = { in: scopeInstitutionIds };
  }

  // 추가 검색 필터
  if (query.name) where.name = { contains: query.name, mode: 'insensitive' };
  // ...
}
```

엔티티 자체가 조직(institution 테이블)인 경우 (조직관리 페이지처럼):

```typescript
// WHERE id IN (scope) — 기관 자체를 필터링
if (scopeInstitutionIds !== null && scopeInstitutionIds !== undefined) {
  where.id = { in: scopeInstitutionIds };
}
```

**엔티티별로 다른 것은 `where.XXX` 필드명 하나뿐이다:**

| 페이지 | Prisma 모델 | scope 적용 필드 |
|--------|-----------|---------------|
| 조직관리 | `Institution` | `where.id = { in: scope }` |
| 사용자 관리 | `User` | `where.institutionId = { in: scope }` |
| 과정 목록 | `Course` | `where.institutionId = { in: scope }` |
| 액세스코드 | `AccessCode` | `where.institutionId = { in: scope }` |
| 통계 (Raw SQL) | — | `AND institution_id = ANY(ARRAY[...scope]::uuid[])` |

#### ④ PARTNER_ABOVE 페이지 — partner_id 기반 scope (별도 패턴)

`resolveUserScope()`는 institution ID 목록을 반환하는 institution 계층 전용 함수다.  
**PARTNER_ABOVE 페이지**(system_admin + partner_admin만 접근)는 scope 단위가 institution이 아니라 **partner**이므로 다른 패턴을 사용한다.

```typescript
// PARTNER_ABOVE 컨트롤러 패턴 (예: course-categories.controller.ts)
@Get()
async findAll(@Query() query: CategoryQueryDto, @Req() req: AuthRequest) {
  // partner_admin: JWT의 partnerId로 강제 고정
  // system_admin: 쿼리 파라미터 partner_id 그대로 사용 (전체 조회 가능)
  const partnerId =
    req.adminRole === 'system_admin'
      ? query.partner_id            // 관리자는 파라미터 사용
      : req.adminPartnerIdAsNumber; // partner_admin은 자기 파트너로 강제
  return this.categoryService.findAll({ ...query, partner_id: partnerId });
}
```

서비스에서의 WHERE:
```typescript
// packages/core/src/course-category/course-category.service.ts
where.partnerId = partnerId; // partner_id = ? (단순 equality, 재귀 불필요)
```

**institution 기반 scope와의 차이**:

| 항목 | institution 기반 (ALL_ADMIN) | partner 기반 (PARTNER_ABOVE) |
|------|----------------------------|------------------------------|
| scope 계산 | `resolveUserScope()` — 재귀 CTE | JWT의 `partnerId` 직접 사용 |
| WHERE 조건 | `institutionId IN (scope[])` | `partnerId = partnerId` |
| group_admin 처리 | 자기 그룹 하위 기관만 | 접근 자체 불가 (AdminRoleGate 차단) |
| 재귀 CTE 비용 | 있음 | 없음 |

> 현재 PARTNER_ABOVE 패턴이 적용된 페이지: **과정 카테고리** (`/admin/content/categories`) — 프론트엔드 파트너 LOCK 완료, 백엔드 API 미구현

#### ③ 응답에 계층 정보 포함 (선택)

목록에 파트너명·그룹명 컬럼이 필요한 경우, 기관 join 후 `toResponse()`에서 계산:

```typescript
// institution과 join이 있다면
const rows = await this.prisma.some.findMany({
  where,
  include: {
    institution: {
      include: { parent: { include: { parent: true } } }
    }
  }
});

// 응답에 추가
partnerName: row.institution?.parent?.parent?.name ?? null,
groupName:   row.institution?.parent?.name ?? null,
```

#### ⑥ 테이블 컬럼

**계층 표시 원칙**: 각 행은 자신의 레벨(타입)에 해당하는 마지막 컬럼에만 이름을 채운다. 상위 컬럼은 컨텍스트(소속), 하위 컬럼은 `-`로 표시한다.

```
파트너명       그룹명      기관명
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ABC파트너    -           -           ← type='partner'
ABC파트너    서울그룹     -           ← type='group'
ABC파트너    서울그룹     강남기관     ← type='institution'
```

```tsx
<thead>
  <tr>
    <th>파트너명</th>
    <th>그룹명</th>
    <th>기관명</th>
    {/* 기타 컬럼 */}
  </tr>
</thead>
<tbody>
  {rows.map((row) => (
    <tr key={row.id}>
      {/* 파트너명: 항상 표시 (partner=자기 이름, 하위=상위 파트너명) */}
      <td style={{ color: row.partnerName ? '#333' : '#ccc' }}>
        {row.partnerName ?? '-'}
      </td>
      {/* 그룹명: group/institution 타입만 표시 */}
      <td style={{ color: row.groupName ? '#333' : '#ccc' }}>
        {row.groupName ?? '-'}
      </td>
      {/* 기관명: institution 타입만 자기 이름 표시, 나머지는 '-' */}
      <td style={{ color: row.type === 'institution' ? '#333' : '#ccc' }}>
        {row.type === 'institution' ? row.name : '-'}
      </td>
    </tr>
  ))}
</tbody>
```

> **조직관리 페이지 전용 규칙**: 조직관리는 partner/group/institution 세 타입을 하나의 목록에 혼합 표시하므로 위 규칙이 필요하다. 사용자·과정 등 단일 타입 엔티티 목록은 기관명 컬럼을 단순히 `row.institutionName`으로 채우면 된다.

#### 증상 vs 원인

| 증상 | 원인 |
|------|------|
| **로그인 "Failed to fetch"** | `CoreAuthModule`·`AuthModule` 미import → 서버 시작 시 크래시 |

| 소속기관 컬럼 | type별 셀 채우기 (partner/group/institution 혼합) | 항상 `user.institutionName` 표시 (단일 기관 소속) |
| system_admin 제외 | 해당 없음 | `excludeSystemAdmin: true` — **백엔드에서 제외** → 페이지네이션 count 정확도 확보 |
| 아이디 검색 | adminEmail 텍스트 검색 | `userId` DB ILIKE 검색으로 연동 |

> **`excludeSystemAdmin` 패턴**: 특정 역할을 목록에서 항상 제외해야 하는 페이지에 사용한다.  
> 클라이언트 측 `filter()`로 제외하면 페이지당 실제 표시 건수가 줄어 빈 페이지가 생긴다.  
> 백엔드 `where.roleCode = { not: 'system_admin' }` 처리 시 count도 동일하게 제외되어 pagination이 정확해진다.

### 5.1 대기 중인 페이지

## 6. 주의사항 및 트레이드오프

### 6.1 `resolveDescendants` 성능

재귀 CTE는 요청마다 실행된다. 조직 계층이 깊지 않고(partner→group→institution 3단계) 기관 수가 수백 개 이내라면 성능 문제 없음.  
기관 수가 1,000개 이상으로 늘어나면 Redis 캐싱 또는 `parent_id` 경로 열(path enumeration) 도입 검토.

### 6.2 `orgContext` 신선도

`/auth/me` 호출 시 DB를 조회해 `orgContext`를 반환한다. 로그인 후 관리자의 소속 기관이 변경되면 재로그인 전까지 구 데이터가 프론트에 남는다.  
운영 상 기관 변경은 드문 일이므로 현재 설계로 충분. 필요 시 `/auth/me` 재호출 후 store 갱신 로직 추가 가능.

### 6.3 `partnerId`/`groupId` 필터의 재귀 비용

프론트엔드에서 `partnerId`/`groupId` 필터를 지정하면 백엔드가 CTE를 한 번 더 실행한다(user scope용 1회 + 필터용 1회). 이 두 결과를 교집합 처리한다. 동일 DB 라운드트립 내에 처리되므로 네트워크 오버헤드 없음.

### 6.4 단건 조회 (`GET /:id`) scope 확인

단건 조회는 현재 **scope 확인 없이** 반환한다.  
URL 직접 접근 시 다른 기관의 데이터를 조회할 수 있다.  
필요 시 컨트롤러에서 단건 조회 후 scope 포함 여부 검사 추가:

```typescript
@Get(':id')
async findById(@Param('id') id: string, @Req() req: AuthRequest) {
  const scope = await this.institutionService.resolveUserScope(
    req.adminUserId, req.adminRole
  );
  const item = await this.someService.findById(id);
  if (scope !== null && !scope.includes(item.institutionId)) {
    throw new NotFoundException('데이터를 찾을 수 없습니다.');
  }
  return item;
}
```
