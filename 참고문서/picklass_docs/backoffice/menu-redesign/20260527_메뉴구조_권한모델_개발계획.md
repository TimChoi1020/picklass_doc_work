## 2. 권한 모델 (2-Tier)

### Tier 1 — 메뉴 접근 자체 차단 (system_admin ONLY)

`AdminRoleGate`에서 라우트 수준으로 차단. 해당 URL 직접 접근 시 `/admin/dashboard`로 리다이렉트.

- **시스템** 대메뉴 전체 (7개 소메뉴 포함)
- **API 로그** 대메뉴 전체 (2개 소메뉴 포함)
- **예외 소메뉴**: 통계/리포트 내 `플랫폼 현황`, `B2B 학습데이터`도 system_admin only

### Tier 2 — 데이터 범위 제한 (ALL_ADMIN 접근 허용)

메뉴에는 모든 관리자(partner_admin·group_admin·academy_admin 포함)가 접근 가능.  
역할에 따라 검색 필터를 **pre-fill + disable**로 고정하여 보이는 데이터 범위를 제한한다.  
메뉴 자체를 숨기거나 차단하지 않는다.

- 조직관리 / 사용자관리 / 콘텐츠 플랫폼 / 통계·리포트 (Tier 1 예외 소메뉴 제외)

### Tier 2 (PARTNER_ABOVE) — 파트너 연동 메뉴

`system_admin`과 `partner_admin`만 접근 가능 (`group_admin`·`academy_admin` 제외).  
`constants.ts`에 `PARTNER_ABOVE = ['system_admin', 'partner_admin']`로 정의.  
data scope: `system_admin` 전체 조회, `partner_admin` 자기 기관만.

- 파트너 API 연동 대메뉴 전체 (단, `연동 테스트`는 Tier 1 — system_admin only)

### 설계 배경 — restrictedToEmails → allowedRoles 전환 (Phase 1)

기존 `restrictedToEmails` 방식(이메일 하드코딩)을 `allowedRoles` + 데이터 범위 제한 방식으로 전환하였다. 위 Tier 1·2 구조가 그 결과물이다.

### MenuItem 타입 변경 이력 (`constants.ts`)

```typescript
// 변경 전
export interface MenuItem {
  label: string;
  href: string;
  icon?: string;
  restrictedToEmails?: string[];
}

// 변경 후
export interface MenuItem {
  label: string;
  href: string;
  icon?: string;
  allowedRoles?: string[];   // 미설정 시 모든 인증 사용자에게 노출 (Tier 2)
  children?: MenuItem[];     // 2-depth 소메뉴
}
```

### 사이드바 필터링 구현 (`app-sidebar.tsx`)

```typescript
const userRole = useAuthStore((s) => s.user?.roleCode ?? null);

function filterByRole(items: MenuItem[], role: string | null): MenuItem[] {
  return items
    .filter((item) => !item.allowedRoles || (role !== null && item.allowedRoles.includes(role)))
    .map((item) => ({
      ...item,
      children: item.children ? filterByRole(item.children, role) : undefined,
    }));
}

const visibleMenu = filterByRole(menu, userRole);
```

### AdminRoleGate 구현 (`admin-role-gate.tsx`)

메뉴 숨김만으로는 URL 직접 접근을 막을 수 없으므로, `ADMIN_MENU`의 `allowedRoles`를 단일 진실의 원천으로 사용해 라우트 접근도 통제한다.

```typescript
// components/auth/admin-role-gate.tsx
export function AdminRoleGate({ children }: { children: React.ReactNode }) {
  const pathname = usePathname();
  const user = useAuthStore((s) => s.user);
  const router = useRouter();

  const routeRoleMap = useMemo(() => {
    const map = new Map<string, string[] | undefined>();
    for (const item of ADMIN_MENU) {
      map.set(item.href, item.allowedRoles);
      item.children?.forEach((child) => {
        map.set(child.href, child.allowedRoles ?? item.allowedRoles);
      });
    }
    return map;
  }, []);

  const allowed = useMemo(() => {
    if (!user) return false;
    // pathname과 가장 길게 매칭되는 경로의 allowedRoles 사용
    const matchedRoles = [...routeRoleMap.entries()]
      .filter(([href]) => pathname === href || pathname.startsWith(href + '/'))
      .sort((a, b) => b[0].length - a[0].length)[0]?.[1];
    if (!matchedRoles || matchedRoles.length === 0) return true;
    return matchedRoles.includes(user.roleCode);
  }, [user, pathname, routeRoleMap]);

  useEffect(() => {
    if (user && !allowed) router.replace('/admin/dashboard');
  }, [user, allowed, router]);

  if (!allowed) return <div>접근 권한이 없습니다.</div>;
  return <>{children}</>;
}
```

```typescript
// app/(admin)/layout.tsx
export default function AdminLayout({ children }) {
  return (
    <AdminAuthGate>     {/* 로그인 여부 */}
      <AdminRoleGate>   {/* role 기반 라우트 접근 — ADMIN_MENU 기준 */}
        ...
      </AdminRoleGate>
    </AdminAuthGate>
  );
}
```

## 4. 데이터 범위(Scope) 규칙 — Tier 2 메뉴 전용

### 원칙

역할에 따라 필터를 숨기는 대신, **자신의 소속 조직명을 미리 입력한 상태로 비활성화(pre-fill + disable)** 한다.  
사용자가 현재 어떤 범위의 데이터를 보고 있는지 명확히 인지할 수 있도록 한다.

**백엔드에서도 동일 scope를 강제 적용**한다. 프론트 우회(직접 API 호출)로 타 기관 데이터를 조회할 수 없다.

### 역할별 고정 필터

| role | 고정되는 필터 | 고정값 출처 |
|------|------------|-----------|
| `system_admin` | 없음 — 전체 조회 | — |
| `partner_admin` | 상위 파트너 🔒 | `orgContext.partnerName` (GET /auth/me) |
| `group_admin` | 상위 파트너 🔒 + 상위 그룹 🔒 | `orgContext.partnerName` / `orgContext.groupName` |
| `academy_admin` | 파트너 🔒 + 그룹 🔒 + 소속기관 🔒 | `orgContext.institutionName` |

### 구현 방식 (2026-05-29 완료)

**`UserOrgContext`** (`packages/types/src/index.ts`):  
로그인 후 `GET /auth/me` 응답에 포함. Zustand `useAuthStore`에 저장하여 모든 페이지에서 공유.

```typescript
interface UserOrgContext {
  partnerId: string | null;     partnerName: string | null;
  groupId:   string | null;     groupName:   string | null;
  institutionId: string | null; institutionName: string | null;
  fixedLevel: 'partner' | 'group' | 'institution' | null;
  // null = system_admin (제한 없음)
}
```

**백엔드 scope 강제** (`packages/core/src/institution/institution.service.ts`):

```typescript
// 역할별 접근 가능 기관 ID 목록 — 재귀 CTE
async resolveUserScope(userId, roleCode): Promise<string[] | null>
// null = system_admin (전체), string[] = 허용 기관 ID 목록

// 컨트롤러에서 사용
const scope = await institutionService.resolveUserScope(req.adminUserId, req.adminRole);
return someService.findAll(query, scope);
// → WHERE institutionId IN (scope) 또는 WHERE id IN (scope)
```

## 5. API 파라미터 규칙

```
공통 쿼리 파라미터: partnerId, groupId, institutionId, courseId, startDate, endDate
```

- `system_admin`: 파라미터 미전송 시 전체 조회. `partnerId`/`groupId` 지정 시 해당 노드의 재귀 하위 기관으로 범위 축소.
- 나머지 role: 백엔드 `resolveUserScope()`가 JWT의 `userId`·`roleCode`로 허용 기관 ID 목록을 자동 산출 → `WHERE institutionId IN (...)` 강제 적용.
- `partnerId`/`groupId`는 **재귀(CTE) 필터**로 동작한다. 직속 자식만이 아닌 전체 하위 계층이 포함된다.
- `parentId`는 **직속 하위 조회** 전용 (드롭다운 옵션 로드용). 재귀 필터와 혼용하지 않는다.
