## ★ 최상위 교차 이슈 — 07_B2B제휴운영모델이 "이상형", 실제 구현은 다른 모델

`07_B2B제휴운영모델.md`(v1.1)는 **aspirational 모델**(PUSH·4종 인증·partner_* 일반화 테이블)로 서술돼 있으나, 실제 구현(api·backoffice 문서)은 정반대다. api·backoffice 스캔이 독립적으로 동일 결론에 도달했다.

| 쟁점 | 07 (이상형) | 실제 구현 |
|---|---|---|
| 연동 방향 | 제휴사→픽클래스 **PUSH**(액세스코드 발급) | 픽클래스가 파트너 API **클라이언트(PULL)** |
| 인증 방식 | **4종**(ONETIME/OAuth·OIDC/API Key/JWT) | **2패턴**(장기 API Key + 원타임 토큰). OAuth/OIDC 미계획 |
| 회원 매핑 | 매핑 없으면 picklass user **자동 생성** | users 레코드 **생성 안 함**(JWT에만 파트너 정보) |
| 이수 판정 | 제휴사 책임, 픽클래스는 KPI 전달만 | **픽클래스가 판정** 후 이수완료 Push |
| 데이터모델 | partner_organizations/user_mappings/product_mappings | pagoda_* 5종 + partner_api_keys + external_access_tokens |
| 채널 적용 | Speaking 독립앱 ❌ 미적용 | 최대 제휴(우유랩스)가 외부 스피킹앱에 공급 |

→ **결정 필요**: 07을 실제 PULL·2패턴 모델로 **덮어쓰기**할지, "이상형 vs 실제 2가지 연동 방식 병기"로 갈지.
