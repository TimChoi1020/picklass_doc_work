지능형 수업 설계 자동화 로직

이 로직은 제공된 레벨별 학습 목표와 8단계 학습 프로세스를 알고리즘화한 것입니다.

---

### **1\. 수업 설계 엔진의 핵심 입력 데이터 (Input)**

엔진이 구동되기 위해 필요한 기초 정보입니다.

* **Target (대상):** 학습자의 현재 레벨 또는 신분 (예: 고1, 대학생, 임원).  
* **Purpose (목적):** 강화하고자 하는 핵심 역량 (예: 수능 독해, 토익 RC, 비즈니스 회화).  
* **Duration (시간):** 수업 목표 시간 (예: 20분, 40분).

---

### **2\. 자동화 로직 단계 (Step-by-Step Logic)**

#### **Step 1: 레벨 및 KPI 직접 선택 (Level & KPI Selection)**

> **설계 원칙:** "임원 → C1/C2", "비즈니스회화 → 말하기유창성"처럼 추상적 대상/목적을 자동으로 매핑하는 방식은 매핑 테이블 유지 부담이 크고, 실제 지문 난이도와 괴리가 생길 수 있습니다. 대신 과정 생성 시 확정된 구체적 데이터를 직접 입력받아 매핑 오류를 원천 차단합니다.

* **레벨 선택:** 과정 생성 시 이미 확정된 지문의 실제 레벨(CEFR)을 자동으로 pre-fill하여 표시하고, 필요 시 수정 가능하게 합니다.
* **KPI 선택:** 백오피스 `KPI_CATEGORY`의 `extraData.goal`(목표)을 기준으로 중복 제거(distinct)한 목록을 멀티셀렉트로 보여주고, 이 수업에서 집중할 KPI를 직접 선택받습니다. 코드는 UI에 노출하지 않습니다. `AiModule.selectedKpiCodes`와 동일한 코드 체계를 사용하므로 별도 변환 없이 모듈 매칭이 직결됩니다.

이렇게 하면 **Step 1(매핑)은 사람이 직접 수행**하고, **Step 2~4(필터링·시퀀싱·검증)는 시스템이 자동 처리**하는 역할 분담이 명확해집니다. 선택 데이터가 누적되면 추후 "이 조합이 자주 선택되었다"는 자동 추천 근거로도 활용할 수 있습니다.

#### **Step 2: 모듈 풀(Pool) 필터링 (Module Filtering)**

전체 모듈 데이터베이스에서 다음 조건에 맞는 후보군을 추출합니다.

1. **Level Match:** 사용자의 레벨 범위에 포함된 모듈 .  
2. **Domain Match:** 목적에 부합하는 영역(Voca, Read, Speak 등)의 모듈.

#### **Step 3: KPI 커버리지 + 인지 부하 곡선 기반 시퀀싱 (Sequence Generation)**

> **설계 원칙:** 단계별 모듈 개수를 미리 정하는 방식(예: Intro 2개, Body 2개, Closure 1개)은 패턴이 고착되어 수업이 단조로워질 수 있습니다. 대신 **"선택한 KPI를 달성하는 데 최적인 모듈 조합"** 을 중심에 놓고, 개수는 시간 제약의 결과로 자연스럽게 결정됩니다.

**시퀀싱 기준:**

1. **KPI 커버리지 최대화:** 선택한 KPI 코드를 가장 많이 커버하는 모듈 조합을 우선 선택합니다 (배낭 문제 방식).
2. **인지 부하 곡선 (Bloom's Taxonomy):** 모듈의 `cognitiveLevel` 필드를 기준으로 인지 수준이 자연스럽게 상승하는 순서로 배열합니다. 개수를 정하는 것이 아니라 인지 흐름이 Intro / Body / Closure를 자동으로 결정합니다.

```
낮은 인지 수준 (기억·이해)  →  중간 (적용·분석)  →  높은 (평가·창조)
        ↑ Intro 자연 배치             ↑ Body               ↑ Closure
```

3. **시간 제약 검증:** 선택된 조합의 `estimatedMinutes` 합산이 수업 시간 이하인지 확인하고, 초과 시 KPI 점수가 낮은 모듈부터 제거합니다.

이 방식은 레벨과 수업 시간에 따라 매번 다른 개수와 조합이 도출되므로, 패턴 반복으로 인한 피로도를 자연스럽게 방지합니다.

### **3\. 로직의 의사코드 (Pseudo-code)**

개발 시 참고할 수 있는 로직의 흐름입니다.

Python

def generate\_lesson\_plan(passage\_level, selected\_kpi\_codes, duration\_minutes):  
    \# 1\. 과정 생성 시 확정된 지문 레벨과 직접 선택된 KPI를 입력으로 받음  
    \#    (자동 매핑 없음 — 사용자가 UI에서 직접 선택)  
      
    \# 2\. 레벨 범위에 맞는 모듈 필터링  
    available\_modules \= db.filter(  
        suitable\_level\_min \<= passage\_level \<= suitable\_level\_max  
    )  
      
    \# 3\. KPI 집합 커버(Set Cover) 방식으로 최적 조합 선택  
    \#    목적: selected\_kpi\_codes 전체를 중복 없이 분담하여 완전 커버  
    \#    - 신규 KPI를 추가로 커버하는 모듈을 우선 선택  
    \#    - 이미 커버된 KPI만 담당하는 모듈은 우선순위 하향  
    \#    - priority 필드를 동순위 타이브레이커로 활용  
    \#    제약조건: sum(estimatedMinutes) <= duration\_minutes  
    \#    시간 초과 시 신규 KPI 기여도 낮은 모듈부터 제거  
    candidate\_sequence \= set\_cover\_select(available\_modules, selected\_kpi\_codes, duration\_minutes)  
      
    \# 5\. 단계 결정 및 정렬 (3순위 체계)  
    \#    1순위: class_* 플래그 → 단계 결정 (단일 플래그: 확정, 다중 플래그: cognitiveLevel로 해소)  
    \#    2순위: cognitiveLevel ASC → 단계 내 인지 부하 순서  
    \#    3순위: priority DESC → 동일 cognitiveLevel 내 운영 우선순위  
    sorted\_sequence \= candidate\_sequence.sort\_by(stage\_order, cognitiveLevel, priority)  
      
    \# 6\. prerequisites / incompatibleWith 제약 검증 및 보정  
    return validate\_and\_adjust(sorted\_sequence)

### **4\. 실제 적용 시나리오 예시: "비즈니스 회화가 필요한 임원"**

1. **Input (UI 직접 선택):**
   * 지문 레벨: `C1` (과정 생성 시 지문 난이도로 자동 pre-fill, 수정 가능)
   * KPI 선택: `FLUENCY_RATE`, `PRAGMATICS` (백오피스 `KPI_CATEGORY` 목표 목록에서 멀티셀렉트 — 코드 미노출)
   * 수업 시간: `30분` (15 / 20 / 25 / 30분 중 선택)
2. **Logic 1 (Filtering):** C1 레벨 범위에 속하는 모듈 추출.
3. **Logic 2 (KPI Scoring):** `말하기유창성`, `화용성` KPI와 겹치는 모듈에 높은 점수 부여.
4. **Logic 3 (Knapsack Selection):** KPI 커버리지를 최대화하면서 30분 이하인 최적 조합 선택 → 이 예시에서는 4개 모듈이 선택됨.
5. **Logic 4 (Cognitive Arc Sorting):** `cognitiveLevel` 기준 오름차순 정렬:
   * `cognitiveLevel 1` → Word Speaking Deck (어휘 기억·이해)
   * `cognitiveLevel 2` → Response Training (즉각적 적용)
   * `cognitiveLevel 3` → Picture Description (분석·표현)
   * `cognitiveLevel 4` → Free Talking (평가·창조적 산출)
6. **Output:** 인지 부하 곡선을 따르는 4개 모듈, 30분 수업 시나리오 완성. 같은 입력이라도 모듈 풀이 달라지면 매번 다른 조합이 도출됨.

---

### **5\. 엔진 고도화를 위한 제언**

* **동적 적응 로직:** 수업 도중 정답률이 80% 미만일 경우, '마무리' 단계 전에 '중간' 단계의 보충 모듈(Review Module)을 실시간으로 추가 삽입하는 기능을 구현할 수 있습니다.  
* **데이터 피드백 루프:** 7단계에서 저장된 성과 지표를 바탕으로, 다음 수업 설계 시 취약한 KPI의 모듈 가중치를 자동으로 높여 설계합니다.

이 로직을 통해 모든 사용자에게 **개인화된 전문 교사**를 붙여주는 것과 같은 자동화된 수업 경험을 제공할 수 있습니다.

## 6\. 백오피스 기반 구현 아이디어

### 현황 분석: 기존 데이터와 로직의 매핑

백오피스 모듈관리(`AiModule`)에 이미 자동 시퀀싱에 필요한 핵심 데이터가 모두 존재합니다.

| 로직 필요 데이터 | 백오피스 DB 필드 |
|---|---|
| 수업 단계 (Intro / Body / Closure) | `classBefore`, `classMiddle`, `classAfter` |
| CEFR 레벨 필터 | `suitableLevelMin`, `suitableLevelMax` |
| 소요 시간 추정 | `estimatedMinutesMin`, `estimatedMinutesMax` |
| KPI 가중치 | `selectedKpiCodes` |
| 우선순위 | `priority` |
| 선행 모듈 제약 | `prerequisites` |
| 호환 불가 모듈 | `incompatibleWith` |
| 도메인 (Speak / Read 등) | `skill` |

### 제안 아키텍처

```
[과정 생성 UI]
  ↓ 지문 레벨 (자동 pre-fill, 수정 가능)
  ↓ KPI 멀티셀렉트 (백오피스 KPI 목록 직접 표시)
  ↓ 수업 시간 선택
[Lesson Plan Generator API]  ← packages/core에 구현
  ↓ Step 1: 모듈 필터링 (레벨 범위 매칭)
  ↓ Step 2: KPI 점수 계산 및 시퀀싱
  ↓ Step 3: 시간 제약 검증
  ↓ Step 4: prerequisites / incompatibleWith 제약 검증
[Generated Lesson Plan]
  → Studio / Tutoring 앱에서 수업 실행
```

### 핵심 구현 단계

#### 1단계: 과정 생성 UI의 입력 설계

추상적 대상/목적 매핑 대신, 과정 생성 시 이미 확정된 구체적 데이터를 직접 입력받습니다:

* **지문 레벨:** 과정 생성 시 지정된 지문의 CEFR 레벨을 자동으로 pre-fill. 수정 가능.
* **KPI 선택:** 백오피스 `KPI_CATEGORY`의 목표(`extraData.goal`)를 기준으로 중복 제거한 목록을 멀티셀렉트로 표시 (코드 미노출) → 이 수업의 집중 역량을 직접 선택. 조건 변경 시마다 가용 모듈 수 실시간 표시 (권장 미달 시 노란 경고, 0개 시 빨간 차단).
* **수업 시간:** 15 / 20 / 25 / 30분 선택 (5분 간격).

> 이 접근의 부가 효과: 선택 데이터가 누적되면 "이 레벨+KPI 조합이 자주 선택된다"는 패턴을 추후 자동 추천의 근거로 활용할 수 있습니다.

#### 2단계: LessonPlanService 구현 (`packages/core`)

```typescript
// packages/core/src/lesson-plan/lesson-plan.service.ts

interface LessonPlanInput {
  passageLevel: string;       // 지문의 실제 CEFR 레벨 (과정 생성 시 확정된 값)
  selectedKpiCodes: string[]; // UI에서 직접 선택한 KPI 코드 배열
  durationMinutes: number;    // 20, 40, 60 등
}

interface LessonPlan {
  intro: AiModule[];     // classBefore = true
  body: AiModule[];      // classMiddle = true
  closure: AiModule[];   // classAfter = true
  totalEstimatedMinutes: { min: number; max: number };
}
```

#### 3단계: 시퀀싱 알고리즘 상세

단계별 개수를 미리 정하지 않고, KPI 완전 커버리지와 인지 부하 곡선을 기준으로 최적 조합을 도출합니다.

> **핵심 발상:** 모듈에 이미 `selectedKpiCodes`가 DB로 연결되어 있으므로, "KPI와 가장 많이 겹치는 모듈"을 고르는 것이 아니라 **"선택한 KPI를 중복 없이 분담하여 빠짐없이 커버하는 최소 조합"** 을 찾는 집합 커버(Set Cover) 문제로 접근합니다. 이 방식은 각 모듈이 수업 안에서 고유한 역할을 담당하게 하고, KPI 코드 중복 없이 완전한 커버리지를 보장합니다.

```
1. suitableLevelMin ≤ passageLevel ≤ suitableLevelMax 조건으로 모듈 필터링

2. KPI 집합 커버(Set Cover) 최적화
   - 목적: 선택한 KPI 전체를 모듈 간 중복 없이 분담하여 완전 커버
   - 이미 커버된 KPI를 담당하는 모듈은 우선순위 하향
   - 새로운 KPI를 추가로 커버하는 모듈을 우선 선택
   - priority 필드를 동순위 모듈 간 타이브레이커로 활용
   예시) 선택 KPI: [말하기유창성, 즉각반응, 화용성]
         모듈 A: [말하기유창성, 즉각반응] → 선택 (2개 신규 커버)
         모듈 B: [화용성]               → 선택 (1개 신규 커버)
         모듈 C: [말하기유창성]          → 제외 (A와 중복)

3. 시간 제약 검증
   - sum(estimatedMinutesMax) ≤ durationMinutes 초과 시
   - 신규 KPI 기여도가 가장 낮은 모듈부터 제거

4. 단계 결정 및 정렬 (3순위 체계)
   - 1순위: class_* 플래그 → 모듈이 배치될 단계(Intro/Body/Closure) 결정 (관리자 의도)
     · 단일 플래그(classBefore OR classMiddle OR classAfter): 해당 단계 확정
     · 다중 플래그: cognitive_level로 적합한 단계 결정 (1-2=Intro, 3-4=Body, 5-6=Closure)
       cognitive_level도 모호하면 priority 높은 단계 채택
     · 플래그 미설정: cognitive_level로 단계 결정 후 body 폴백
   - 2순위: cognitive_level ASC → 같은 단계 내 인지 부하 순서
     · 낮은 수준(기억·이해) → 중간(적용·분석) → 높은 수준(평가·창조)
   - 3순위: priority DESC → 동일 cognitive_level 내 운영 우선순위

5. 제약 검증 및 보정
   - prerequisites: 선행 모듈이 앞에 배치되었는지 확인 후 순서 보정
   - incompatibleWith: 충돌 모듈 감지, KPI 기여도 낮은 쪽 제거
```

#### 4단계: 수업설계 UI

```
과정 생성 화면 (또는 /admin/lesson-designer)
  ├── Input 패널
  │   ├── 지문 레벨: 과정 생성 시 확정된 CEFR 레벨 자동 표시 (수정 가능)
  │   ├── KPI 선택: 백오피스 KPI_CATEGORY 목표(goal) 기준 distinct 멀티셀렉트 (코드 미노출)
  │   │   └── 실시간 가용 모듈 수 표시 (조건 변경 시마다 업데이트)
  │   │       예) "현재 조건으로 이용 가능한 모듈: 3개 (권장: 4개 이상)" → 노란색 경고
  │   │           "현재 조건으로 이용 가능한 모듈: 1개 (생성 불가)" → 빨간색 차단
  │   └── 수업 시간 선택 (15 / 20 / 25 / 30분, 5분 간격)
  │
  ├── [수업 자동 생성] 버튼 → API 호출
  │   (모듈 풀 부족 시 단계적 폴백 체인 자동 실행)
  │
  └── 결과 패널
      ├── Intro   단계: 선정 모듈 카드 (예상 소요시간 표시)
      ├── Body    단계: 핵심 훈련 모듈 카드
      ├── Closure 단계: 마무리 모듈 카드
      ├── 총 예상 시간 표시
      ├── 폴백으로 추가된 모듈은 "KPI 외 보충 모듈" 배지로 구분 표시
      └── [수동 조정] 드래그앤드롭으로 모듈 교체 가능
```

결과는 JSON으로 export → Studio / Tutoring 앱이 import하여 수업 실행.

### KPI DB 연결을 활용한 진화 경로

모듈의 `selectedKpiCodes`가 DB로 연결되어 있다는 사실은 시스템이 정적 태그에서 동적 성과 기반으로 진화할 수 있는 기반이 됩니다.

| 단계 | 모듈 선택 기준 | 데이터 소스 |
|---|---|---|
| **MVP** | KPI 집합 커버 최적화 (관리자 사전 태그) | `selectedKpiCodes` |
| **고도화** | KPI별 실측 향상률이 높은 모듈 우선 선택 | 수업 성과 DB (누적) |

고도화 단계에서는 "관리자가 이 모듈이 이 KPI에 좋다고 태그했다"는 정적 판단 대신, "이 KPI를 목표로 한 수업에서 실제로 향상률이 높았던 모듈"이라는 실측 데이터가 선택 기준이 됩니다. 수업이 쌓일수록 추천 품질이 자동으로 높아지는 구조입니다.

### 구현 우선순위 (MVP → 고도화)

| 단계 | 내용 | 비고 |
|---|---|---|
| **MVP** | `LessonPlanService` 구현 + 수업설계 UI | KPI 집합 커버 + cognitiveLevel 정렬 |
| **고도화 1** | KPI별 실측 향상률 기반 모듈 랭킹 | 수업 성과 데이터 누적 후 적용 |
| **고도화 2** | 동적 보충 모듈 삽입 | 정답률 80% 미만 시 Review Module 추가 삽입 |
