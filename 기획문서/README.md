## 문서 상태 표기 범례 (구 §0)

각 섹션·항목에는 **개발 진척도 마커**가 붙는다. 마커가 표기되지 않은 항목은 별도 검증 전이므로 임시로 "📋 기획 단계"로 간주한다.

| 마커 | 의미 |
|---|---|
| ✅ **구현 완료** | 실제 코드·DB·운영 환경에 반영되어 동작 중 |
| 🟢 **MVP** | 일부 기능 구현, 운영 검증 진행 중 |
| 📋 **기획 단계** | 문서·설계만 정의, 미구현 |
| ⚠️ **재정의** | 초기 기획과 실제 구현이 일부 달라 갱신됨 |
| ❌ **폐기** | 구버전 기획, 현재 시스템에서 제거됨 |

## 작성 범위 가이드 — 무엇을 쓰고, 무엇을 쓰지 않는가

> **본 폴더는 서비스 "기획" 문서이지 "개발" 문서가 아니다.** 구현 상세(DB 스키마·API 명세·코드 참조 등)는 각 서비스 리포지토리의 `docs/`가 소유한다. 아래 기준으로 경계를 유지한다.

쓸지 망설여지면 아래 3문항을 순서대로 묻는다. 하나라도 **No**면 리포 docs로 보낸다.

| # | 질문 | Yes → | No → |
|---|---|---|---|
| 1 | 이 내용이 바뀔 때 결정권자가 **기획/사업 측**인가? (요금·정책·UX 원칙·우선순위) | 기획문서 | 리포 docs |
| 2 | **코드를 열어보지 않고도** 맞는지 검증할 수 있는가? | 기획문서 | 리포 docs |

### 소급 적용 정책 (기존 문서 정리 시)

기존 문서에 이미 있는 ❌ 항목(SQL·API 스키마 등)은 **일괄 삭제하지 않는다.** 각 문서를 다음에 개정할 때 점진 처리한다.

1. 해당 리포 `docs/`에 대응 문서가 있으면 → 기획서에서 삭제하고 링크로 치환
2. 대응 문서가 없으면 → 리포로 이관 후 링크로 치환 (**기획서가 유일한 기록인 상태에서 삭제 금지**)
3. 이관 전까지는 블록 위에 `> ⚙️ 구현 상세 — 리포 docs 이관 대상` 표시만 부착

## 운영 규칙

1. **SSoT** — 한 주제는 소유 문서 1곳에만 기술. 다른 문서는 상대링크로만 참조. 내용 복사 금지.
2. **frontmatter 필수** — `title / version / updated / owner_service / master_origin / depends_on`. 문서 수정 시 `version`·`updated` 갱신.
3. **아카이브 불변** — `_archive/` 문서는 갱신하지 않는다. 신규 내용은 반드시 분할 문서에 기술.
4. **컴패니언 산출물** — `Picklass_모듈_카탈로그.xlsx`, `Picklass_모듈_시나리오_상세.md`, `Picklass_KPI_체계_상세.md` 등은 기존 위치(요청사항 폴더) 유지. 04_통합모듈시스템·06_진단평가_PPD에서 참조.
5. **기획서 vs 리포 docs** — 기획서 = 정책·원칙·구조, 각 서비스 리포 `docs/` = 구현 스펙. 구현 상세는 기획서에 옮기지 않는다.
6. **분할 임계** — 단일 문서가 **800줄 또는 50KB 초과** 시 §경계·SSoT 단위로 분할을 검토한다(무조건 분할이 아님). 그 미만은 주제 응집을 우선해 단일 문서로 유지한다. 분할 시 본편에 크로스링크 스텁을 남기고, 각 분할 파일은 독립 frontmatter를 갖는다. (예: Speaking 본편/KPI측정/음성인프라/앱UX/대화엔진 5분할, 2026-07-18)
